이 명령은 사이클 S3(구현)의 **선택형 기본 루프**다(`docs/harness-cycle.md` §4-3). spec·plan·다이어그램은
개발자가 직접 확정한다 — 루프는 그 다음부터 맡는다. 쓰지 않아도 사이클은 성립하고, 강제되는 것은 PR에 담기는
task 문서뿐이다(D11).

핵심 제약:

- **런타임이 아니다.** 이 문서(프롬프트)가 기존 CLI — `gate commit`·`boundary check`·`scenario check`·`review` —
  를 엮을 뿐이다. 루프 전용 CLI를 만들거나 요구하지 않는다.
- **쓰기는 단일 스레드다(D4).** 한 시점에 쓰는 주체는 Dev 하나다.
- **push·PR을 하지 않는다.** 루프는 로컬 커밋까지만 한다. push·PR·파괴적 변경은 사람의 몫이다(아래 멈춤 조건).
- **언어별 지식을 갖지 않는다.** 검사 명령은 `.harness/gates.json`과 spec의 `## Done evidence` 선언에서만 온다.

Raw slash-command 인수:
`$ARGUMENTS`

인수 해석: 모든 토큰은 이번 루프에서 특히 지킬 focus 문구로 Dev 지시와 리뷰에 그대로 전달한다.

## 진입

1. **전제 확인** — 활성 task(`.harness/active.json`), spec의 Ambiguity 게이트 통과, 미완 단계(`- [ ]`)가 있는
   `<name>-plan.md`. 하나라도 없으면 무엇이 빠졌는지 알리고 멈춘다 — spec·plan을 만드는 일은 루프 밖이다
   (`/harness-spec`·`/harness-interview`). plan의 다이어그램 단계가 미완이면 `/harness-diagram`으로 먼저 닫으라고 안내하고 멈춘다.
2. **질문** — 한 번만 묻는다: **오케스트레이터로 진행할까, 개별로 진행할까?**
   개별을 고르면 아무것도 하지 않고 끝난다 — 개별 진행은 어느 게이트에도 합류할 의무가 없다.
3. **실행 수단 probe → degrade → record** — 이 세션에 서브에이전트 도구가 있으면 Dev는 서브에이전트(`수단 subagent`),
   없으면 메인 세션이 Dev를 겸한다(`수단 main`). 어느 쪽이든 artifact 기록 줄에 수단을 남긴다.
   Workflows는 사용자가 명시적으로 요청할 때만 쓴다. 병렬 Dev(Agent teams·cross-session)는 이 루프에서 쓰지 않는다 —
   각 Dev가 격리 worktree(D5)를 가져야 하는 별도 설계다.
4. **게이트 확인** — `harness-team gate commit`이 "미설정"을 알리면 기계 검사가 시나리오 선언에만 기대게 된다는
   사실을 사용자에게 한 번 알리고 계속한다(`harness-team gate suggest`로 만들 수 있다). 미설정은 실패가 아니다.

루프는 plan의 첫 미완 단계부터 시작한다 — plan.md가 곧 상태라서, 멈췄다가 다시 부르면 그 자리에서 이어진다.
리뷰·ship·PR 같은 단계에 도달하면 구현 반복을 끝내고 마무리로 간다.

## Dev

Dev는 plan 단계 **하나**만 구현한다. Dev가 도는 동안 오케스트레이터는 쓰지 않는다. Dev는 커밋하지 않는다 —
커밋은 QA를 통과한 뒤 오케스트레이터가 한다. Dev 지시에는 아래를 담는다(서브에이전트는 이 대화를 보지 못한다):

```text
너는 Dev다. 아래 plan 단계 하나만 구현한다. 다른 단계·리팩터·요청 밖 변경을 하지 않는다.
task 문서: <spec 경로> · <plan 경로> — 먼저 읽는다. 이번 단계: <단계 원문>
직전 QA 실패 근거(있으면): <실패 집합과 요약>
금지: git commit · push · PR · 파괴적 명령 · 의존성 추가.
spec이 답하지 않는 결정이 필요하면 구현하지 말고 "spec 공백: <질문>"으로 보고하고 끝낸다.
끝나면 바꾼 파일 목록과, 이번 단계가 겨냥한 시나리오 id(있으면)를 보고한다. <focus>
```

Dev가 "spec 공백"을 보고하면 멈춤 조건으로 간다. 의존성 추가·파괴적 변경이 필요하다고 보고하면 승인 필요로 간다.

## QA

QA는 두 겹이다. read-only 검증자는 테스트를 실행하지 못한다 — 테스트가 임시 파일을 쓰기 때문이다. 그래서
기계 검사는 오케스트레이터가 실행한다. exit code를 읽는 일이라 자기 채점이 아니다. 판단이 필요한 루브릭만
별도 프로세스의 read-only 검증자가 맡는다.

단계마다 (Dev가 끝난 직후):

1. `harness-team gate commit` — exit 0이 아니면 실패.
2. `harness-team boundary check` — spec에 `## Boundary contracts`가 없으면 `not-configured`로 통과한다.
3. `harness-team scenario check` — spec에 `scenarios`를 선언했을 때만. 이번 단계 전에 증거가 없던 시나리오는 진전 판정에서 뺀다 —
   아직 만들지 않은 시나리오가 실패하는 것은 정상이다. 다만 Dev가 이번 단계에서 겨냥했다고 보고한 시나리오와,
   전에 통과했던 시나리오(회귀)는 센다.
4. 통과한 시나리오마다 실행 출력에서 **테스트 이름이 찍힌 줄**을 artifact `## 결과`에 남긴다. exit 0과 요약 개수는
   테스트가 실제로 돌았다는 증거가 아니다 — 이름 필터가 아무것도 고르지 못해도 exit 0이 난다. raw stderr는 옮기지 않는다.

**실패 집합** = 이번 회차에 실패한 검사 이름과 시나리오 id. 실패하면 멈춤 조건의 "진전 없음"을 먼저 판정하고,
아니면 실패 근거를 Dev에게 돌려보낸다.

모든 단계가 끝난 뒤(마무리):

5. `harness-team review <engine> --framing scenario --scope diff` — 시나리오를 선언한 task에서만. 루브릭은 모든 단계가 끝난 뒤 한 번 돌린다 —
   단계마다 돌리면 아직 만들지 않은 시나리오가 E1에서 실패한다. `<engine>`을 생략하면 CLI가 폴백 체인(codex → claude)으로 고른다.
   fail 판정은 오케스트레이터가 재현·판별한 뒤(D6) 실패 집합으로 삼아 Dev에게 돌려보낸다.
6. R3 — `harness-team review <engine> --scope diff`. 발견은 재현·판별한 뒤 유효한 것만 Dev 턴으로 반영하고, 반영 뒤에는
   1–4를 다시 돈다. 같은 task에 리뷰를 동시에 두 번 돌리지 않는다.

## 커밋과 기록

QA 1–4를 통과하면 오케스트레이터가:

1. plan의 그 단계를 `- [x]`로 바꾸고, 구현과 함께 로컬 커밋한다(프로젝트 커밋 관례, 훅 우회 금지). 커밋 훅이 실패하면 QA 실패로 다룬다.
2. 커밋 직후 artifact `## 결과`에 기록 줄과 "무엇을, 왜 했는지" 한두 줄을 남긴다. 기록 줄 형식:
   `- loop: <YYYY-MM-DD> · 수단 <subagent|main> · 단계 <plan 단계 요약> · QA pass · commit <sha7>`
   이 기록과 post-commit 훅의 handoff 변경은 다음 커밋에 담긴다.
3. 다음 미완 단계로 간다.

멈출 때도 한 줄을 남긴다: `- loop: <YYYY-MM-DD> · 수단 <subagent|main> · 단계 <plan 단계 요약> · 멈춤 <조건>`.

## 멈춤 조건

멈추면 사람에게 무엇이 남았는지 보고한다 — 멈춘 조건, 마지막 실패 집합, 커밋된 단계, 다음 한 걸음.

- **성공** — 모든 단계 통과 + 루브릭(시나리오 선언 시) + R3 통과. PR은 사람이 만든다 — `/harness-ship`으로 넘긴다.
- **spec 공백** — Dev나 QA가 spec이 답하지 않는 질문을 만났다. 질문을 사람에게 그대로 넘긴다(R1로 되돌림).
  spec이 고쳐지면 `/harness-loop`를 다시 불러 이어간다.
- **진전 없음** — 직전 Dev 턴 이후 실패 집합이 같고 diff에도 변화가 없으면 멈춘다. 비교는 Dev 턴 전후의
  `git diff HEAD` 출력과 실패 집합이다. 횟수 상한을 두지 않는다 — 상한은 진전 중인 루프를 끊고, 진전 없는 루프는
  상한에 닿을 때까지 헛돈다.
- **승인 필요** — push·PR·파괴적 변경·의존성 추가처럼 되돌리기 어려운 행위가 필요하다. 하지 않고 멈춘다.

## Codex

v1에서 Codex는 루브릭(5)과 R3(6)의 검증 엔진이다 — 작성 엔진과 달라 자기 승인 편향이 없다. Codex가 없으면
CLI가 claude 엔진으로 대신한다. Codex 세션이 이 루프의 오케스트레이터를 맡는 경로는 **실험적**이다 — D2
(drive = Claude)와 D9를 먼저 고쳐야 하는 별도 결정이다. Codex는 병렬 서브에이전트가 기본이라, 그 경로에서
순차 실행은 설정이 아니라 이 문서의 지시로만 지켜진다.
