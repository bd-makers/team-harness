— harness-team observe

0.26.0은 기능 하나를 담습니다. observe-tools 훅은 0.15.x부터 도구 호출마다 JSONL을 써 왔지만, 그 로그를 읽는 코드는 저장소에 하나도 없었습니다. 외부 6층 플레이북과 이 하네스를 층별로 비교한 분석이 그것을 "쓰기만 있는 관측"으로 짚었고(권고 ①), 이 릴리스는 최소형 소비자 — 스코어카드와 트립와이어 2종 — 로 답합니다. 발화하면 exit 1이라 훅과 CI가 센서로 쓸 수 있습니다.

.harness/observability/v1/<day>/*.jsonl을 창(기본 7일, 상한은 훅 보존 기간 14일)만큼 읽어 일별 · task별 · 도구 분류별로 started · finished · failed · denied · 실패거부율 · interrupted · p50/p95 · 바이트 · usage 토큰을 집계합니다. text 표는 핵심 7열, --json의 scorecard에 전체 필드가 있습니다. 모듈은 읽기 → 순수 집계 → 렌더의 세 층이고 집계 함수는 레코드 배열만 받습니다.
왜
PDF L6의 운영 질문 — "가장 비싼 task는? 어느 센서가 가장 많이 잡았나? 한 시간 안에 실패를 알 수 있나?" — 에 이 로그로 답할 수 있는 만큼만 답합니다. 토큰 usage는 도구 응답에 거의 실리지 않아 비용 열은 대부분 비고, 도구 이름은 HMAC이라 분류만 보입니다. 그 한계를 숨기지 않고 표에 그대로 둡니다.
그래서
task 참조는 로컬 .key와 docs/<user>/<task>/*-meta.json으로만 HMAC을 재계산해 이름으로 되돌립니다 — 훅 파일을 import하지 않고, 실제 훅으로 쓴 레코드의 task_ref가 재계산값과 같음을 테스트가 고정합니다. 심볼릭 링크 · .jsonl이 아닌 파일 · 창 밖 날짜는 읽지 않고, 깨진 줄 · v≠1 · 필수 필드 누락 · 비문자열 task_ref · 파싱 불가 날짜는 건너뛰고 skipped_lines로 셉니다. 로그는 절대 수정·삭제하지 않습니다.

트립와이어 2종 — PDF TABLE VII를 이 로그의 신호로

브레인스토밍에서 넷 중 둘을 골랐습니다. 로그가 주는 신호로 판정할 수 있는 것은 실패·거부율, 같은 도구 반복 실패, 쓰기 호출 급증, 소요시간 급증 네 가지였고, 센서 통과율·도메인 접촉은 로그에 없습니다.

임계값 넷(20 · 5 · 2× · 3회)은 PDF 표와 오탐 방지 바닥값에서 정했고 실사용 데이터로 보정하지 않았습니다. 넷 다 export 상수라 조정은 한 줄입니다. 쓰기 호출 급증·소요시간 3×는 후보로 남겨 두었고, doctor 배선과 SessionStart 한 줄 nudge는 이 릴리스의 범위 밖입니다 — "한 시간 안에 알 수 있나"에 가장 가까운 것은 후자라 다음 결정입니다.

외부 리뷰 — P2 둘, P3 넷, 다섯 반영

codex read-only 리뷰(gpt-5.6-sol)가 브랜치 diff와 task 문서를 봤습니다. 발견은 주장이고, 작성 세션이 테스트로 재현한 뒤에만 반영했습니다. 마커는 task artifact ## Reviews에 있습니다.

심각도리뷰어가 뚫은 것판별 · 반영
P2task_ref: 123인 한 줄이 reader를 통과한 뒤 .slice에서 TypeError로 명령 전체를 중단진짜(테스트로 재현) — reader가 null/문자열만 통과시키고 집계도 비문자열을 (no task)로 처리
P2text 표가 spec·문서가 약속한 succeeded·p50·바이트·usage를 보이지 않음사실이나 터미널 폭 때문에 핵심 열만 보이게 한 설계 — 코드가 아니라 문서를 좁힘("text 7열, 전체는 --json")
P3날짜를 recorded_at 앞 10자로 판정해 offset 타임스탬프가 UTC 자정 근처에서 잘못된 날로 집계사실(훅은 항상 Z를 쓰지만 순수 함수 입력은 아님) — Date.parse 기반 UTC 일 판정, 파싱 불가 레코드는 건너뜀
P32× 테스트가 실제로는 2.5×라 구현이 >로 회귀해도 통과진짜 — 정확히 2×(0.25→0.50) 발화·0.45 비발화 테스트 추가, 구현을 >로 바꿔 실패를 확인한 뒤 복원
P3spec은 잘못된 --days의 status를 invalid라 적었는데 구현은 error사실 — spec을 fail 관례(error)로 정정
P3성공 경로가 process.exitCode를 0으로 되돌리지 않음기각 — CLI는 프로세스당 명령 하나이고 summary·doctor도 리셋하지 않는 관례
리뷰어가 못 돌린 것: 임시 디렉터리가 필요한 통합 테스트 9건은 read-only 샌드박스의 mkdtemp EPERM으로 실행되지 않았고(26건 통과), 작성 세션의 전체 npm test가 그 자리를 채웠습니다. 리뷰어는 재리뷰를 권했지만 수정이 4곳·테스트 4건으로 작고 전부 테스트가 고정해 생략했습니다.

이 릴리스가 남기는 것

export된 순수 함수는 호출자가 곧 입력 경계다

비문자열 task_ref를 reader에서만 막았더니 집계 함수를 직접 부르는 경로가 TypeError로 남았습니다. 파일을 읽는 층과 계산하는 층을 나눈 이유가 "계산 층은 어떤 배열을 받아도 죽지 않는다"였으므로, 방어는 두 층 모두에 둡니다.

경계 테스트는 임계값 그 자체를 친다

"2배 이상"을 2.5배로 검증하면 >=가 >로 바뀌어도 통과합니다. 정확히 2×를 발화로, 그 바로 아래를 비발화로 고정하고, 구현을 일부러 >로 바꿔 실패하는 것을 봤습니다 — 0.25.0의 "⊆ 대신 집합 동등" 교훈과 같은 종류입니다.

브레인스토밍의 architectural 경로가 파일 11개 규모에 맞았다

코드 전에 결정 넷 — 형태(새 하위명령만), 트립와이어(넷 중 둘), 발화 시 exit 1, 훅 파일을 import하지 않고 HMAC을 재구현(테스트로 동일성 고정) — 을 질문 두 개와 설계 승인 한 번으로 고정했고, spec의 Ambiguity 게이트와 plan의 Task별 RED→GREEN이 그 위에서 돌았습니다. 구현 중 되돌린 결정은 없었습니다.
