Verification guide · 0.20.0

루브릭 평가 —
자기 채점을 믿지 않는 방법

0.20.0의 D6(적대적 검증)은 작업 산출물의 품질 판정을 작업자 자신에게서 떼어내 별도 컨텍스트의 read-only 검증자에게 맡깁니다. 검증자는 루브릭(finding 스키마)으로 반박만 하고, 반영은 작성 세션이 재현·판별한 뒤 단일 스레드로 수행합니다. 이 문서는 그 전체 계약 — 스키마·프레이밍·엔진·마커·게이트 — 을 한 장에 담습니다.

0.20.0 기준 D6 = D2의 작업 단위 적용 read-only 검증자 루브릭 5 + 1 자동 수정 루프 금지
대상
하네스에서 검증 프레이밍(/harness-review 계열·페르소나 외부 엔진 모드)을 쓰거나 설계하는 사람

1. 왜 루브릭인가 — 결정론 가드가 못 하는 일

하네스의 가드는 두 층으로 나뉩니다. 이 구분을 모르면 "가드가 있는데 왜 또 검증자냐"가 됩니다.

결정론 게이트가 강제하는 것 — "기록했는가"

harness-team done은 판정 창 안의 커밋·테스트 파일 변경·리뷰 마커의 존재를 검사합니다. 빠르고 반박 불가능하지만, 마커 뒤의 리뷰가 대충이었는지는 알 수 없습니다. 가드 스스로 "이 체크가 막는 것은 망각이다"라고 명시합니다.

자기 채점이 새는 곳 — "품질 판정"

품질 판정을 작업자 자신의 자가 채점에 두면 낙관적 체크가 게이트를 무력화합니다. spec을 쓴 세션이 자기 spec의 가정을 반박하면 sunk-cost 편향이 반론을 무디게 하고, 테스트를 쓴 세션은 tautological 테스트를 알아보지 못합니다.

D6의 답은 새 메커니즘이 아니라 기존 원칙의 재사용입니다 — D2(작성자·리뷰어 분리)를 릴리스 단위가 아닌 작업 단위에 적용하고, 실행 경로는 /harness-review의 엔진 runner 표와 마커 계약을 그대로 씁니다. 검증자는 읽기만 하므로 D4(단일 스레드 쓰기)를 위반하지 않습니다.

✅
판정 주체 분리 + 실행 표면 최소화

"판정 주체를 분리하되 실행 메커니즘은 기존 리뷰 경로를 재사용해 표면 증가를 최소화한다" — docs/decisions.md D6. 새 CLI 서브커맨드도, 새 훅도 없습니다. 커맨드 문서의 프롬프트 교체 + 마커 접미사가 전부입니다.

2. finding 스키마 — 모든 프레이밍이 공유하는 5필드

검증자의 산출물은 산문 감상이 아니라 finding 표입니다. 각 행은 다섯 필드를 갖습니다.

필드값규칙
idA1·T3·S5 …루브릭 표의 행 식별자 — 어느 항목을 채점했는지 추적 가능해야 한다
항목pass 조건 서술루브릭이 정의한 검사 내용
심각도BLOCKER MAJOR MINORBLOCKER fail이 하나라도 남으면 해당 게이트(완료 선언·준비 완료 선언)를 통과하지 못한다
판정pass / fail / na증거 없는 항목은 pass가 아니라 na — 정직성 규칙
근거파일·git·실행 출력 인용산문은 신호가 아니다. spec/plan 문장 인용, file:line, 명령 출력만 근거가 된다

정직성 규칙

pass 판정은 파일·git·실행 출력 증거에만 근거한다. 증거를 인용할 수 없으면 na다. sim 루브릭의 "프로즈 신뢰 금지" 결정을 상속했다.

자동 수정 루프 금지

검증자의 발견은 주장이지 사실이 아니다. 검증자에게 쓰기·자동 반영 권한을 주면 read-only 리뷰 원칙과 D4가 동시에 무너진다.

BLOCKER 게이트

BLOCKER fail이 남아 있는 동안 testcritic은 "완료"를, shipcheck는 "준비 완료"를, contrarian(A1)은 "구현 진입"을 선언하지 못한다.

3. 검증 루프 — 누가 읽고, 누가 쓰는가

모든 프레이밍이 같은 루프를 돕니다. 쓰기는 항상 driver(작성 세션) 한 곳에서만 일어납니다.

4. 프레이밍 5 + 1 — 무엇을, 어느 층에서 반박하나

검증 프레이밍은 kind=<engine>-<프레이밍> 접미사로 구분됩니다. 절차·엔진 표는 전부 /harness-review를 재사용하고, 각자 리뷰 프롬프트(루브릭)만 교체합니다.

프레이밍대상 층루브릭진입점kind / scope막는 것
adversarial 구현 diff 자유 반박 (P1–P3 심각도) /harness-adversarial-review -adversarial / worktree|diff 거부되어야 할 설계·접근이 머지되는 것
testcritic 새 테스트 T1–T6 테스트 3형제 6단계 (unittest·comptest·inttest) -testcritic / worktree|diff tautological·mock 반향 테스트가 "커버리지"로 통과하는 것

ℹ️
interview만 외부 엔진이 없는 이유

선행 채점은 D6 정직성 규칙(증거 없는 pass는 na)을 그대로 상속하지만, 문답 자체는 여전히 사용자와의 대화입니다 — 숨은 가정은 코드가 아니라 사용자의 머릿속에 있어서, 외부 검증자가 대신 캐낼 수 없습니다. 그래서 리뷰 마커도 남기지 않고 spec의 Ambiguity 체크박스를 채점표 근거로만 갱신합니다.

5. 라이프사이클 — 어느 단계에 어떤 검증이 꽂히나

task의 흐름(spec → plan → 구현 → 테스트 → ship → done)마다 반박의 대상이 다릅니다. 전부 옵트인이며, 중요한 변경(AGENTS.md 리뷰 프로토콜 기준)에서 켭니다.

6. 엔진 층 — 누가 검증자가 되나

프레이밍(무엇을 채점하나)과 엔진(누가 채점하나)은 직교합니다. 엔진 미지정이면 probe 폴백 체인 codex → claude가 첫 가용 엔진을 씁니다(Gemini는 멤버가 아니다 — D7).

엔진호출분리 수준비고
codexcodex exec --sandbox read-only "…" < /dev/nullvendor 분리< /dev/null 생략 금지 — stdin이 열려 있으면 무한 블로킹
claudeclaude -p --permission-mode plan "…"컨텍스트 분리만sunk-cost 편향은 제거되지만 같은 모델의 맹점은 공유 — 폴백 체인의 마지막인 이유
custom.harness/reviewers.json의 custom.command 템플릿설정에 따름명시 호출 전용 — 폴백 체인에 포함되지 않음. read-only 요건은 사용자 책임
⚠️
claude 엔진의 한계를 알고 쓰기

claude-only 팀원의 경로로는 유효하지만, "외부 검증"의 외부가 컨텍스트까지인지 vendor까지인지가 다릅니다. 중요한 변경일수록 vendor 분리 엔진(codex)을 우선하세요.

7. 마커 계약과 증거 게이트 — 검증을 결정론에 연결

검증의 품질 판정은 사람과 검증자의 몫이지만, "검증이 있었는가"는 done 가드가 기계적으로 확인합니다. 연결 고리가 artifact의 한 줄 마커입니다.

<!-- artifact ## Reviews 기록 끝에 한 줄로 append -->
<!-- harness:review kind=codex-testcritic scope=diff tip=3fa1b2c at=2026-08-28T09:00:00Z -->
Done evidence 키기본값가드가 인정하는 마커
review: required optional 판정 창 안의 모든 리뷰 마커 — kind를 목록 대조하지 않는다 (커스텀 엔진·새 프레이밍이 코드 변경 없이 통과하는 확장점)
verify: required optional (0.20.0) kind가 검증 프레이밍 접미사로 끝나는 마커만 — -adversarial · -testcritic · -shipcheck · -contrarian · -simplifier
  • 검증 마커는 review 증거를 겸하지만, 역은 성립하지 않는다 — 일반 kind=codex 리뷰는 verify: required를 만족하지 못한다.
  • 접미사 열거의 정본은 commands/harness-review.md 5단계이고, src/commands/task.mjs의 VERIFY_KIND_SUFFIXES 상수와 pin 테스트로 양방향 동기화된다.
  • 가드는 마커의 존재·kind·시각만 읽는다 — finding 내용(BLOCKER가 실제로 해소됐는지)의 판정은 결정론 게이트 밖이며, 그것이 D6의 역할 분담이다.
  • 판정 창보다 앞선 마커는 무효다 — 창의 시작은 <name>-meta.json의 firstActivatedAt.

8. 함정 — 루브릭이 있어도 새는 곳

산문 pass

"전반적으로 잘 작성됨 — pass"는 판정이 아니다. 근거 인용이 없는 pass는 na로 적어야 하고, na가 남은 표는 "검증 완료"가 아니다.

검증자에게 고치게 하기

"발견한 김에 수정까지"는 편해 보이지만 read-only 원칙과 D4를 동시에 깬다. 검증자의 출력은 항상 주장이고, 반영 전에 driver가 재현·판별한다 — 오탐을 그대로 반영하는 것도, 검증 없이 기각하는 것도 금지다.

마커 없는 기록

artifact에 리뷰 요약을 남겨도 마커 한 줄이 없으면 가드에게는 보이지 않는다. "기록 없는 리뷰는 안 한 것"의 기계 판독 버전이다.

일반 리뷰로 verify 채우기

verify: required는 검증 프레이밍 접미사만 센다. /harness-review codex를 아무리 돌려도 kind=codex는 verify 증거가 되지 않는다 — 프레이밍이 다르면 묻는 질문이 다르기 때문이다.

모든 task에 풀 게이트 걸기

반대 방향의 함정. 검증 프레이밍은 중요한 변경(새 기능·아키텍처·복잡한 리팩토링·보안·스키마/API)용 옵트인이다. 작은 버그·문서 수정에까지 걸면 게이트가 요식이 되고, 요식이 된 게이트는 진짜 필요한 곳에서도 대충 통과된다.

kind 접미사 확장

새 프레이밍이 필요하면 kind=<engine>-<새이름>으로 오늘 바로 쓸 수 있다(review 가드는 kind 비대조). 단 verify 증거로 인정받으려면 정본 열거(harness-review.md 5단계)와 VERIFY_KIND_SUFFIXES를 함께 갱신해야 한다 — pin 테스트가 한쪽만 바뀐 상태를 잡는다.
