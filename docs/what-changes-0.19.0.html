Node 24 (BREAKING) 죽어 있던 done 가드 거짓 초록 3종 이월과 방향
Release note · 2026-08-26

초록이던 것들이
사실은 아무것도 재지 않았다

0.19.0은 최소 Node 버전을 24로 올리는 BREAKING 변경과 함께, 통과하고 있었지만 실제로는 검사하지 않던 가드들을 되살리는 minor 릴리스입니다. done의 테스트 증거 가드는 문서를 테스트로 오분류해 사실상 죽어 있었고, 시뮬레이션 SC7은 7개 경로에서 false-PASS를 냈으며, perf 예산은 부하에서 무작위로 빨개졌고, CI annotation은 실패 없이 조용히 비어 있었습니다. 넷 다 형태가 같습니다 — 신호는 초록인데 정작 검증하려던 일은 일어나지 않았다.

BREAKING — 최소 Node 버전이 18에서 24로 올라갑니다

두 가지가 겹친 결과입니다. 지원 종료된 런타임만 시험하고 있었고, 우리를 괴롭히던 러너 버그의 수정이 v24 라인에만 백포트됐습니다.

업그레이드 전에 확인하세요: engines.node가 ">=24"입니다. Node 18·20·22에서는 harness-team CLI 설치가 거부됩니다. 이 하네스는 런타임 의존성이 0개이므로 Node만 24로 올리면 다른 마이그레이션은 없습니다.
Changed · BREAKING

engines.node: ">=24"

변경
CI 테스트 matrix를 [18, 20] → [24]로, 릴리스 발행 런타임을 20 → 24로 옮겼습니다. README·docs/prerequisites.md·MAINTAINING.md의 "Node.js ≥ 18" 서술도 함께 정정했습니다.
왜
Node 18(2025-04-30)·20(2026-04-30)이 둘 다 지원 종료라 CI가 EOL 런타임만 시험하고 있었습니다. 릴리스 발행 job까지 node 20에서 돌고 있었습니다.
그래서
"활성 LTS 두 개(22·24)"가 아니라 24 단독입니다 — 아래 카드의 백포트 사정 때문입니다. 22를 넣으면 flake가 그대로 되돌아옵니다.
Fixed

node:test 러너 flake — 백포트는 v24에만

변경
node:test가 결과 payload 길이를 부호 있는 정수로 읽는 버그(nodejs/node#64061)가 CI를 간헐적으로 빨갛게 만들었습니다. 수정(nodejs/node#64706)은 26.7.0에 들어간 뒤 v24 라인에만 백포트됐습니다.
왜
v22는 활성 LTS인데도 백포트를 받지 못했습니다. "활성 LTS로 옮기면 해소된다"는 전제가 실측으로 반증됐고, 그래서 24 단독이 됐습니다.
그래서
실제 해소는 Node 24.20.0(2026-08-26) 이후입니다 — node-version: 24는 최신 24.x로 해석되는데 그 이전 최신인 24.19.0에는 백포트가 없습니다. 워크플로우가 매 실행마다 ::notice::runtime vX.Y.Z를 남겨 이를 추정이 아니라 사후 확인으로 만듭니다.

죽어 있던 done 가드를 되살렸습니다

0.18.1이 더한 증거 기반 가드 2종은 켜져 있는 것처럼 보였습니다. 실제로는 둘 다 통과할 수 없는 조건이거나, 통과하지 말아야 할 것을 통과시키고 있었습니다.

Fixed

모든 task가 자기 spec으로 테스트 가드를 통과하고 있었다

변경
isTestPath()가 문서를 테스트 파일로 오분류했습니다. ① basename 규칙 (^|[._-])(test|spec)s?\.에 <name>-spec.md의 -spec.md가 걸렸고 ② 디렉터리 규칙 specs?/에 docs/**/specs/*.md가 걸렸습니다. 이제 두 규칙이 신호의 세기에 맞는 확장자 조건을 각각 씁니다.
왜
모든 task가 자기 spec을 커밋합니다. 소스만 바꾸고 테스트를 한 줄도 안 써도 spec 커밋 하나로 가드가 통과했습니다 — 가드는 존재했지만 아무것도 막지 못했습니다.
그래서
두 규칙에 같은 화이트리스트를 걸면 tests/foo.test.mts·tests/run-e2e처럼 목록 밖·무확장자 테스트가 증거에서 빠져 정직한 작업이 차단됩니다(codex 리뷰 P2에서 반증). 디렉터리 규칙(강한 신호)은 산문만 걷어내고, basename 규칙(약한 신호)은 코드 확장자만 인정합니다.
Fixed

판정 창이 종결 때마다 스스로 초기화됐다

변경
가드가 증거를 찾는 창의 시작점이 active.json의 switchedAt이었는데, 이 값은 "마지막 활성화 시각"이지 "이 task의 작업 구간"이 아닙니다. 이제 창의 시작은 <name>-meta.json의 새 필드 firstActivatedAt(생성 시 1회만 기록)입니다.
왜
done은 활성 task만 대상이라 끝난 task를 닫으려면 재활성화해야 하고, 그 재활성화가 창을 초기화해 이미 만족된 리뷰 마커·커밋을 창 밖으로 밀어냈습니다 — 종결 시 항상 재현됐습니다.
그래서
필드가 없는 기존 task는 시각 비교를 포기해 degrade합니다(리뷰 마커는 존재만 확인, 커밋 0개·테스트 미작성 가드는 건너뜀). 다른 시각으로 대체하지 않는 이유는 git log --since가 리포 전체를 스캔해, 창을 넓히면 다른 task의 커밋이 이 task의 가드를 만족시키기 때문입니다.
이 릴리스로 가드가 처음 실제 발동합니다. 소스를 바꾸고 테스트를 쓰지 않은 task는 이제 done에서 막힙니다. 불필요한 경우 spec에 "tests": "skip"을 선언하세요 — --force를 상습화하면 가드 전체가 무력해집니다.

거짓 초록 3종 — 통과가 곧 검증은 아니다

시뮬레이션·성능 예산·CI annotation. 셋 다 초록을 냈지만, 셋 다 정작 재려던 것을 재지 않았습니다.

Fixed

perf 가드가 CI에서 무작위로 빨개지던 문제

변경
예산의 분모를 bare 스폰에서 동일 작업량 baseline으로 바꾸고, 차(ms)가 아니라 비(배수)로 판정합니다 — cold 3배·checkpoint 5배. 절대 상한 500/800ms는 값 그대로 두되 모든 스폰 shape에 untimed warmup을 붙였습니다.
왜
부하 중 첫 cold 샘플이 453~541ms(정상 60~90ms)로 튀어 상한 자체가 flake 발생원이었습니다. matrix 경합설은 기각했습니다 — gh api .../jobs로 확인한 결과 두 job은 서로 다른 hosted 러너 VM에서 돌아 max-parallel: 1이 no-op이고, 실제 부하원은 제거할 수 없는 호스트의 noisy neighbour입니다.
그래서
탐지력은 낮추지 않았습니다. CPU burn 주입 mutation test에서 신규 가드가 잡는 회귀 임계는 +58ms → +35ms로 오히려 좁아졌습니다.
Fixed

CI annotation이 실패 없이 조용히 비어 있었다

변경
계측 패턴이 ^# spawn floor처럼 TAP 접두사에 앵커돼 있었습니다. node ≤20은 기본 리포터가 TAP이고 ≥22는 spec(ℹ·✖·AssertionError)입니다. 이제 접두사가 아니라 내용으로 매칭하고, 실패 패턴에 두 리포터를 모두 넣었습니다.
왜
matrix를 [24]로 옮긴 첫 실행은 green이었지만 annotation은 한 줄도 나오지 않았습니다. 이 저장소를 유지보수하는 머신은 raw CI 로그를 받을 수 없어(blob storage 403) annotation이 유일한 진단 경로입니다 — 그 머신에게는 가장 나쁜 형태의 침묵이었습니다.
그래서
이번에는 추정하지 않고 네 조합(node 20·24 × 통과·실패)의 실제 출력을 캡처해 패턴을 검증했습니다. 실패는 ::error::, perf 수치는 통과한 run에서도 ::notice::로 남습니다.
Added

harness-sim SC7 — /harness-spec 산출물 검증

변경
0.18.0이 인도한 /harness-spec은 시뮬레이션 커버리지가 0건이었습니다. 전용 시나리오를 두어 결정적 산출물만 채점합니다 — 트리거 해석, (interview) 출처 태그, 자가진단 절, specSources read-modify-write, merge 시 알 수 없는 절 보존.
왜
SC5를 일반화할 수 없었습니다. SC5는 canon.dir를 SC3·SC4와 공유하는데 harness-spec은 writer라 그 자리에 쓰고, SC4가 active.json을 null로 만든 뒤라 그대로 돌리면 "활성 task 없음"으로 조기 종료합니다.
그래서
접히지 않는 것(라이브 MCP fetch·대화 UX·replace/cancel)은 PASS로 위조하지 않고 N/A + 사유로 리포트에 남깁니다. 채점을 순수 함수로 분리해 export했으므로 토큰 없이 CI에서 검증됩니다 — tests/agentloop-spec-signals.test.mjs.
Fixed

SC7의 false-PASS 경로 7건 차단

변경
기존 값 보존을 "비어 있지 않음"으로, merge 보존을 sentinel 잔존만으로, specSources를 저장 여부만으로 봤습니다. 이제 원래 값과의 동등성·merge가 spec을 실제로 갱신했다는 증거·프롬프트로 준 값 대조·실제 heading과 체크박스 존재·trial마다 독립 샌드박스로 판정합니다.
왜
7번째가 가장 미묘했습니다 — "보존했다"와 "쓰기가 아예 없었다"를 구분하지 못했습니다. 기대값을 실행 직전 파일에서 읽으므로 커맨드가 config를 아예 건드리지 않아도 비교가 참이 되는데, 유닛 테스트가 그 false-PASS를 의도된 동작으로 못박아 회귀 방지가 아니라 회귀 고정이었습니다.
그래서
실행 전 원문과 대조해 쓰기가 없으면 PASS가 아니라 N/A로 접고, N/A를 FAIL로 접던 aggregateTrials도 함께 고쳤습니다(전부 N/A → N/A, 일부 N/A → N/A, FAIL이 섞이면 FAIL). 트리거·인계 판정에 a.ok를 더해 타임아웃·spawn 실패가 PASS로 집계되던 경로도 닫았습니다.

이월과 이번 릴리스가 택한 방향

옛 리뷰 이름 4개의 제거는 0.20.0으로 다시 이월합니다. commands/harness-codex-review.md·commands/harness-codex-adversarial-review.md와 동명의 스킬 2개, 총 4개의 포워딩은 0.19.0 트리에 그대로 남습니다. 선행 조건인 팀원 머신 전역 CLAUDE.md의 새 이름 전환이 아직 확인되지 않았고, 옛 이름을 부르는 안내가 살아 있는 동안 포워딩을 지우면 그 안내가 그대로 실패하기 때문입니다. 다만 README.md가 안내하던 옛 이름은 이번에 /harness-review codex·/harness-adversarial-review codex로 고쳤습니다 — 이월된 것은 하위 호환이지 권장 경로가 아닙니다.

초록은 증거가 아니다

이번 릴리스에서 고친 것 넷은 증상이 전혀 달랐습니다 — 종결이 막히지 않고, 시뮬레이션이 통과하고, CI가 무작위로 빨개지고, annotation이 비어 있었습니다. 그런데 원인의 형태는 하나였습니다: 신호는 나오는데 그 신호가 재려던 것을 재지 않았다. 문서를 테스트로 세고, 우리가 심은 sentinel의 잔존을 보존의 증거로 세고, 스폰 비용 분모로 작업량 지연을 재려 했습니다. 가드를 새로 더하는 것보다, 이미 있는 가드가 정말로 무엇을 재는지 한 번 더 확인하는 편이 값이 큽니다.

탐지력을 낮추는 방식으로 flake를 없애지 않는다

flake는 임계를 헐겁게 하면 언제나 사라집니다 — 그리고 가드도 함께 사라집니다. perf 예산은 분모를 바꿔 측정 대상은 그대로 두고 잡음만 소거했고, mutation test로 탐지 임계가 좁아졌음을 확인한 뒤에 채택했습니다. 마찬가지로 SC7의 false-PASS를 막을 때도 검증을 느슨하게 하는 대신 N/A라는 정직한 상태를 새로 만들었습니다.

가드가 처음 발동하는 릴리스는 시끄럽다

0.18.1의 테스트 증거 가드는 이번에 처음으로 실제 동작합니다. 지금까지 통과하던 작업 방식이 갑자기 막힐 수 있고, 그것이 이 수정의 의도입니다. 막히는 것이 부당하다고 느껴지면 --force가 아니라 spec의 ## Done evidence 선언으로 끄세요 — --force가 습관이 되는 순간 이 가드들은 다시 장식이 됩니다.
