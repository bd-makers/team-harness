탐색이 실행이 되던 구멍

원인은 하나입니다: CLI가 인자를 검사하지 않고, 모르는 것을 전부 true로 받아들인 뒤 기본값으로 명령을 실행했습니다.

업그레이드 시 확인: 이제 인식하지 못하는 플래그는 실행되지 않고 exit 2로 거부됩니다. 지금까지 조용히 무시되던 오탈자·구식 플래그를 넘기는 스크립트가 있다면 그 호출이 실패합니다 — 조용히 다른 동작을 하는 것보다 나은 실패입니다.
Help gate

--help가 명령을 실행하던 문제

변경
src/cli-args.mjs의 resolveInvocation이 argv 전체를 먼저 해석해 help·version 응답을 라우터에 닿기 전에 끝냅니다. 명령 자리든 뒤든 --help는 언제나 사용법이고, 그 판정은 파싱 오류·플래그 오류보다 우선합니다.
왜
CLI는 --help를 command 자리에 있을 때만 인식했습니다. harness-team release --help는 help를 평범한 boolean 플래그로 파싱한 뒤 라우터로 내려가 매니페스트 4개를 범프하고 ~/.claude의 캐시·마켓플레이스·installed_plugins.json까지 썼습니다.
그래서
모든 명령이 --help·-h에 사용법으로 답합니다. 없던 --version도 추가했습니다 — 안전하게 탐색하려는 호출이 Unknown command가 되면, 다음 시도는 부작용 있는 명령이 됩니다.
Flag validation

오탈자가 기본값 릴리스가 되던 문제

변경
명령이 선언하지 않은 플래그는 exit 2로 거부합니다. 값이 필요한 플래그(--target 등)에 값이 없는 경우도 마찬가지입니다.
왜
같은 뿌리입니다: 모르는 플래그가 조용히 true가 되고 명령은 기본값으로 실행됐습니다. --dryrun 오타 하나가 release에서는 live 범프였고, 값이 빠진 --target은 boolean이 경로 해석에 도달해 무관한 TypeError로 죽었습니다.
그래서
틀린 호출은 아무 일도 하지 않고 무엇이 틀렸는지 말합니다. -- 뒤는 전부 자유 텍스트라 retro -- --help는 그 단어를 기록하고, doctor --target -h의 -h는 값으로 다뤄집니다.

플래그 계약

1차 수정은 같은 실패를 다른 자리에서 재현했습니다 — 외부 리뷰가 그것을 잡았습니다.

Codex review

수용되지만 무시되던 backup 플래그

변경
각 명령은 자기 구현이 실제로 읽는 플래그만 선언합니다. backup·migrate는 backup 플래그를 선언하지 않고, --backup-parent는 init/apply만 가집니다. 선언한 플래그가 그 명령을 처리하는 모듈에서 읽히지 않으면 테스트가 실패합니다.
왜
1차 수정이 backup 계열 전체에 --backup-dir를 허용했는데, backup과 migrate는 loadBackupDir만 호출해 그 값을 읽지 않습니다. harness-team backup --backup-dir B가 오류 없이 통과한 뒤 기존 설정 A에 대해 파일을 옮기는 — 이번 릴리스가 없애려던 것과 정확히 같은 종류의 실패입니다. Codex read-only 외부 리뷰가 지적했습니다.
그래서
"허용되는 플래그"와 "실제로 동작하는 플래그"가 테스트로 묶였습니다. 명령 테이블이 help 문구와 검증의 단일 소스이므로, 문서화되지 않은 플래그를 몰래 받는 경로도 없습니다.
Docs

릴리스 절차를 실제 운용에 맞춤

변경
MAINTAINING.md의 릴리스 단계를 main 기준(범프 커밋 → push → 태그 push)으로 고치고, 이제 거짓이 된 --help 함정 경고를 제거했습니다. 구현이 사라진 지 오래인 --no-symlinks도 help에서 걷어냈습니다.
왜
문서는 기능 브랜치 + PR + self-merge 금지를 지시했지만 실제 릴리스는 main에서 이뤄집니다. 문서와 운용이 어긋나면 그 문서를 따르는 쪽이 매번 우회로를 만듭니다.
그래서
범프·CHANGELOG 이동·what-changes 스냅샷을 한 커밋에 넣어야 하는 이유(세 검사가 모두 태그가 가리키는 한 커밋에서 실행됨)가 절차에 명시됐습니다.

이번 릴리스가 택한 방향

가드를 추가하는 일과 가드가 작동함을 아는 일은 다릅니다.

테스트가 가드를 밟을 수 없어야 한다

"release --help는 릴리스하면 안 된다"를 CLI 실행으로 검증하면, 가드가 깨진 바로 그 실행에서 저장소가 범프됩니다. 그래서 테스트는 순수 함수 resolveInvocation의 반환값을 검사합니다 — 위험 없이 같은 성질을 증명합니다.

통과가 아니라 실패로 증명한다

가드 다섯 개(help 스캔, 미지 플래그, 값 누락, 선언-사용 일치, -- 종료자)를 하나씩 되돌려 대응 테스트가 전부 실패하는 것을 확인하고 복원했습니다. 0.14.0이 세운 기준을 그대로 적용한 것입니다.
