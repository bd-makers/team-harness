0.21.0은 기능을 더하지 않습니다. 0.17.0에서 “1개 마이너 버전만 유지”라고 약속하고 남긴 deprecated 포워딩 4개를 실제로 지우는 릴리스입니다. 그 약속은 0.18.0 · 0.19.0 · 0.20.0 세 릴리스를 지나도록 지켜지지 않았습니다. 미룬 것 자체는 옳은 판단이었지만 — 지울 조건이 충족되지 않았습니다 — 미룬 사실이 문서에 반영되지 않은 것은 옳지 않았습니다. 이번 릴리스의 절반은 삭제이고, 나머지 절반은 그 삭제를 세 번이나 예고해 놓고 틀린 채 방치된 문장들을 고치는 일입니다.

옛 리뷰 이름은 이제 아무것도 하지 않습니다

0.17.0이 리뷰 커맨드를 엔진 중립으로 재편하면서(/harness-review·/harness-adversarial-review) 남긴 codex 전용 옛 이름 포워딩 4개 — 커맨드 2개와 동명의 스킬 2개 — 를 삭제했습니다.

이것은 breaking change입니다. /harness-codex-review·/harness-codex-adversarial-review를 문서·브리프·스크립트에 박아 뒀다면 지금 바꿔야 합니다. 대체 경로는 /harness-review codex·/harness-adversarial-review codex이고, 엔진 인자를 생략하면 probe 폴백 체인(codex → gemini → claude)이 첫 가용 엔진을 씁니다. 실패 방식이 조용합니다 — 없는 커맨드는 오류를 내는 대신 아무 반응도 하지 않습니다.
Removed

커맨드 2개 · 스킬 2개 · 매니페스트 항목 2개

변경
commands/harness-codex-review.md·commands/harness-codex-adversarial-review.md와 동명의 스킬 디렉터리 2개를 지우고, .claude-plugin/plugin.json의 commands 항목 2개를 함께 제거했습니다. 플러그인이 제공하는 슬래시 커맨드가 26개에서 24개로 줄어듭니다.
왜
엔진이 커맨드 이름에 박혀 있으면 엔진이 늘 때마다 커맨드가 프레이밍 수만큼 곱으로 늘어납니다. 0.17.0이 이 축을 인자로 분리했고, 포워딩은 그 전환을 위한 한시적 다리였습니다. 다리를 영구히 두면 두 이름 체계가 공존하며 — 어느 쪽이 정본인지 매번 판단해야 합니다.
그래서
skills/harness-codex-sim은 제거 대상이 아닙니다. 이름이 비슷해 grep 오탐을 부르는 별개 스킬이며 그대로 남습니다. .codex-plugin/plugin.json은 "skills": "./skills/" 디렉터리 참조라, marketplace.json은 커맨드를 열거하지 않아 둘 다 갱신이 필요 없었습니다.

게이트는 코드가 아니라 사람 확인에 걸려 있었습니다

제거를 세 번 미룬 이유는 기술적 미완성이 아니었습니다. 지울 준비는 0.18.0부터 끝나 있었고, 막고 있던 것은 팀원 머신 전역 ~/.claude/CLAUDE.md의 새 이름 전환 확인이라는 하나의 조건이었습니다.

전역 CLAUDE.md는 머신마다 별개 파일이라 저장소가 동기화할 수 없습니다. 그 파일이 옛 이름을 부르고 있는 상태에서 포워딩을 지우면, 그 안내는 오류를 내지 않고 무반응이 됩니다. 실패가 보이지 않는 실패라 릴리스 노트로 경고할 수도 없습니다 — 읽는 사람은 자기 파일이 낡았다는 것을 모르기 때문입니다.
Verified

두 머신 확인 완료 — 게이트 해제

변경
회사 머신은 앞선 task에서, 홈 머신은 2026-08-28 그 머신 세션에서 실측 확인했습니다. 두 파일 모두 새 이름을 호출 경로로 안내하고, 옛 이름은 “새 참조를 옛 이름으로 만들지 말 것”이라는 금지 문구로만 등장합니다.
왜
금지 문구는 호출 경로가 아닙니다. 포워딩을 지워도 실패할 안내가 없습니다 — 이 구분이 게이트의 전부였습니다. “옛 이름이 언급되는가”가 아니라 “옛 이름을 부르라고 하는가”가 판정 기준입니다.
그래서
확인 근거는 task spec의 선행 조건 체크리스트에 문장으로 남겼습니다. 체크박스만 켜면 무엇을 보고 켰는지가 사라지고, 다음 사람이 같은 확인을 처음부터 다시 해야 합니다.

포워딩만 지우면 문서가 거짓말을 시작합니다

삭제 자체는 파일 4개와 매니페스트 항목 2개로 끝납니다. 그런데 그 이름을 부르거나 예고하던 곳이 저장소 곳곳에 남아 있었습니다.

Changed

“0.19.0에서 제거됩니다”라고 적힌 문장 6곳

변경
docs/harness-fleet-guide.html·docs/harness-task-guide.html·docs/harness-workflow-simulation.html의 6곳이 제거 시점을 0.19.0으로 예고하고 있었습니다. 전부 제거 완료 시제로 고쳤습니다. README.md 3곳의 커맨드 개수(26 → 24), commands/harness-diagram.md의 유추 대상 참조도 함께 정정했습니다.
왜
이 문장들은 세 릴리스 내내 틀린 상태였습니다. 0.19.0에 제거되지 않았는데도 아무도 갱신하지 않았습니다. 예고를 남긴 채 실물만 지우면 이번에는 이미 지워진 것을 미래형으로 예고하는 문서가 됩니다 — 틀린 방향만 바뀔 뿐 여전히 틀립니다.
그래서
정정문에 새 릴리스 번호를 박지 않았습니다. 완료 시제로 쓰고 번호는 CHANGELOG 릴리스 절이 말하게 뒀습니다. 번호를 박은 것이 애초에 이 문장들이 틀린 원인이었습니다.
Changed

발행된 버전 스냅샷은 손대지 않습니다

변경
docs/harness-overview-*.html·what-changes-*.html·harness-workflow-simulation-0.18.1.html은 그대로 뒀습니다. 현재 문서인 docs/harness-overview.html만 npm run docs:generate로 재생성했습니다.
왜
버전 스냅샷은 그 시점의 사실 기록입니다. what-changes-latest-version.html의 “이번에도 이월합니다” callout은 0.20.0에 대해 참이며, 소급 수정하면 0.20.0이 무엇을 알고 무엇을 몰랐는지가 사라집니다. tests/what-changes-latest-version.test.mjs가 이 동일성을 강제하기도 합니다.
그래서
재생성 순서에 함정이 하나 있습니다 — overview 생성이 git ls-files 기반이라 삭제도 git add가 선행돼야 반영됩니다. 지우고 바로 docs:generate를 돌리면 사라진 커맨드가 표에 남습니다.

이 릴리스가 남기는 것

문서에 미래 릴리스 번호를 박지 않는다

“0.19.0에서 제거됩니다”는 작성 시점에 참이었고, 그 다음 날부터 거짓이 될 준비가 된 문장이었습니다. 이월은 흔한 일이고 이월할 때마다 이런 문장을 전수 조사해 고칠 사람은 없습니다. 번호는 한 곳에만 둡니다 — CHANGELOG의 릴리스 절. 나머지 문서는 “제거됐다”·“deprecated다”처럼 상태만 말하고, 시점은 그쪽을 가리킵니다.

이월은 기록되어야 이월이다

0.19.0은 “다시 이월한다면 그 사실을 그 릴리스의 이 절에 적는다”는 규칙을 스스로 정했고, 0.20.0이 그것을 지키지 않았습니다. 제거를 안 한 것보다 안 했다고 적지 않은 것이 문제입니다 — 기록이 없으면 다음 사람은 이월을 발견하지 못하고, 발견하지 못한 이월은 무기한 연장됩니다. 0.20.0 절은 발행됐으므로 소급 수정하지 않고 [Unreleased]에 정정 기록으로 남겼습니다.

삭제의 범위는 파일이 아니라 이름이다

task plan에는 원래 6단계가 적혀 있었습니다 — 파일 4개, 매니페스트, 테스트, 재생성, CHANGELOG. 실행해 보니 그 이름을 부르는 곳이 5군데 더 있었습니다. 무언가를 지울 계획을 세울 때 적어야 하는 것은 지울 대상이 아니라 그 대상을 이름으로 부르는 모든 곳입니다.
