PR 없이 커밋하는 저장소도
위키 컴파일을 돌립니다

0.47.0의 위키 컴파일(/harness-wiki)은 출처로 PR 번호를 요구했습니다. 들여온 커밋 메시지에서 번호를 못 찾으면 wiki sources가 no-pr로 막고 --pr <N>을 달라고 했습니다. 그런데 PR 없이 기본 브랜치에 직접 커밋하는 저장소에는 넣을 번호가 존재하지 않습니다. 그런 저장소는 컴파일을 영영 못 했고, 컴파일된 task만 지우는 C2b 삭제 게이트도 영원히 닫혀 있었습니다(소비자 저장소 실측). 0.49.0은 PR 번호가 없으면 막지 않고 커밋 sha를 출처로 마커를 만듭니다. PR 번호가 있는 경로는 바이트 단위로 그대로입니다.

왜 minor인가 — wiki sources의 출력 계약이 넓어졌다

명령·플래그는 늘지 않았습니다. 다만 wiki sources가 막던 입력(no-pr)을 이제 통과시키고, 그때 pr= 키가 없는 새 마커 형식을 냅니다. 마커를 읽는 쪽이 pr=를 늘 기대했다면 달라집니다. 제거된 명령·플래그는 없습니다.

커밋 출처 — PR 번호가 없을 때의 마커

출처 우선순위는 --pr <N> > 커밋 메시지에서 읽은 번호 > 커밋 출처입니다. 앞의 둘은 0.48.0과 같습니다.

Changed · #138

PR 번호가 없으면 pr= 없는 마커

원인
CLI는 "PR이 없는 저장소"와 "PR이 있었지만 rebase·fast-forward 병합으로 번호가 빠진 경우"를 가르지 못합니다. 앞의 경우에는 --pr에 넣을 번호가 아예 없어 no-pr 막힘을 풀 방법이 없었습니다.
지금
번호를 못 찾으면 <!-- harness:wiki task=<user>/<task> commit=<sha7> author=<user> at=<날짜> -->를 냅니다. 번호를 지어내지 않고, 가짜 값(pr=none)도 두지 않습니다 — "없음"은 키가 없는 것으로 표현합니다.
소리
막힘은 아니지만 조용하지도 않습니다. 텍스트 출력에 note: 한 줄, JSON summary에 "PR 없음 — 커밋 출처", /harness-wiki 보고에 그 사실이 남습니다. PR로 들여왔는데 번호가 빠진 경우라면 --pr <N>으로 다시 실행합니다.
멱등
이미 컴파일됐는지는 계속 task=로만 판정합니다. 커밋 출처로 컴파일한 뒤 PR 번호가 생겨 --pr로 재컴파일해도 같은 단락을 교체합니다. 그래서 C2b 삭제 게이트(compiled)가 PR 없는 저장소에서도 열릴 수 있습니다.
Changed · #138

커밋 출처의 commit=은 종결 커밋

원인
PR 출처의 commit=은 task 폴더를 처음 들여온 커밋(머지·squash)이라 변경 전체를 가리킵니다. 직접 커밋 저장소에서 같은 정의를 쓰면 spec 초안 커밋이 나와 변경을 대표하지 못합니다.
지금
PR 번호가 없을 때만 commit=은 HEAD first-parent 이력에서 task 폴더를 마지막으로 건드린 커밋(done이 만드는 종결 커밋)입니다. PR 출처와 PR 번호 추론에 쓰는 커밋은 0.48.0과 같습니다.
시점
컴파일은 머지 후 종결에서 done 다음, 폴더 삭제(C2b) 전에 돕니다. 그 자리에서 이 값은 종결 커밋입니다. 종결 커밋을 읽지 못하면 들여온 커밋으로 조용히 되돌리지 않고 no-commit으로 막습니다.
