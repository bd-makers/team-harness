재현된 우회 — 모두 exit 0이었습니다

임시 프로젝트에서 실패하는 npm test를 두고 훅에 JSON payload만 넘겼습니다. 실제 git 명령은 실행하지 않았습니다.

훅명령0.39.00.39.1왜 샜나
pre-commit-check.shgit -C . commit -m xexit 0exit 2*"git commit"* 부분 문자열 검사 — 옵션이 끼면 문자열이 안 붙는다
pre-commit-check.shgit --no-pager commitexit 0exit 2같은 이유
block-dangerous-git.shgit push --force;echoexit 0exit 2경계 END가 공백·끝·"만 인정 — ;는 경계가 아니었다
block-dangerous-git.shgit push -f; echoexit 0exit 2같은 이유
init마지막 "Apply?"에 n.harness/config.json 남음아무것도 안 남음ensureUsername이 이름 확정 즉시 저장

이 훅들은 nudge이지 보안 경계가 아닙니다. Claude Code 세션의 Bash 도구가 보내는 명령 문자열을 보는 것이라 세션 밖에서는 아예 걸리지 않습니다. 그래도 세션 안에서 옵션 하나로 새는 것은 "게이트가 있다"는 믿음을 거짓으로 만듭니다 — 그래서 patch로 바로 발행합니다.

경계의 정의 — 열거하지 않는다

첫 수정은 ;·&·|·)를 경계 목록에 더했습니다. codex 리뷰가 바로 git commit>/dev/null·bash -c 'git commit'을 들고 왔습니다.

Changed

차단 방향: 단어 문자가 아니면 전부 경계

정의
END='([^[:alnum:]_-]|$)'. 공백·"·;·&&·|·)·>·'·백틱 — 무엇이 오든 토큰은 끝난 것으로 본다. 미열거 구분자는 fail-closed.
왜 -는 단어인가
--force-if-includes가 -f 패턴에 걸리지 않는 것은 -force 뒤 -가 경계가 아니기 때문이고, git commit-tree는 ref를 옮기지 않는 저수준 명령이라 commit이 아니다.
codex P1

허용 방향은 좁게 — restore -S'W'

무엇
넓힌 경계를 restore --staged 허용 예외에도 쓰면 git restore -S'W' f가 -S 뒤 '를 경계로 보아 staged로 통과한다. 셸은 인용을 벗겨 -SW(워킹트리 덮어쓰기)를 git에 넘긴다.
조치
허용 판정만 SAFE_END='([[:space:]]|$)'. 차단 판정(-W·DANGEROUS_PATTERNS)은 넓은 경계 유지. 같은 정규식 조각이 차단에서는 fail-closed를, 허용에서는 fail-open을 넓힌다 — 두 방향을 따로 검토해야 한다.
