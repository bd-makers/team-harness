## 집계 방법

아래 코드를 `/tmp/review-evidence.mjs`로 저장하고, 저장소 루트에서 `node /tmp/review-evidence.mjs`를 실행한다. checkout은 수정하지 않는다. Node 22 이상이 필요하다(`globSync`). done 가드가 export하는 `evidenceWindowStart`와 리뷰 파서를 그대로 쓴다(`src/commands/task.mjs:889-909,977-996`). `review`는 artifact 마커와 meta 기록을 모두 인정하고, `verify`만 meta 키가 있으면 meta만 인정한다.

pre/post=[전체, 무증거, 날짜 산문], required=[선언, 무증거], window=[증거, 무증거]다. 전체 기록과 창(reopenedAt/firstActivatedAt)을 구별한다. 산문은 날짜 포함 bullet·제목, forced는 최근 우회 흔적 보유 task 수다.

```javascript
import { readFileSync, existsSync, globSync } from 'node:fs';

const { parseReviewMarkers, parseMetaReviews, evidenceWindowStart } =
  await import(process.cwd() + '/src/commands/task.mjs');
// done 가드의 선언 정규식(src/commands/task.mjs:581). HTML 주석 안의 선언은 맞지 않는다.
const DECL = /^## Done evidence[ \t]*\r?\n(?:[ \t]*\r?\n)*```json[ \t]*\r?\n([\s\S]*?)^```[ \t]*$/m;
const read = (p) => (existsSync(p) ? readFileSync(p, 'utf8') : '');

const r = {
  done: 0, evidence: 0, none: 0, noneDatedProse: 0,
  pre: [0, 0, 0], post: [0, 0, 0],          // [전체, 무증거, 무증거 중 날짜 산문]
  requiredPre: [0, 0], requiredPost: [0, 0], // [선언, 무증거]
  window: [0, 0],                            // [창 안 증거, 창 안 무증거]
  windowPostNone: 0, windowRequiredNone: 0, different: [],
  forced: 0, commands: globSync('commands/*.md').length,
};

for (const m of globSync('docs/*/*/*-meta.json')) {
  const meta = JSON.parse(read(m));
  if (meta.status !== 'done') continue;
  r.done++;

  const base = m.replace(/-meta\.json$/, '');
  const art = read(base + '-artifact.md');
  const reviews = Array.isArray(meta.reviews) ? meta.reviews : [];
  const all = [...parseReviewMarkers(art), ...parseMetaReviews(reviews)];
  const has = all.length > 0;
  const windowStart = evidenceWindowStart(meta).at;
  const inWindow = all.some((x) => windowStart === null || x.at >= windowStart);

  const pre = (meta.created || '') < '2026-09-10';
  const cohort = pre ? r.pre : r.post;
  cohort[0]++;
  if (has) {
    r.evidence++;
  } else {
    r.none++;
    cohort[1]++;
    const section = (art.split(/^## Reviews/m)[1] || '').split(/^## /m)[0];
    if (/^\s*([-*]|#{3,})\s.*20\d\d-\d\d-\d\d/m.test(section)) {
      r.noneDatedProse++;
      cohort[2]++;
    }
  }

  r.window[inWindow ? 0 : 1]++;
  if (!pre && !inWindow) r.windowPostNone++;
  if (has !== inWindow) r.different.push(base);

  const decl = read(base + '-spec.md').match(DECL);
  let evidence;
  try { evidence = decl && JSON.parse(decl[1]); } catch {}
  if (evidence?.review === 'required') {
    const req = pre ? r.requiredPre : r.requiredPost;
    req[0]++;
    if (!has) req[1]++;
    if (!inWindow) r.windowRequiredNone++;
  }
  if (meta.forcedAt) r.forced++;
}

console.log(JSON.stringify(r));
```

#### 1. 하네스 5대 구성 축 감사 체크리스트

하네스는 모델 가중치를 손대지 않고 주변(around the model) 환경의 결정론적 통제망을 구축하는 5가지 축으로 구성됩니다 [1, 2].

| 구성 축 | 정의 | 잘 설계됐다는 판단 신호 (PASS) | 흔한 실패 및 안티패턴 (FAIL) |
| :--- | :--- | :--- | :--- |
| **권한<br>(Permissions)** | 모델의 접근 범위 및 위험 연산(DELETE 등)을 통제하고 최소 권한(RBAC)을 부여하는 축 [2, 3]. | • 검증·리뷰 에이전트에서 `Edit`/`Write` 권한이 완전 제거되어 Read/Grep 전용으로 동작함 [3-5].<br>• 수정 권한이 필요한 단일 에이전트에게만 제한적 `Edit` 부여 [4, 6]. | • 한 에이전트가 배포나 수정 권한까지 모두 소유하여 최소 권한 원칙이 파괴됨 [3, 7].<br>• 권한 통제가 프롬프트지시("건드리지 마")에만 의존함 [2, 8, 9]. |
| **도구<br>(Tools)** | 부작용 범위를 고려하여 허용 도구 목록(`tools`/`allowed-tools`)을 선별·제한하는 축 [2, 3]. | • 에이전트/태스크별 활성 도구가 15개 이하로 큐레이션됨 [3, 10, 11].<br>• 미사용 MCP 서버가 비활성화되어 있음 [10, 12]. | • 15개 초과 도구가 노출되어 모델이 판단력을 잃는 **'토큰 마비(Token Paralysis)'** 발생 [3, 10].<br>• 사용률 0인 도구나 수십 개 도구를 가진 MCP가 상시 로드되어 컨텍스트를 잠식함 [10-12]. |
| **검증<br>(Verification)** | 산출물의 오류나 거짓 보고를 걸러내고 PASS/FIX/REDO를 판정하는 루프 축 [2, 13, 14]. | • 객관적 기준(테스트/린터 통과, 스키마 일치)으로 판정함 [13-15].<br>• 재시도 상한(2~3회) 도달 시 명시적으로 사람에게 에스컬레이션함 [13, 15, 16]. | • 모호한 자연어 기준으로 판정하여 결과 편차가 큼 [13, 17].<br>• 종료 조건 없는 무한 루프 또는 실패를 숨기고 강제 통과시키는 구조 [13, 16, 18]. |
| **상태<br>(State)** | 세션이 끝나도 작업 내역과 중간 산출물이 영속화되도록 저장소 파일에 기록하는 축 [1, 2, 19]. | • 에이전트 간 소통 및 중간 결과물이 프롬프트 텍스트가 아닌 `_workspace/` 내 파일로 관리됨 [19-21].<br>• 세션 교체/중단 후에도 기존 파일을 읽고 부분 재실행 가능함 [21, 22]. | • 중간 결과가 대화 컨텍스트/메모리에만 존재하여 세션 종료 시 복구 불가능 [2, 22, 23]. |
| **관측<br>(Observability)** | 실행 과정, 토큰 비용, 이상 징후(도구 호출 피로 곡선, 컨텍스트 임계치)를 포착하는 축 [1, 2, 24]. | • 각 에이전트 로그가 중앙 모집중화됨 [24].<br>• `/cost` 및 지표 계측으로 루프 조기 감지 및 컨텍스트 임계치(180k 등) 시 세션 분할 [12, 24, 25]. | • 단순 실행 로그만 남기고 지표 모니터링이 없음 (73%의 모니터링 부재 실패) [24, 26].<br>• 동일 파일 5회 이상 수정 등 이상 피로 곡선을 포착하지 못함 [12, 24]. |

#### 2. 생성-검증(Generator-Verifier) 분리 원칙 구체 요건

* **검증자의 독립성**: 작성자(`author`/`generator`)와 검토자(`reviewer`/`verifier`)는 반드시 **독립된 에이전트 파일**로 분리되어야 합니다 [20, 27]. 혼자 쓴 PR을 혼자 머지하듯 단일 에이전트가 자기 출력물을 검토하면 처음에 놓친 가정을 검증에서도 다시 놓치게 됩니다 [18, 28, 29].
* **권한의 차등 배분**: 검증자 에이전트에게는 **`Edit` 및 `Write` 권한을 절대 부여해서는 안 됩니다** [3-5]. 검증자가 직접 코드를 고치면 거짓 양성(False Positive)이 그대로 커밋되거나 생성 에이전트의 책임 경계가 무너집니다 [4, 30].
* **컨텍스트 분리 및 매개체**: 두 에이전트는 대화 맥락을 직접 공유하기보다 `_workspace/` 폴더 내의 독립된 파일(초안 파일, 검토 리포트 파일)이나 명확한 프로토콜 메시지를 매개로 소통해야 합니다 [19-21, 31].
* **루프 안전장치 (재시도 상한 및 에스컬레이션)**: 재호출 상한(기본 2~3회)을 명시해야 합니다 [13, 15, 16, 20]. 상한 초과 시 실패를 감추지 않고 경고 플래그와 함께 사람에게 넘기는(에스컬레이션) 규칙이 필수적입니다 [16, 17].
* **피드백의 구체성**: 검증 피드백은 "코드 품질 부족" 같은 모호한 표현이 아니라 "라인 42 null 체크 누락"처럼 구체적인 위치와 원인을 지정해야 교착(Deadlock)을 막을 수 있습니다 [12, 17].

#### 3. 에이전트·스킬·오케스트레이터 분리 원칙과 책임 경계

| 요소 | 질문 | 핵심 책임 | 저장/운영 위치 |
| :--- | :--- | :--- | :--- |
| **에이전트 (Agent)** | **누가** | 전문가 역할 설정, 판단 기준, 작업 원칙, 입출력 프로토콜 (역할 계약서) [27, 32]. | `.claude/agents/{name}.md` [27, 32] |
| **스킬 (Skill)** | **어떻게** | 워크플로, 자연어 트리거(`description`), 절차적 지식 (절차 자산) [27, 32]. | `.claude/skills/{name}/SKILL.md` [27, 32] |
| **오케스트레이터 (Orchestrator)** | **언제·누구와** | 팀 구성, 작업 의존성(`depends_on`), Phase 전환, 실행 순서 조율 [32, 33]. | 세션 런타임 + `CLAUDE.md` 하네스 포인터 [32, 33] |

##### 흔한 책임 혼재 안티패턴
1. **에이전트 과집중**: 한 에이전트가 생성, 검증, 조율을 모두 맡아 수백 줄짜리 신(God) 파일이 됨 [7, 29].
2. **에이전트에 절차 지식 작성**: 공통 절차나 지식을 에이전트 파일에 직접 다 작성하여 다른 팀원에서 재사용 불가능 [7, 29].
3. **스킬의 리더화**: 스킬 본문이 팀 구성, 예외 복구, 단계 전환 등 20단계 넘는 지휘 로직을 직접 포함함 (메타스킬 제외) [7].
4. **리더 병목 (우체국 안티패턴)**: 오케스트레이터/리더가 직접 일을 처리하거나 모든 팀원의 대화 메시지를 중앙에서 일일이 중개함 [4, 7, 34].

#### 4. 결정론적 강제 vs 프롬프트 규범의 역할 분담

책이 제시하는 핵심 원칙은 **"안쪽은 확률론, 가장자리는 결정론"**입니다 [35, 36].

* **프롬프트 규범 (자연어 지침)**:
  * "DB를 건드리지 말 것", "세미콜론을 붙일 것" 등 자연어 지시는 **'설득'에 의존**합니다 [8, 11].
  * 자연어로만 작성된 규칙은 준수율이 약 **37% 수준**에 불과하며, 호출 횟수가 늘어나면 51번째 호출에서 반드시 위반이 발생합니다 [8, 25].
* **결정론적 강제 (훅·스크립트·게이트)**:
  * 린터, 타입 체커, 테스트, Hooks, RBAC 도구 제한(`tools`), 결정론적 재현 스크립트(`reproduction.sh`)는 기계가 확인합니다 [6, 9, 35, 36].
  * 훅으로 이관된 규칙은 **토큰 소비가 0**이 되며 규칙 **준수율은 100%로 고정**됩니다 [37].
* **분담 평가 기준**: "이 규칙을 기계가 검증할 수 있는가?"를 먼저 물어야 합니다 [25]. 기계 검증이 가능한 영역(린트, 테스트, 권한)을 자연어 문장에 의존하고 있다면 **'계층 혼재' 안티패턴**에 해당합니다 [25].

#### 5. 컨텍스트 관리 원칙 및 수치 기준

* **`CLAUDE.md` 크기 기준**: **권장 150줄 이하** (실용적 최대 200줄 이하) [11, 23, 38, 39]. 150줄을 넘어가면 최신 LLM도 일관성을 잃고 하네스 포인터 섹션을 누락하기 시작합니다 [23].
* **Progressive Disclosure (3층 지연 로딩 수치)** [40]:
  * **Layer 1 (상시 노출)**: 스킬의 `description` 및 `when_to_use`. **하드 상한 1,536자** (~100단어, 1% 토큰 예산 기준 약 250자) [40, 41].
  * **Layer 2 (호출 시 로딩)**: `SKILL.md` 본문 (공통 절차). 본문이 **500줄 근접 시 references로 분리** [40].
  * **Layer 3 (조건부 로딩)**: `references/` 내 서브 마크다운 파일. 에이전트가 특정 조건을 충족할 때만 선택적으로 읽음 [40, 42].
* **서브에이전트 및 팀 규모 수치** [43]:
  * 소규모 작업(5~10개): **2~3명** / 중규모(10~20개): **3~5명** / 대규모(20개+): **5~7명** [43].
  * 팀원이 7명을 초과하면 Phase 단위로 팀을 분할 및 교체(`TeamDelete` 후 `TeamCreate`)해야 합니다 [30, 43].
  * 메시지 폭주 방지를 위해 클로드 코드 내부의 **팀원 메시지 큐는 최대 50개**로 제한됩니다 (292개 에이전트 폭주 사고 발생에 따른 표준) [43, 44].
* **도구 및 MCP 수치 기준**:
  * 세션 시작 시 **활성 도구 수 < 15개** [3, 10, 11].
  * **활성 MCP 서버 수 < 3개** [11, 39]. MCP 서버는 연결만 해도 모든 도구 스키마가 컨텍스트를 즉시 잠식하므로 서브셋 노출 옵션을 사용해야 합니다 [10, 12].
* **HTML 주석 금지**: `CLAUDE.md`나 스킬 파일에 `<!-- -->` 형태로 비활성화한 규칙은 컨텍스트에서 **자동 제거**되므로 주석으로 규칙을 숨기는 행위는 엄격히 금지됩니다 [23, 38, 39].

#### 6. 하네스 점진적 개선·진화 루프

* **기본 원칙**: "하네스는 한 번 만들고 끝나는 산출물이 아니며, 한 번에 하나씩 바꾸고 즉시 기록하는 진화하는 생명체"입니다 [45].
* **`CLAUDE.md` 하네스 포인터와 변경 이력 테이블** [46, 47]:
  * `CLAUDE.md`에는 백과사전식 상세 규칙을 담지 말고 하네스 포인터를 등록해야 세션마다 로딩됩니다 [45, 46].
  * 변경 이력표는 **`| 날짜 | 변경 내용 | 대상 | 사유 |`** 4개 열을 엄격히 유지해야 합니다 [46-48]. (순서가 바뀌면 감사 도구가 동작하지 않음) [48].
  * **'사유(Reason)'의 중요성**: AI 모델 능력이 향상되었을 때 불필요해진 하네스 구성요소를 삭제할 정당한 근거가 되며 퇴행(regression)을 방지합니다 [47, 48].
* **진화를 촉발하는 3대 신호** [22, 48]:
  1. **반복 피드백**: 동일한 사용자 교정 지적이 반복될 때 (스킬/에이전트 층위 수정) [47, 48].
  2. **반복 실패**: 에이전트 오류 패턴이 누적될 때 (검증 단계 추가 또는 에이전트 분할) [48].
  3. **우회 관찰 (가장 결정적 징후)**: 사용자가 하네스를 호출하지 않고 직접 편집기를 열 때. 이는 하네스가 제 기능을 못 한다는 증거이므로 `description`이나 워크플로를 수정해야 합니다 [22, 48].

#### 2. 주요 운영 요소별 구체 가이드라인

##### 1) 세션 간 인수인계(Handoff) 및 장기 작업의 상태 영속화
* **`_workspace/` 공유 파일 시스템**: 세션이 끝나거나 이전 팀이 해체(`TeamDelete`)되어도 `_workspace/` 폴더 안의 중간 산출물(설계서, JSON 요구사항, 패치 파일)은 지워지지 않고 보존되어 다음 세션/Phase로 연결됩니다 [33, 34].
* **`CLAUDE.md` 하네스 포인터**: 새 세션이 시작될 때마다 `CLAUDE.md`에 작성된 하네스 포인터가 로드되어, 에이전트가 "이 프로젝트에 어떤 오케스트레이터와 파일 구조가 존재하는지" 즉시 인지하도록 돕습니다 [33, 35, 36].
* **JSON 기반 상태 머신 (Status Machine)**: 마크다운 대신 `00_requirements.json`이나 `batches.json` 같은 JSON 파일 내에 `passes: false`나 `status: "pending" | "in-progress" | "done" | "manual-queue"` 상태를 저장하여 세션 경계를 넘어도 중복 작업을 방지합니다 [6, 7, 37].
* **세션 시작 시 상태 복원 프로토콜**: 새 세션의 첫 작업으로 baseline 전체 테스트를 실행하여 회귀 여부를 점검하며, 오케스트레이터는 `_workspace/` 감지 로직을 통해 `initial`, `partial_rerun`, `new_run`으로 실행 모드를 자동 분기합니다 [37, 38].

##### 2) 완료(Done) 판정의 증거 요건 — 거짓 보고 방지
* **기계적·결정론적 exit code 환원**: 확률적 LLM의 "완료했습니다"라는 주장이나 텍스트 응답을 절대 신뢰하지 않으며, 반드시 Bash 스크립트 실행의 `exit 0`이라는 결정론적 통과 결과로만 완료를 판정합니다 [16, 22].
* **결정론적 재현 스크립트 (`reproduction.sh`)**: 버그 수정 작업의 경우, 수정 전에는 `exit 1`이 발생하고 수정 후에는 `exit 0`으로 바뀌는 스크립트를 작성하여 3회 연속 통과해야만 "수정 완료"로 간주합니다 [16, 39-41].
* **체크리스트 강제 통과 및 `git diff` 검사**: 수정 에이전트가 완료 선언을 하기 전, 회귀 테스트 통과는 물론 "버그를 우회하기 위해 테스트 코드를 수정/삭제하지 않았는지" `git diff`로 기계 검사합니다 [20, 23].
* **PreCompletion 게이트**: 오케스트레이터 스킬의 마지막 단계에 `npm test && npm run lint` 등 자동화 테스트 스위트의 execution exit status가 0인 경우에만 `passes: true` 플래그를 갱신합니다 [22].

##### 3) 리뷰 단계에서 다른 모델 / 다른 벤더 에이전트 활용에 대한 책의 견해
* **Anthropic 모델 믹스(Model Mix)**: 책에서는 Anthropic Claude 계열 내에서 작업 성격에 맞게 모델을 배분하는 **'모델 믹스'**를 권장합니다 [13, 42]. 정적 분석이나 키워드 추출은 **Haiku**, 일반적 코드 구현 및 보안 감사는 **Sonnet**, 다축 추론/교차 검증/독립 리뷰어는 **Opus**를 할당하여 비용과 속도를 최적화합니다 [13, 19, 42].
* **다른 벤더(OpenAI GPT, Google Gemini 등) 혼용에 대한 견해**: 책 1장에서 Grok, Gemini, Grok Code Fast 등의 모델에서도 동일한 하네스 효과가 나타났다는 벤치마크 수치를 인용하지만 [43], **리뷰어로 외부 벤더 모델(Gemini/GPT 등)을 섞어 쓰는 구체적인 하네스 구현 방식은 "책에 없음"**으로 정리됩니다. (Claude Code CLI의 프론트매터 `model:` 필드는 sonnet, opus, haiku, inherit 및 Claude 전용 모델 ID만을 지원하도록 설계되어 있습니다 [44]).

##### 4) 병렬 에이전트의 동일 파일/브랜치 수정 방지 (Worktree 격리 등)
* **Cross-Reference Drift 및 파일 충돌 금지**: 팀 모드에서 여러 에이전트가 같은 파일에 동시에 쓰기 작업을 수행하는 것은 머지 충돌 및 덮어쓰기 사고를 유발하므로 안티패턴으로 다룹니다 [22, 45, 46].
* **`isolation: "worktree"` 활용**: 클로드 코드 프론트매터의 `isolation: "worktree"` 필드를 선언하여, 병렬 실행되는 에이전트들이 독립된 git worktree 환경에서 안전하게 작업을 수행하도록 물리적으로 격리합니다 [44, 47].
* **수정 권한 제한 및 래퍼 파일 규약**: 코드 수정 권한(`Edit`)은 단 한 명의 구현/리팩터링 에이전트에게만 부여하고, 수정 대상 또한 `_workspace/patches/*.diff` 파일 형태로 제한하여 원본 파일 직접 수정 충돌을 원천 차단합니다 [13, 18].
* **`TaskCreate`와 `taskListId` 공유**: 모든 워커 에이전트가 동일한 `taskListId`를 공유하고 태스크별로 담당자(`assignee`)를 명시하여 소유권 충돌을 방지합니다 [45, 46].

#### 2. 세부 설계 이슈 심층 검토 (책의 원칙 대조)

##### 세부 1. 오케스트레이터 없이 "설정·상태 하네스"로 범위를 좁힌 결정이 타당한가? 잃는 것은 무엇인가?

* **잃는 것**:
  1. **런타임 동적 협상 및 수평 통신(Peer-to-Peer SendMessage)**: 리더/오케스트레이터가 없으므로 에이전트 간 직접 대화나 복잡한 팬아웃/팬인, 동적 팀 구성(`TeamCreate`/`TeamDelete`)을 수행할 수 없습니다 [30-32].

##### 세부 2. 리뷰어를 다른 벤더 모델(Codex)로 두는 것에 대한 평가
* **책의 원칙**: 책에서는 생성-검증 분리의 핵심을 "같은 모델, 같은 컨텍스트가 자기 출력물을 교정할 때 발생하는 확증 편향(혼자 쓴 PR을 혼자 머지)"을 막는 것으로 설명합니다 [10, 35, 36].
* **책에 없음 (추론)**: 책은 Claude 계열 내 Model Mix(Sonnet/Opus/Haiku) [2, 16] 및 `codex exec`처럼 외부 CLI 도구를 통제하는 방식을 다루지만, 외부 벤더 모델(Codex)을 리뷰어로 붙이는 아키텍처는 **책에 없음(추론)**입니다.
* **장점**: 기반 모델 아키텍처 자체가 달라 상호 보완적인 맹점(Blind spot) 탐지가 가능하며, `codex exec --sandbox read-only`를 통해 검증자 권한을 강제로 차단하는 뛰어난 가드레일을 달성합니다 [1, 2].
* **단점**: 프로토콜/출력 스키마 해석 방식의 차이로 구체적 피드백(라인 번호, 수정 가이드) 전달 시 파싱 실패가 발생하거나, 리뷰어 모델의 특이적 편향에 대한 튜닝이 어려울 수 있습니다 [15, 17, 36].

##### 세부 3. eager 지침 231줄 (AGENTS 152 + CLAUDE 79) 평가
* **책 기준 (미흡/FAIL)**: 책 부록 C.5 및 10장에서 `CLAUDE.md` (혹은 상시 로드 eager 지침)가 **150~200줄을 넘어가면 LLM의 인지 과부하로 하네스 포인터가 가장 먼저 누락되고, KV 캐시 적중률이 깨져 토큰 비용이 급증한다**고 경고합니다 [24-27]. 231줄은 명백한 경고 대상입니다.
* **해결책**: 상시 노출(Layer 1) 지침을 150줄 이하로 압축하고, 경로별 규칙은 `.claude/rules/`로, 절차 지식은 스킬(`SKILL.md`, Layer 2/3)로 지연 로딩해야 합니다 [25, 27, 28].

##### 세부 4. 상태를 마크다운 체크박스(`plan.md`)로 관리하는 것은 안티패턴인가? 훅이 이를 완화하는가?
* **책의 경고**: 책 12장 및 안티패턴에서 "마크다운 체크리스트는 AI 모델이 세션 도중 완료된 것으로 착각하고 자의적으로 항목을 수정/삭제/체크하는 안티패턴이 발생한다"고 명시하며, JSON 스키마 기반(`00_requirements.json`, `passes: true/false`) 관리를 권장합니다 [9].
* **완화 정도**: `team-harness`는 `boundary` 훅(JSON Schema 필수필드 검사)과 `done` 가드(미완 체크박스 및 artifact/evidence 형식 확인)를 통해 자의적 수정 안티패턴을 **상당 부분 완화**하고 있습니다.
* **남은 리스크**: 마크다운 체크박스의 텍스트 표현 자체를 모델이 세션 중 미세하게 왜곡할 가능성은 여전히 존재하므로, 최종 판정 상태는 `boundary` 훅과 JSON/exit code로 100% 동기화시키는 구조가 더 안전합니다 [7, 37].

### 질문

> [질문 B — 단계별 실행 절차(flow) 검증]
> 같은 team-harness의 실제 단계별 흐름입니다(앞서 준 사실 요약 기준).
>
> 1) init: 소비자 저장소에 지침·훅·템플릿 설치. doctor가 진단(경고는 exit code에 영향 없음).
> 2) 세션 시작: SessionStart 훅이 활성 task·plan의 첫 미완 단계를 주입(nudge, 차단 없음). 활성 task가 없으면 "재개/새 task/task 없이 진행"을 모델이 사용자에게 묻도록 지침.
> 3) task 생성: `harness-team task <name>` → spec·plan·handoff·artifact·meta 생성.
> 4) spec: /harness-spec이 Confluence·Figma·인터뷰 중 선택 소스로 초안. Ambiguity 자가진단 게이트(Goal·Constraint·Success·Context·Ontology 점수) + /harness-interview가 원천 간 충돌(R1)을 먼저 검토. 통과 판정은 모델/사람 몫이며 기계 차단 아님. 작은 버그·문서 수정은 생략 허용.
> 5) plan: `## 단계` 마크다운 체크박스, Ontology 변경 로그, Done evidence 선언. 하지 않은 단계를 미리 체크하지 말라는 규범. 선택적으로 다이어그램.
> 6) 구현: 방식 자유(TDD 권장, 강제 아님). 선택형 /harness-loop가 gate commit·시나리오·plan 단계를 엮는 프롬프트 루프. 단위/컴포넌트/통합 테스트 작성 스킬 제공.
> 7) boundary/scenario: spec에 선언했을 때만 동작(옵트인). 미선언이면 not-configured로 통과.
> 8) review: `harness-team review codex|claude` + framing(adversarial, scenario, shipcheck, testcritic, contrarian, simplifier). 성공한 리뷰만 artifact `## Reviews`에 기록. 매 task 필수는 아니고 spec이 required 선언 시에만 done이 증거 확인. 리뷰 내용 품질은 기계 판정 안 함. 재시도 상한 규정 없음.
> 9) commit: gates.json 명령 실행·실패 시 차단 → post-commit이 handoff 자동 갱신(다음 커밋에 포함).
> 10) ship: scope/base 결정, 문서 갱신, 검증, shipcheck 리뷰, pr-check. PR 생성은 별도 지시.
> 11) done(기본 브랜치에서 머지 후): done 가드 → summary --write → 종결 커밋. `--force` 우회 가능(기록 남음).
> 12) retro/promote/wiki: 선택. retro는 활성 task가 있어야 동작하고 done 후엔 활성 task가 비워짐.
>
> 각 단계마다 책 기준으로: (a) 판정(적절/보완 필요/과잉), (b) 누락된 게이트나 안티패턴 노출, (c) 구체 개선안. 그리고 다음 두 가지를 별도로 답하세요.
> - "강제 범위를 최소화하고 개발 방식은 자유롭게 둔다(D11)"는 철학과, 책이 요구하는 "완료는 exit 0으로만 판정, 1줄 수정이라도 생략 불가"는 어떻게 충돌하며, 책이라면 어디에 선을 그을지
> - 이 흐름이 1인 개발자의 작은 변경에 과도하게 무거운지, 책의 "diff ≤100줄이면 단일 에이전트로 축약" 같은 규모별 분기 기준에 비춰 어떤 경량 경로를 두어야 하는지

| **5) plan** | **보완 필요** | • 마크다운 체크박스 사용 및 "하지 않은 단계를 미리 체크하지 말라"는 규범은 책이 경고한 **'마크다운 체크리스트 자의적 수정'** 안티패턴. | • 마크다운 체크박스와 병행하여 `meta.json` 내 `tasks` 배열의 `passes: true/false` 상태를 훅으로 동기화·기계 검증. |
| **6) 구현** | **보완 필요** | • TDD 권장 수준 및 자유 구현 방식은 구현과 검증이 분리되어 오류가 누적되는 **'끝 검증(분리 QA)'** 안티패턴 노출 위험. | • 코드 수정 시 단위 테스트 파일 동반 수정 여부를 `commit` 게이트에서 체크하는 린트 옵션 추가. |
| **7) boundary / scenario** | **보완 필요** | • 주 경계면 검증이 기본 활성화되지 않는 **'옵트인(Opt-in)'** 구조여서 검증이 쉽게 생략되는 안티패턴 발생. | • 기본값(Default)을 minimal boundary check로 설정하고, 필요 시 명시적으로 끄는 'Opt-out' 방식으로 전환. |
| **8) review** | **보완 필요** | • 리뷰어 framing 및 read-only 샌드박스는 우수하나, 재시도 상한 규정이 없고 리뷰 없이 머지되는 안티패턴(실제 운영 이슈) 발생. | • 리뷰 실패 시 **재시도 상한(최대 2~3회)** 설정, 피드백 포맷 스키마화, 리뷰 미수행 시 `done` 게이트 경고/에스컬레이션. |
| **9) commit** | **적절** | • `gates.json` 명령 실행 및 실패 시 차단, post-commit handoff 자동 갱신으로 결정론적 통제망 작동. | • `gates.json` 미설정 시 기본 테스트/린트 명령(`npm test` 등)을 자동 감지하여 강제 실행. |
| **10) ship** | **적절** | • shipcheck 리뷰 및 `pr-check` 적용이 우수함. 단, `--no-verify`로 우회 가능한 점은 관리 필요. | • CI/CD 파이프라인에서 `--no-verify` 우회 태그가 달린 commit/PR은 머지를 차단하도록 연동. |
| **11) done** | **과잉 & 보완 필요** | • `done`이 테스트를 직접 실행하지 않고 증거 파일 존재만 확인하며, `--force` 우회가 가능하여 **'거짓 보고 승인'** 안티패턴 노출. | • `done` 실행 시 `gates.json` 테스트 스위트를 **직접 1회 실행하여 `exit 0`을 확인**하는 필수 게이트로 변경. |
| **12) retro / promote** | **보완 필요** | • `done` 완료 후 활성 task가 비워져 `retro` 실행이 불가능해지는 순서상 연결 매끄럽지 않음. | • `done` 명령 실행 과정에 `retro` 작성을 선택적 워크플로로 포함하거나 task 상태를 `archived`로 변경하기 전 retro 수행. |

##### 반론 3 (done에서 테스트 재실행): "done은 PR 머지 후 실행되며, 이미 commit 게이트와 CI에서 돈 테스트를 중복 실행할 필요가 없다."

* **근거**:

##### 반론 4 (--force 금지): "예외 상황에서 우회를 막으면 사람들은 하네스를 아예 우회한다. 사유 기록 + 집계 노출이 낫다."
* **판정**: **수용**
* **근거**:
  * 책 10장(Phase 7-4)에서는 하네스 운용 중 가장 결정적인 이상 징후로 **'우회 관찰(Bypass Observation)'**을 꼽습니다 [17, 18]. 사용자가 하네스를 쓰지 않고 직접 편집기를 열거나 무단 우회하는 것은 하네스가 현장과 어긋나 있다는 증거입니다 [18].
  * 하네스가 하드 블로킹으로 사용자를 가둬버리면 사용자는 하네스 자체를 비활성화하게 되며, 이는 관측성(Observability) 자체를 파괴합니다 [17, 18]. 책 역시 동일한 오류나 예외 발생 시 무조건 멈추는 대신 `[MANUAL_INTERVENTION_REQUIRED]` 플래그를 남기고 사람에게 개입 권한을 넘기는 수동 에스컬레이션을 권장합니다 [19].
  * **결론**: `--force` 우회를 제공하되 **사유 입력을 강제하고 `meta.json` 및 `observe` scorecard에 우회 이력을 기록하여 회고(retro) 및 하네스 승격(promote)의 진화 재료로 삼는 현재 방식**은 책의 '우회 관찰 기반 진화 루프' 철학에 완벽히 부합합니다 [17, 18].

##### 반론 5 (quick 경로): "현재도 'task 없이 진행'을 선택하면 spec/plan 없이 commit 게이트만 거친다. 기존 경로 명시가 낫다."
* **판정**: **수용**
* **근거**:
  * 책은 1인 개발자나 소규모 변경(diff ≤ 100줄) 상황에서는 복잡한 다중 에이전트 팀이나 8단계 하네스 파이프라인을 돌리지 말고, **`CLAUDE.md` 30줄과 최소한의 검증 규칙으로 이루어진 단일 에이전트 모드**로 가볍게 시작하라고 권장합니다 [20, 21].
  * 불필요하게 CLI 신규 명령어를 추가하는 것은 오버 엔지니어링이며 [22], 이미 존재하는 "task 없이 진행" 경로의 진입 조건과 최소 게이트(`gates.json`)를 명확히 문서화하고 정식 패스트트랙으로 규정하는 것이 훨씬 우수한 하네스 설계입니다 [20, 21].

##### 반론 6 (마크다운 plan): "plan.md는 사람이 읽는 문서다. done 가드와 boundary 훅이 검사한다면 체크박스로도 충분하다."
* **판정**: **부분 수용**
* **근거**:
  * **수용 측면**: 사람이 읽고 PR에서 리뷰해야 하는 인터페이스 문서로서 `plan.md` 마크다운 형태는 필수적입니다 [책에 없음(추론)].
  * **기각 측면**: 그러나 책 12장 및 13장에서는 마크다운 체크리스트만 사용할 경우 세션이 길어지면 **AI 모델이 완료되지 않은 항목을 자의적으로 완료로 착각하거나 체크리스트를 통째로 지워버리는 안티패턴**이 발생한다고 분명히 지적합니다 [16, 23]. 따라서 책은 machine-state 관리를 위해 JSON 스키마(`00_requirements.json`, `batches.json`) 형태의 `status`/`passes` 관리를 병행하도록 요구합니다 [16, 23].
  * **결론**: 사람이 읽는 `plan.md` 마크다운을 유지하되, 훅(`boundary`)이 체크박스 이벤트를 감지할 때 **`meta.json` 내 기계 상태(`passes: true/false`)를 100% 자동 동기화**하도록 이중 레이어로 처리해야 완벽한 안정성을 얻을 수 있습니다 [16, 23].

#### 3. team-harness 0.54.0 종합 성숙도 평가 (한 단락)

> **종합 성숙도 평가**: `team-harness 0.54.0`은 책의 거버넌스 단계 모델상 **'2단계: 표준화 단계(Standardized Harness)'에서 '3단계: 최적화 단계(Optimized Harness)'로 넘어가는 우수한 전환기 시스템**입니다 [24]. `codex read-only` 샌드박스를 활용한 검증자 권한 기계적 차단 [25], `observe-tools` 훅 기반의 관측성 체계 [26], 회고 및 승격(`/harness-promote`)을 통한 점진적 진화 루프 [17], 그리고 현장의 우회 니즈를 수용하는 `--force` 가드레일 설계는 매우 뛰어난 수준입니다 [18]. 다만 런타임 동적 조율자(Orchestrator)를 의도적으로 배제함에 따라 에이전트 간 수평 통신(Peer-to-Peer)이 제한되고 [27], 상시 노출(eager) 지침이 231줄로 다소 과밀하여 LLM 인지 과부하 리스크에 노출되어 있습니다 [9]. eager 지침을 150줄 이하로 압축하고 마크다운 체크박스를 기계 상태 머신(`meta.json`)과 100% 동기화한다면, 토큰 경제성과 정합성을 갖춘 명실상부한 **3단계 최적화 하네스**로 완성될 것입니다 [12, 24].
