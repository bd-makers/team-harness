## 1. 결론

### 1.1 전반 판정

**철학은 일관되고, 경계의 결정론적 게이트도 코드상 구현돼 있다(훅을 실행해 보지는 않았다, §2). 남은 공백은 "규범으로 둔 단계가 실제로 지켜지는지"를 보이는 장치다.**

강점은 다섯 가지다.
- 범위 절제: 런타임 오케스트레이터를 두지 않는다는 D11의 선택은 노트북도 타당하다고 봤다.
- 결정론적 경계: 커밋(`gates.json`), 푸시(`pr-check`), 종결(`done` 가드)에 기계 검사를 둔다.
- 리뷰어 분리: 내장 리뷰 엔진은 쓰기 권한 없이 실행된다.
- 파일 기반 상태: task 문서 4종과 meta로 세션을 넘어 이어진다.
- 진화 루프: retro, promote, 결정 로그가 있다.

약점은 세 가지다.
- `review: required`를 선언하지 않은 task는 리뷰 증거 없이 닫히고, 그것이 결함인지 판단할 기록이 없다(1.4).
- task-gate와 R3 문구가 기록된 결정과 어긋난다(1.2).
- 규범 준수율을 재는 장치가 없다.

노트북이 제시한 책 기준으로 10개 영역을 판정하면 **부합 1 · 부분 8 · 미흡 1(수치 미검증, P1 조치는 기각)**이다(1.5 표). 미충족 9개 중 4개(권한·검증·구성요소 책임 분리·컨텍스트)는 기록된 범위 결정(D10·D11)과 연결된 의도된 선택이다. 1개(확률과 결정론)는 D11과 관련되지만 준수율을 재지 않는 공백이라 §6 #3이 다룬다. 나머지 4개(도구·상태·관측·진화)는 결정 없이 남은 공백이다.

### 1.2 소유자 확인 요청

두 항목 모두 새 결정이 아니다. 이미 기록된 결정에 문구를 맞추는 정정이다. 응답이 없으면 현재 문구가 그대로 남는다.

**(1) task-gate 문구**
- 현재 문구: [AGENTS.md:100](../../AGENTS.md?plain=1#L100)과 [templates/AGENTS.md.hbs:100](../../templates/AGENTS.md.hbs#L100)은 "**재개 / 새 task / task 없이 진행**을 확인하라 — 이는 block이 아닌 nudge이며 판단은 Claude 몫."이라고 쓴다. [session-context.mjs:92-93](../../src/commands/session-context.mjs#L92)은 "· task 없이 진행"과 "(단순 질문·조회·잡일이면 무시.)"를 출력한다. [README.md:160](../../README.md?plain=1#L160)과 [harness-task-guide.html:596](../harness-task-guide.html#L596)도 같은 세 선택지를 안내한다.
- 문제: "task 없이 진행"에 변경 규모 기준이 없고 "잡일"도 정의되지 않았다. D11은 "작은 수정도 full task다"를 재론하지 않을 항목으로 둔다([decisions.md:228-229](../decisions.md?plain=1#L228)).
- 제안 문구: "task 없이 진행"은 비변경 작업(질문·탐색·리뷰)에만 쓴다고 다섯 곳에 명시한다.

**(2) R3 문구**
- 현재 문구: [harness-cycle.md:40](../harness-cycle.md?plain=1#L40)은 마지막 열에 "△ spec이 required 선언할 때만 강제"라고 쓰면서, 같은 행의 게이트 열에는 "**R3 로컬 리뷰** (PR 전 필수)"라고 쓴다. [:75](../harness-cycle.md?plain=1#L75)는 "R3 — PR 전 코드 리뷰 루브릭, 필수."라고 쓰고, [:151](../harness-cycle.md?plain=1#L151)은 루프 안의 R3를 무조건 단계처럼 쓴다.
- 근거: 코드는 선언이 있을 때만 강제한다. spec 템플릿은 선언을 주석 처리한 채로 내보낸다([task.mjs:153-158](../../src/commands/task.mjs#L153)).
- 제안 문구: :40의 게이트 열과 :75, :151을 "권장, spec 선언 시 강제"로 맞춘다. AGENTS.md:59의 "중요한 변경" 조건과도 같은 뜻이 되도록 한 줄로 연결한다.
- 적용: task-gate와 R3 문구 정정을 task `notebooklm-review-fixes`에서 2026-11-16에 반영했다.

### 1.3 실행 순서

1. **두 문서를 정정한다(1.2).** 기록된 결정과 어긋난 문구를 먼저 맞춰야 이후 권고의 기준이 선다.
2. **`done` 출력에 리뷰 증거 유무를 보인다(§6 #1).** 1.4의 판별 불가를 종결 시점에 드러내는 가장 싼 방법이다.
3. **retro를 `done` 전에 하라고 적는다(§6 #2).** 지금 순서로는 종결 뒤 retro가 실패한다.
4. **규범 준수 eval 기준선을 잰다(§6 #3).** 규범을 강제로 바꿀지 판단하려면 먼저 수치가 필요하다.

### 1.4 핵심 근거

**`review: required`를 선언한 task 75건은 모두 리뷰 증거가 있다.** `done` 가드는 선언한 task가 증거 없이 닫히는 것을 막는다([task.mjs:977-993](../../src/commands/task.mjs#L977)). `--force`로 이 가드를 우회할 수 있지만([task.mjs:1097-1117](../../src/commands/task.mjs#L1097)), 표본에서 강제 종결된 2건도 모두 선언이 있었고 증거도 있었다. 두 건이 우회한 항목은 리뷰가 아니라 "커밋되지 않은 변경이 있음"이었다(각 task meta의 `forcedIssues`).

**`review: required`를 선언하지 않은 task는 증거 없이도 닫힌다.** 2026-09-10 이후 생성된 task 86건 가운데 16건(18.6%)이 리뷰 증거 없이 종결됐다. 16건은 모두 `review: required`를 선언하지 않았고, 그중 13건은 날짜가 붙은 산문 리뷰 기록도 없다. 16건 중 10건은 `## Done evidence` 블록이 있었는데, 7건은 `review: optional`을 명시했고 3건은 `tests`만 선언했다. 나머지 6건은 블록이 없다(같은 선언 정규식으로 따로 셌다, [집계 방법]). 명시한 `optional`은 가드를 끈다는 선언일 뿐, 리뷰를 생략한 사유를 기록한 것은 아니다. 2026-09-10은 `harness-team review`가 실행 기록을 meta에 쓰기 시작한 날이다(커밋 `d836c3e`).

**이 16건이 결함인지는 지금 판단할 수 없다.** AGENTS.md는 기록하지 않은 리뷰를 "안 한 것"으로 간주하므로([AGENTS.md:62](../../AGENTS.md?plain=1#L62)) 16건은 리뷰를 하지 않은 것으로 센다. 그러나 같은 문서는 리뷰를 "중요한 변경"에만 요구하고([AGENTS.md:59](../../AGENTS.md?plain=1#L59), [:140](../../AGENTS.md?plain=1#L140)), 중요도나 생략 사유를 기록하는 장치는 없다. 그래서 "의도한 생략"과 "빠뜨림"을 구분할 수 없다. 엄격도는 팀의 선언으로 올린다는 일반 원칙은 D11의 2026-11-02 정정에 있지만, 이 정정은 `tests`를 두고 쓴 것이다([decisions.md:208-210](../decisions.md?plain=1#L208)). 리뷰 기본값 OFF에 고유한 근거(마커 신뢰 기반이라 부분 검증일 뿐이고, 전면 강제는 `--force` 습관을 만든다)는 코드 주석에만 있다([task.mjs:586-589](../../src/commands/task.mjs#L586)).

## 2. 방법과 신뢰도

**방법.** 읽기 전용 조사 3건(설계·아키텍처, 단계별 흐름, 운영 증거)으로 하네스 사실 요약을 만들고, 핵심 주장은 소스로 다시 확인했다. NotebookLM에는 다섯 번 물었다. Q1·Q2는 레포 정보 없이 책의 기준만 물었고, Q3·Q4는 사실 요약을 주고 대조를 요청했으며, Q5는 작성자 반론 6개에 대한 판정을 받았다. 리뷰 증거 수치는 `done` 가드와 같은 파서로 셌다([집계 방법]).

**신뢰도 한계.** 아래 판단을 쓸 때 함께 고려해야 한다.
- 출처가 책 한 권이다. 노트북의 판정은 이 책을 노트북이 해석한 기준일 뿐이다.
- 책 원문은 대조하지 않았다. 판정에 쓰인 수치 가운데 37%, "51번째 호출" 위반, 150줄, 도구 15개, MCP 3개, 180k, diff 100줄, 73% 모니터링 부재, 메시지 큐 50개, Vercel 47%p, Stripe 400개 도구, 스킬 description 1,536자, 거버넌스 성숙도 모델은 모두 미확인이다.
- Q2의 단계 흐름은 노트북이 여러 장을 "종합하여 정리"한 것이다(부록 Q2). 책이 정의한 단계 목록으로 읽으면 안 된다.
- Q3에 준 사실 요약에 오류 5건이 있었다. 이 보고서는 [정오표]를 기준으로 다시 판정했다.
- Q5에서 노트북은 반론 6개 중 3개를 수용, 3개를 부분 수용했고 새 인용은 거의 없었다. 동조 가능성이 있어 번복은 근거로 쓰지 않았다. 반론은 이 보고서 작성자가 썼으므로 자기검토 편향도 있다.
- 질문마다 한 번씩만 물었다. 같은 질문을 반복했을 때의 변동은 모른다.
- 표본은 이 저장소 자체의 task다(chad·hslee). 소비자 프로젝트로 일반화하기 어렵다.
- 평가하지 않은 것: 전체 테스트 실행, 훅의 런타임 동작, 소비자 프로젝트 동작, 모델 eval. migrate와 안전 가드(protect-files 등)는 짧게만 다뤘다.

## 3. 설계·구현 철학

Q3에서 물은 쟁점마다 판정을 먼저 적는다.

**(1) 오케스트레이터 없는 범위: 타당.** 노트북은 책의 "30분 Quick Start" 관점에서 범위를 좁힌 것을 긍정했고, D11도 서비스형 런타임 오케스트레이터를 소유하지 않기로 했다. 대가는 동적 팬아웃·팬인과 에이전트 간 수평 조율이 없다는 점이다. 선택형 기본 루프(`/harness-loop`, S3)가 이를 일부 메운다.

**(2) 다른 벤더 리뷰어: 내장 엔진은 부합.** 작성자(Claude)와 리뷰어(Codex)를 나누고, 내장 엔진은 쓰기 권한 없이 실행한다. 책은 벤더 분리에 입장이 없고, 장단점(맹점 보완 대 출력 형식 차이)은 노트북의 추론이다. Codex가 없으면 Claude로 폴백해 같은 벤더가 검증하는데, 이는 D7이 정한 리뷰어 집합이다. 남는 약점은 `review: required` 가드가 어느 엔진이 돌았는지 보지 않는다는 점이다. custom 엔진은 권한이 강제되지 않지만 이 저장소에서는 쓰이지 않으므로 D6 재평가 항목으로 둔다(1.5 [^c], §5).

**(3) 마크다운 plan: 부분.** 노트북은 마크다운 체크리스트를 모델이 자의로 고치는 안티패턴으로 봤다. `done` 가드는 체크하지 않은 단계를 막지만, 하지 않은 단계를 체크한 경우는 잡지 못한다. boundary·scenario 검사는 spec에 선언했을 때만 돕는다. JSON 상태로 옮기자는 제안은 SSOT를 둘로 나누므로 받지 않았다(§5).

**(4) 컨텍스트: 미흡(책 수치 기준).** 노트북은 eager 지침 231줄이 150줄 기준을 넘는다고 봤다. 하네스는 줄 수 대신 바이트 예산을 쓰고 그 예산은 충족한다(1.5 [^d]). 150줄 수치는 원문을 확인하지 못했으므로, 줄이는 방향은 감시 항목으로만 둔다(§6).

**(5) 관측: 부분.** 모든 도구 호출·실패·권한 거부를 Claude Code에서 기록하고 scorecard를 만든다. 책이 말한 피로 곡선(같은 파일 반복 수정)과 컨텍스트 임계 신호는 없다. Codex 쪽을 관측하지 않는 것은 D9의 의도다.

**(6) 환경(D12): 책 5축 밖.** D12는 환경을 서술하고 빈칸을 보고하지만 갖춤은 요구하지 않는다([decisions.md:249](../decisions.md?plain=1#L249)). 노트북의 5축에는 환경이 없어서 판정 대상에서 뺐다.

### 4.2 작은 수정의 경량 경로

**판정: 일치(조건부).** 노트북의 Q2 답변은 스스로 엇갈린다. Phase 0은 "축약 불가", Phase 1은 "diff 100줄 이하면 팬아웃 생략", Phase 4는 "1줄 수정도 exit 0 필수", Phase 7은 "구조 검증만"이라고 했다. 공통 핵심은 "설계 팬아웃은 줄여도 되지만 결정론적 게이트는 생략하지 않는다"이다. 하네스는 작은 수정도 full task로 두되 spec Ambiguity 게이트는 생략을 허용하고, 커밋 게이트는 유지한다. 이 핵심과 일치한다. 단, `gates.json`이 설정된 경우에만 그렇다. 이 조건부 일치는 커밋 게이트에만 해당한다. `done`은 테스트의 exit 0을 요구하지 않는다(4.1 [^5]).

### 4.3 리뷰 증거 집계

1.4의 수치를 시기별로 나누면 다음과 같다. 모두 [집계 방법]의 스크립트 출력이다.

| 구분 | 종결 task | 리뷰 증거 없음 | 그중 날짜 산문도 없음 | required 선언(누락) |
|---|---|---|---|---|
| 2026-09-10 이전 생성 | 90 | 56 | 16 | 24 (0) |
| 2026-09-10 이후 생성 | 86 | 16 | 13 | 51 (0) |
| 합계 | 176 | 72 | 29 | 75 (0) |

- **증거**는 artifact의 리뷰 마커 또는 meta의 리뷰 기록이다. `done` 가드도 `review`에 대해서는 둘 다 인정한다([task.mjs:977-993](../../src/commands/task.mjs#L977)). meta만 인정하는 것은 `verify`뿐이다.
- **날짜 산문**은 `## Reviews` 아래 날짜가 붙은 항목이나 제목이다. 가드가 증거로 세지는 않지만, 리뷰를 했다는 흔적일 수 있다.
- **증거 창**: 가드는 reopen 이후 등 특정 시점 이후의 증거만 센다. 창을 적용하면 합계가 103/73으로 1건 달라지고(`docs/chad/template-refresh-policy`), 2026-09-10 이후 수치와 required 수치는 같다.
- **강제 종결**: `--force`로 닫은 흔적은 176건 중 2건이다. 기록은 task마다 가장 최근 1건만 남는다([task.mjs:1131-1135](../../src/commands/task.mjs#L1131)).

**#1 완료 기준.** 이미 있는 "보장 범위" 출력([describeDoneScope, task.mjs:914-930](../../src/commands/task.mjs#L914), 커밋 `473354f`)을 넓힌다. 지금은 선언이 없을 때 "리뷰 실행 기록(review: optional)"을 "확인 안 함"으로만 표시하고, 증거가 실제로 있는지는 말하지 않는다. 증거 있음·없음과 `gates.json` 설정·미설정의 네 조합에 대해 정확한 출력 문자열을 확인하는 테스트를 `tests/done-guard.test.mjs`에 추가한다. 현재 출력 줄을 그대로 담은 골든 픽스처([tests/fixtures/task-paths-golden/expected.txt:60](../../tests/fixtures/task-paths-golden/expected.txt#L60))도 함께 갱신하고, 기존 done 테스트와 골든 e2e 테스트(`tests/e2e/task-paths-golden.test.mjs`)가 통과하면 완료다. 커밋 게이트는 통과할 때 이미 실행한 선언 게이트를 알린다([gate.mjs:65](../../src/commands/gate.mjs#L65)). 따라서 #1은 그 보고를 반복하지 않고, `gates.json`이 없는 경우를 `done` 출력에 더하는 것이다.
- 2차 장치 규칙: 새 장치를 만들지 않고 기존 출력 한 줄을 넓힌다. 원래 장치(리뷰 마커)를 없애는 안은 리뷰 기록 자체를 잃으므로 기각했다. 규범 자체를 줄이는 안, 즉 기록하지 않은 리뷰를 "안 한 것"으로 보는 규범([AGENTS.md:62](../../AGENTS.md?plain=1#L62))을 빼는 안도 검토했다. 이 규범을 빼면 1.4의 16건을 판단할 기준마저 사라지므로 기각했다.

**#2 완료 기준.** [commands/harness-retro.md](../../commands/harness-retro.md?plain=1#L10)에 "활성 task가 있을 때, 즉 `done` 전에 실행한다"는 문장이 있으면 완료다. [skills/harness-retro/SKILL.md](../../skills/harness-retro/SKILL.md?plain=1#L12)는 명령 문서를 정본으로 가리키기만 하므로 고치지 않는다.
- 2차 장치 규칙: `done`이 retro를 자동 실행하는 안은 새 장치라 택하지 않았다.

**#3 완료 기준.** 기존 23건은 스킬 라우팅과 응답 품질을 재고, 규범 준수는 재지 않는다([evals/README.md:3](../../evals/README.md?plain=1#L3)). 그래서 신규 케이스 4건(아래 표)은 기존 케이스와 따로 집계하는 규범 준수 기준선이다. 케이스마다 3회 실행하고, 판정 모델을 고정해 기록한다. 기본 판정 모델은 haiku로 작성자와 같은 벤더다([evals/README.md:40](../../evals/README.md?plain=1#L40)). 도구가 다른 벤더의 판정 모델을 지원하면 그것을 쓰고, 지원하지 않으면 이 한계를 결과에 함께 적는다. 기준선을 실제로 돌리고, 케이스별 통과율과 모델·날짜·실행 횟수를 한 artifact에 기록한 뒤 같은 artifact에 숫자 임계값을 정하면 완료다. 임계값만 정하고 기준선을 돌리지 않으면 완료가 아니다. 시작값으로는 "케이스마다 3회 중 2회 이상 통과"를 제안한다. 다만 3회 중 2회는 한 번의 흔들림으로 판정이 바뀌므로, 같은 출력을 다시 채점해 판정 모델이 같은 판정을 내는지도 함께 기록한다.
- 2차 장치 규칙: 측정 장치를 하나 더하는 일이다. 원래 장치(규범 문장)를 줄이는 안은 근거 수치가 없어 지금은 판단할 수 없다. 기준선 결과를 보고 그 task의 spec에서 축소 여부를 정한다.

| `53-review-recorded-before-pr` | 중요한 변경에서 PR 전에 리뷰를 기록하는가 |

**감시 항목(조치 아님).** eager 합계가 doctor 예산에 가까워지면, 즉 소비자 프로젝트에서 예산 경고가 실제로 나오면 AGENTS.md의 task 절차 상세를 명령 문서로 옮기는 안을 검토한다. 그 전에는 줄 수 기준을 두지 않는다.

[^j]: [evals/README.md:45-46](../../evals/README.md?plain=1#L45). 기본값은 케이스당 3회이고, WITH(플러그인)와 W/OUT(플러그인 없음) 두 갈래로 돈다. 그래서 신규 4건의 기본 실행은 4건 × 3회 × 2갈래 = 24회이고, `--ablation none`이면 WITH만 돌아 12회다. $7.91은 2026-11-01에 7개 케이스 측정과 추가 확인 5회를 돌린 비용이다. 케이스 수와 실행 설정이 달라 신규 4건의 비용 추정이 아니라 규모를 가늠하는 참고값이다.

## 용어

- **D2·D6**: 작성자와 리뷰어를 나누고(D2), 리뷰어는 별도 컨텍스트에서 읽기만 하며 반박만 한다(D6).
- **D4·D5**: 같은 워킹트리에서는 쓰기를 한 줄로만 하고(D4), 격리된 브랜치·worktree 병렬은 허용한다(D5).
- **D7**: OpenCode·Gemini를 멤버에서 빼고, 리뷰어 집합을 Codex와 같은 모델의 `claude` 엔진(plan 모드)으로 정했다.
- **D9**: Codex 훅은 SessionStart 하나로 제한한다.
- **D10**: Claude가 AGENTS.md를 읽을 수 있어도 CLAUDE.md의 import 구조를 유지한다.
- **D11**: 하네스의 범위 헌장. 강제는 PR의 task 문서로 좁히고, 구현 방식은 자유이며, "작은 수정도 full task"는 재론하지 않는다.
- **D12**: 환경 하위 시스템. 서술과 빈칸 보고는 하되 갖춤은 요구하지 않는다.
- **R1–R3**: 검토 지점. R1은 원천 문서 검토, R2는 시나리오와 증거 대조, R3는 PR 전 코드 리뷰다.
- **S0–S8**: 사이클 단계. S0 셋업, S1 spec, S2 plan, S3 구현, S4 구현 검증, S5 커밋, S6 코드 리뷰, S7 PR, S8 지식화.
- **Q1–Q5**: NotebookLM에 한 질문 다섯 개. Q3=질문 A, Q4=질문 B, Q5=질문 C. P1–P5는 Q5의 우선순위 Top 5다.
- **부합·부분·미흡**: 노트북이 제시한 책 기준을 충족함, 일부만 충족함, 충족하지 못함(1.5 영역 판정). Q3 답변의 "부분 부합"은 "부분"과 같은 뜻이다.
- **적절·보완 필요·과잉**: Q4 답변이 단계별로 쓴 판정어다(4.1 단계 판정). 이 보고서도 단계 판정에는 같은 말을 쓴다. 보류는 운영 근거가 아직 부족해 판정을 미룬 것이다(4.1 S8).
- **자체 판단**: 노트북의 판정과 다르거나 노트북 판정이 없어서 이 보고서가 내린 판정.
- **리뷰 증거**: artifact의 리뷰 마커 또는 meta의 리뷰 기록. **날짜 산문**: `## Reviews` 아래 날짜가 붙은 서술형 기록(가드는 세지 않는다).
- **증거 창**: `done` 가드가 증거로 인정하는 기간. reopen이나 첫 활성화 이후다.
- **nudge**: 막지 않고 안내만 하는 신호. **eager**: 세션마다 항상 로드되는 지침. **baseline**: 기준선 측정값.
- **2차 장치 규칙**: 다른 장치를 고치거나 보이기 위해 새 장치를 추가하기 전에, 원래 장치를 빼거나 줄이는 안을 먼저 검토하고 기각 사유를 남긴다([decisions.md:222](../decisions.md?plain=1#L222)).
