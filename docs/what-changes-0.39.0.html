검증 프레이밍 프롬프트의 정본이
문서에서 src로 갑니다

0.39.0은 D6 검증 프레이밍 5종(adversarial·testcritic·shipcheck·contrarian·simplifier)의 리뷰 프롬프트를 src/commands/review-prompts.mjs 상수로 옮깁니다. 0.37.0은 공용 리뷰 프롬프트만 src에 두고 프레이밍은 "문서를 읽어 파일에 옮겨 쓴 뒤 --prompt-file로 넘겨라"로 남겼습니다 — 그 옮겨 쓰기 단계가 kind와 실제로 엔진에 간 프롬프트 사이에 기록되지 않는 변형을 끼웠습니다. 이제 harness-team review <engine> --framing <접미사>만으로 실행됩니다.

contrarian · simplifier"활성 task의 spec/plan 실제 경로를 읽으라고 지시하고 아래 표를 D6 스키마로 채점하게 구성하라" — 세션마다 다른 프롬프트src 상수. spec/plan 경로는 CLI가 채우고 scope는 task-docs로 고정

바뀌지 않은 것. kind 형식·verify allowlist·마커 형식·엔진 runner·scope 결정·기록 경로·루브릭 행의 문구는 그대로입니다. 이 릴리스는 프롬프트 텍스트의 정본 위치를 옮기는 것이지 기준 개정이 아닙니다. 문서가 정본인 것은 여전히 절차입니다.

달라진 것

Changed

템플릿 7종이 src 정본, 문서 블록은 마커로 pin

무엇
FRAMING_TEMPLATES(framing·rubric·target·doc·template). 각 커맨드 문서의 <!-- harness:prompt framing=… [rubric=…] --> 마커 다음 text 블록이 미러이고, pin 테스트 loop 1개가 7종을 한 글자 단위로 대조합니다. 문서에만 있는 고아 마커도 셉니다.
왜
공용 프롬프트(REVIEW_PROMPT_TEMPLATE)와 같은 구조입니다 — kind ↔ 실제 프롬프트가 결정론적으로 묶여야 meta.reviews의 kind가 "무엇을 물었는가"를 뜻합니다.
Added

--rubric — testcritic의 루브릭 선택자

무엇
--framing testcritic --rubric unit|component|integration. kind는 바뀌지 않고 meta.reviews 항목에 rubric 필드가 있을 때만 붙습니다. artifact 정보 줄에도 표시됩니다.
거부 조건
testcritic에 --rubric이 없거나, 다른 프레이밍에 붙이거나, 열거 밖이면 엔진을 돌리기 전에 error 패킷 — 아무것도 쓰지 않습니다.
Changed

task-docs 프레이밍의 scope 고정과 경로 치환

무엇
contrarian·simplifier는 --scope를 생략하면 task-docs이고, 다른 값을 주면 거부합니다(프롬프트가 diff를 보지 않는데 diff로 기록하면 거짓 기록). git target 프레이밍에 --scope task-docs를 붙이는 것도 같은 이유로 거부. <spec path>·<plan path>·<artifact path>는 활성 task의 실제 경로로 CLI가 채웁니다.
왜
CLI가 활성 task를 이미 알고 있는데 에이전트가 경로를 써 넣던 단계가 남아 있었습니다.
Changed

문서 7종 + harness-review.md 5단계

무엇
루브릭 마크다운 표를 마커 + text 블록으로 대체했습니다(같은 문서 안에 표와 블록이 둘 다 있으면 서로 drift). 실행 명령은 --framing(+--rubric)로. "프롬프트를 파일에 쓰고"라는 지시가 남아 있지 않은지 테스트가 grep합니다.
override
--prompt-file은 남습니다 — 템플릿 대신 다른 프롬프트를 쓸 때의 경로이고 kind는 그대로 --framing에서 옵니다.

소비자가 할 일

Upgrade

플러그인 갱신 후 프레이밍 커맨드는 파일을 쓰지 않습니다

무엇
커맨드 문서를 따르는 에이전트는 harness-team review <engine> --framing <접미사>만 호출합니다. 테스트 스킬 3종은 --rubric을 붙입니다.
기존 호출
--framing X --prompt-file P는 그대로 동작합니다(override). contrarian·simplifier에 손으로 주던 --scope task-docs도 같은 값이라 통과합니다. 다른 scope를 주던 호출만 거부됩니다.
None

기존 증거는 바뀌지 않습니다

왜
kind·allowlist·마커 형식이 불변이라 이미 기록된 meta.reviews와 artifact 마커는 종전 그대로 판정됩니다. rubric은 새 항목에만, 있을 때만 붙습니다.
알아두실 것
이 릴리스 자신의 리뷰가 새 경로의 첫 dogfood였습니다 — review codex --framing adversarial(프롬프트 파일 없음)이 P2 1건(생성 문서 인벤토리 누락)을 잡았고 반영했습니다.
