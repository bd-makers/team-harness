Release note · 2026-09-11

끝난 일을 다시 시작하는 것과
증거를 옮길 길이 없던 것

0.38.0은 두 가지를 닫습니다. 하나는 다른 클론에서 이미 종결된 task를 모르고 다시 붙잡는 실패 — 2026-09-10에 두 클론이 같은 task를 각자 구현해 6커밋을 폐기했습니다. 다른 하나는 0.37.0이 의도적으로 남긴 빈칸입니다: 구 task를 CLI 소유 리뷰 증거로 옮기는 명시적 경로가 없어서, 릴리스 노트가 "지금은 손으로 "reviews": []를 넣지 마세요"라고만 말할 수 있었습니다. 이제 migrate --adopt-reviews가 그 길이고, 잃는 증거를 가드와 같은 방식으로 세어 보여준 뒤에만 옮깁니다.

"열려 있다"는 로컬의 사실이지 팀의 사실이 아니었습니다

.harness/active.json은 gitignore 대상입니다. 그래서 한 클론이 task를 종결해도 다른 클론의 세션은 그 사실을 구조적으로 볼 수 없었습니다 — 2026-09-10에 두 클론이 같은 task를 각자 구현해 6커밋을 폐기했습니다.

Added

main에서 이미 종결된 task를 세 지점이 알립니다

판정
활성(또는 활성화하려는) task의 meta를 origin/<default>에서 fetch 없이 읽어 status === 'done'인지 본다. 정본은 새 모듈 src/commands/remote-task.mjs 한 곳.
세 지점
session-context(SessionStart — breadcrumb·TCC 대신 nudge만) · doctor(done on main warning) · task <name>(출력 첫 줄). 막지 않습니다 — 판단은 사람 몫입니다.
Design

고의로 다시 연 task에는 조용합니다

규칙
로컬 meta가 이미 done이거나, 로컬 reopenedAt이 원격 closedAt보다 나중이면 침묵합니다. 재개는 정상 동작이지 사고가 아닙니다.
degrade
git이 없거나·저장소가 아니거나·origin이 없거나·partial clone이라 blob이 없으면 조용히 건너뜁니다(2 s timeout, GIT_NO_LAZY_FETCH=1). "모른다"를 "열려 있다"로 바꾸지 않습니다.

migrate --adopt-reviews — 옮길 길을 만들되, 비용을 먼저 말합니다

0.37.0은 reviews 키가 없는 구 task를 종전 판정(artifact 마커)에 두고, review도 키를 만들지 않습니다 — 키 생성을 부수효과로 두면 첫 호출 순간 기존 손 마커가 증거에서 빠지기 때문입니다(적대적 리뷰 P1). 옮기고 싶은 사람에게는 길이 없었습니다.

Added

harness-team migrate --adopt-reviews

대상
열린(status !== 'done') task 중 meta에 reviews 키가 없는 것. 같은 실행의 meta backfill 뒤에 돌아 방금 만들어진 meta도 후보가 됩니다.
고지
task마다 "채택하면 증거에서 빠지는 검증 마커 N개"와 그 결과(verify: required면 종결 전 리뷰 재실행 필요)를 보여준 뒤 확인을 받습니다. spec이 verify를 요구하지 않으면 "잃는 증거 없음"이라고 그대로 말합니다.
Design

N은 가드와 같은 함수로 셉니다

왜
사용자가 보는 수와 가드가 세는 수가 다르면, 증거를 잃는 것에 동의하는 그 순간에 잘못된 정보를 준 것입니다.
어떻게
판정 창 계산을 evidenceWindowStart(meta)로, kind 대조를 isVerifyKind(kind)로 task.mjs에서 추출해 가드와 migrate가 같은 함수를 호출합니다. 창 규칙은 이미 두 번 바뀐 자리라 복제하면 반드시 갈라집니다.
Safety

--yes 단독으로는 채택하지 않습니다

규칙
플래그가 없으면 안내 한 줄만 내고 아무것도 바꾸지 않습니다. --adopt-reviews가 옵트인이고, --yes는 그 안의 확인만 만족시킵니다.
왜 이 단계만
다른 migrate 단계는 구조를 옮기지만, 이 단계는 증거를 잃습니다. 되돌리려면 그 meta에서 reviews 키를 지우면 됩니다.

review 기록 품질 3건 — 0.37.0 codex 실측 리뷰가 잡은 것

증상왜 문제인가조치
리뷰 블록이 EOF에 붙어 ## Reviews가 아니라 Learnings 절 아래에 쌓임두 절의 의미가 뒤집힙니다 — 기록의 자리가 곧 기록의 종류입니다fence 상태를 추적해 fence 밖 첫 줄머리 Learnings 헤딩 앞에 삽입. 없으면 종전대로 append
exit 0이면 stdout이 0 B여도 증거로 기록됨아무것도 출력하지 않는 잘못 설정된 custom reviewer가 verify: required를 통과시킵니다공백뿐인 stdout은 error 패킷으로 거부 — artifact 파일을 만들지도 않습니다(패킷에 stderr 꼬리 포함)
custom 상대경로 preflight가 process cwd 기준실행은 targetDir에서 하므로 --target과 조합하면 멀쩡한 reviewer가 오거부됩니다which(name, env, cwd) — 첫 토큰 경로와 PATH 항목 양쪽을 실행 기준으로 resolve

fence 인식이 장식이 아닌 이유. 이 저장소를 리뷰하면 엔진 출력 안에 Learnings 헤딩 문자열이 그대로 들어옵니다(템플릿과 가드 코드에 있는 문자열입니다). 순진한 정규식은 두 번째 리뷰부터 이전 블록의 fence 안쪽을 찍어 파일을 반으로 가릅니다 — 깨끗한 템플릿으로 쓴 단위 테스트는 통과하고 실제 artifact만 깨지는 종류의 결함이라, 테스트를 이전 블록이 있는 상태로 고정했습니다.

바꾸지 않은 것

대상이 릴리스왜
기존 task의 종결 판정불변채택은 사용자가 플래그로 고르는 조작입니다. 아무것도 하지 않으면 종전 그대로입니다
review의 부수효과 금지불변CLI는 여전히 구 task에 reviews 키를 만들지 않습니다 — 그 금지가 채택을 별도 조작으로 만든 이유입니다
가드의 위협 모델불변 — 망각·실수meta를 손으로 고치는 위조는 여전히 막지 않습니다
done-on-main nudge의 강도nudge — 막지 않음원격 상태는 "모를 수" 있고(partial clone·offline), 모르는 것으로 작업을 막으면 가드가 아니라 장애가 됩니다
templates/불변소비자 설치 파일은 바뀌지 않습니다

리뷰 — codex 3회, 세 번째에 APPROVE

발견판별조치
P2 which()의 PATH 루프가 join(dir, name)이라 PATH 항목 자체가 상대 경로면 여전히 process cwd 기준진짜 — 첫 토큰만 고치고 루프를 남기면 같은 버그가 한 자리 옮겨 살아남음resolve(cwd, dir, name) + 엔진 probe 두 자리도 같은 기준으로 통일, 회귀 테스트 추가
P3 가드가 추출한 isVerifyKind() 대신 private 정규식을 계속 호출진짜 — "같은 판정 함수" 계약이 반쪽가드도 isVerifyKind()를 호출
P2 삽입이 문장을 갈라 블록이 ## Reviews보다 앞에 놓임오탐 — 원인은 코드가 아니라 1차 블록을 손으로 옮길 때 쓴 naive indexOfartifact 복구 후 3차 리뷰로 배치를 실측(## Reviews 아래·Learnings 앞 확인)
P3 artifact의 "신규 테스트 12건"이 실제 13건과 불일치진짜 — 문서 오기수정

1차 리뷰는 옛 코드로 돌았습니다. PATH의 harness-team은 마켓플레이스 clone(= 마지막 릴리스 코드)이라, 방금 고친 배치 동작이 아니라 0.37.0의 EOF append를 그대로 재현했습니다. 개발 중 dogfood는 node bin/harness-team.mjs로 돌려야 의미가 있습니다 — MAINTAINING.md의 "필수 검증" 절이 이미 같은 이유로 세 명령을 로컬 bin으로 부르라고 적고 있습니다.

소비자가 할 일

None

기본값은 여전히 "아무것도 하지 않기"입니다

구 task
reviews 키가 없는 meta는 종전 판정 그대로이고, review를 돌려도 키가 생기지 않습니다. 이미 있는 마커 증거는 그대로 유효합니다.
업그레이드
플러그인 갱신만으로 끝납니다 — templates/가 바뀌지 않았으므로 init 재실행이 필요 없습니다.
Optional

옮기려면 CLI에 맡기세요

명령
harness-team migrate --adopt-reviews — 잃는 마커 수와 그 결과를 보여주고 확인을 받은 뒤에만 reviews: []를 넣습니다.
여전히 금지
손으로 "reviews": []를 넣지 마세요. 그 순간 고지 없이 기존 마커가 verify 증거에서 빠집니다 — 0.37.0 노트의 그 문장은 인가 경로가 생겼을 뿐 유효합니다.
Note

다른 클론에서 종결한 task를 붙잡고 있었다면

증상
SessionStart·doctor·task <name>이 "main에서 이미 종결됨"을 알립니다.
정상 복구
main을 가져온 뒤 harness-team task <name> — 로컬 meta가 done이 되고, 다시 열면 reopenedAt이 생겨 다음 세션부터 조용합니다.
