0. 시작 전 확인 — 3개 채널이 모두 닫혔는가

하네스 구성요소는 서로 독립된 3개 채널로 도달합니다. 한 채널이 끝나도 다른 채널은 자동으로 끝나지 않습니다. 이 표를 모르면 "커맨드가 안 보인다 / 훅이 안 돈다"의 절반이 여기서 발생합니다.

채널단위제공하는 것
init프로젝트당 1회 (재실행은 갱신)hooks · rules(RN 계열만) · AGENTS/CLAUDE.md · docs/ 구조 · .codex/hooks.json · .cursor/rules(RN 계열만)
Claude Code 플러그인 설치사람·머신마다/harness-* 슬래시 커맨드
전역 harness-team CLI 링크사람마다터미널과 훅이 호출하는 CLI 실행 파일
⚠️
이미 하네스가 적용된 저장소를 clone했다면 init을 다시 돌릴 필요가 없습니다

프로젝트 채널은 이미 커밋되어 있습니다. 당신에게 없는 것은 플러그인 설치와 전역 CLI 링크뿐입니다. 이 패키지는 npm 공개 저장소에 배포되지 않으므로, 전역 CLI는 /plugin install이 만든 로컬 마켓플레이스 클론을 링크해서 얻습니다.

# 내 머신에만 필요한 두 채널
/plugin marketplace add https://github.com/bd-makers/team-harness
/plugin install harness-aijient-team
npm i -g "${CLAUDE_PLUGINS_ROOT:-$HOME/.claude/plugins}/marketplaces/harness-aijient-team-marketplace"

# 확인 — 여기서 green이 아니면 작업을 시작하지 않는다
cd my-project
harness-team doctor

doctor는 파일 무결성만 보지 않고 PATH의 harness-team이 실제로 실행되며 session-context/handoff를 지원하는지까지 확인합니다(0.13+). 실패하면 전역 CLI 재링크 안내를 냅니다 — 훅이 조용히 죽어 있는 상태로 며칠을 보내는 사고를 막는 검사입니다.

0.15.2에서 여기에 버전 드리프트 검사가 붙었습니다. 릴리스는 슬래시 커맨드 캐시만 새 버전으로 만들고 PATH의 CLI는 마켓플레이스 클론에 묶여 옛 버전으로 남을 수 있습니다. 신기능이 "없다"고 느껴지면 먼저 harness-team --version(0.15.1 신설)으로 채널을 확인하세요 — 이 명령이 Unknown command로 떨어지면 그 자체가 클론이 낡았다는 신호입니다.

0.23.0에서는 여기에 eager 계층 크기 경고가 하나 더 붙었습니다 — 매 세션 무조건 로드되는 AGENTS.md + CLAUDE.md의 UTF-8 합산이 24 KiB를 넘으면 경고합니다. fail이 아니라 warning이라 doctor는 계속 green이고, 문서가 커지는 데에는 정당한 이유가 있을 수 있어 판단은 사람 몫으로 남깁니다 — 그래서 대응은 지시를 지우는 것이 아니라 절차를 커맨드 문서·스킬 같은 lazy 정본으로 옮기는 쪽입니다.

0.23.1은 그 합산의 범위를 실제 로드 집합에 맞췄습니다 — 프로젝트 .claude/CLAUDE.md와 사용자 전역 CLAUDE.md(CLAUDE_CONFIG_DIR ?? ~/.claude 아래)를 더해 네 파일의 합계에 예산을 겁니다. 파일마다 임계를 두면 "각각은 통과하는데 합계는 초과"가 두 줄 모두 green으로 빠져나가기 때문입니다. 전역 파일은 프로젝트 밖(사용자 소유)이라 크기만 보고하고 조치는 지시하지 않으며, 없거나 읽을 수 없으면 조용히 건너뜁니다 — CI·컨테이너·새 머신에서 흔한 정상 상태입니다.

1. 하루의 루프 — task 하나가 열리고 닫히는 길

0.13부터 task를 만들면 stdout이 다음 칸을 알려 줍니다 — 아래 아홉 번째 칸(ship)만은 예외로, PR/MR을 여는 경우에만 밟는 선택 단계라 CLI 안내에 들어 있지 않습니다.

실제 출력 — task는 다음 칸을 알려준다

$ /harness-task auth-refresh
created: docs/chad/auth-refresh/
active: chad/auth-refresh
next: /harness-spec으로 docs/chad/auth-refresh/auth-refresh-spec.md 초안 생성 (또는 직접 작성, Ambiguity 자가진단 포함)
next: /harness-interview → 구현 → 테스트 (/harness-unittest 계열) → 리뷰 → /harness-retro → done

같은 이름으로 다시 부르면 생성이 아니라 활성화이고, 이때는 next: 현재 단계는 …-plan.md 에서 확인이 나옵니다. 즉 task 전환도 같은 한 줄로 합니다.

📐
신규 생성 직후 한 번 물어봅니다 — 다이어그램 옵트인 (0.17.0)

"이 task의 spec/plan 단계에서 다이어그램도 함께 만들까요?" 신규 생성 때만 1회 묻고, 기존 task를 다시 활성화할 때는 묻지 않습니다. "예"면 plan.md에 - [ ] spec/plan 다이어그램 작성 → …-diagram.html 단계가 추가됩니다 — plan에 그 단계가 있는지가 곧 상태이고, 전용 설정 키나 상태 파일은 없습니다.

그 단계를 실제로 실행하는 것은 /harness-diagram입니다 0.17.0 — 다이어그램을 직접 그리는 명령이 아니라, diagram-design 같은 외부 스킬을 부르되 그 앞뒤에 하네스 규약(산출물 경로 · 자립형 inline SVG · artifact 기록)을 주입하는 어댑터입니다. 상류 스킬을 직접 부르면 이 규약이 하나도 적용되지 않습니다. plan에 그 단계가 없는 task에 쓰려면 --force를 붙입니다.

산출물 <name>-diagram.html은 SSOT 4파일이 아니며, 옵트인이므로 없는 task가 정상입니다. 도구(diagram-design 같은 외부 플러그인)가 없는 머신이면 task를 실패시키지 말고 그 단계를 지우지 말고 - [x] … — 미실행(도구 없음)으로 닫은 뒤 artifact에 한 줄 남깁니다. 지우면 옵트인 사실이 사라지고, 열어 두면 done이 막힙니다.

🚫
/harness-task new feature auth-refresh 같은 형태는 쓰지 마세요

커맨드는 인수를 그대로 CLI에 넘기고, CLI는 첫 번째 위치 인수만 task 이름으로 씁니다. 실제로 실행해 보면 docs/<user>/new/가 만들어지고 new-spec.md·new-plan.md가 생깁니다. 올바른 형태는 /harness-task <name> 하나뿐이고, 이름은 ^[\w.-]+$(영숫자·_·.·-)만 허용합니다. feature/fix 구분이 필요하면 이름에 넣으세요 — fix-token-race.

생성되는 파일 6개 — 4개는 SSOT, 1개는 캐시, 1개는 기계 상태

파일성격무엇을 쓰나
<name>-spec.mdSSOT요구사항·설계·Ontology·Ambiguity 자가진단 (+ 필요 시 결정·Boundary contracts)
<name>-plan.mdSSOT단계별 체크리스트 + Ontology 변경 로그
<name>-handoff.mdSSOT세션 인수인계 — post-commit 훅이 자동 append
<name>-artifact.mdSSOT결과 · ## Reviews · ## Learnings
<name>-context.md비-SSOT 캐시지금 필요한 working set만 (Task Context Card, §5 참고)
<name>-meta.json비-SSOT 기계 상태 0.16.0created·status·closedAt, 그리고 firstActivatedAt(다음 릴리스). harness가 소유하므로 손으로 고치지 않습니다 — 특히 firstActivatedAt은 done 가드가 증거를 찾는 판정 창의 시작점이라 이 값을 밀면 가드가 오탐을 냅니다

영속 요구사항·결정은 spec/plan에, 결과·학습은 artifact에 씁니다. Context Card에 쓴 것은 언제든 버려도 되는 것이어야 합니다 — 이 구분이 흐려지면 재개할 때 무엇이 진실인지 알 수 없게 됩니다.

🧾
원장 2개는 이제 생성물입니다 (0.16.0)

docs/task_summary.md와 docs/<user>/<user>-task.md는 task·done이 더 이상 쓰지 않습니다. task 디렉터리(위 meta.json 포함)를 스캔해 harness-team summary가 렌더합니다. 그래서 브랜치를 병렬로 둬도 이 두 파일에서 충돌하지 않습니다 — 예전에는 모든 브랜치가 같은 줄을 고쳐 병합마다 충돌했습니다.

# 인자 없이 = stdout으로 미리보기 · --check = 검사만 · --write = 실제 갱신
harness-team summary --write   # 기본 브랜치에서만 허용된다 (피처 브랜치에서는 거부)

2. 프롬프팅 — 어느 단계에서 무슨 말을 하면 무엇이 발동되나

프롬프트를 길게 쓰는 게 아니라, 이미 문서에 있는 것을 가리키게 쓰는 것이 요령입니다.

단계프롬프트 예발동되는 것
시작/harness-task auth-refresh + 요구사항 2~3문장CLI가 파일 6개 + 활성 포인터 + 다음 단계 두 줄을 출력하고, 이어서 커맨드가 다이어그램 옵트인을 1회 묻습니다(질문은 CLI stdout이 아니라 커맨드 절차입니다)
spec 초안/harness-spec 0.18.0Confluence(PRD·정책) · Figma(와이어프레임) · task 이름 기반 인터뷰 3소스에서 초안 생성. 소스 접근은 MCP 우선 + 수동 붙여넣기 폴백이고, 원문 덤프 대신 요약 + 출처 링크만 남깁니다
spec 검증/harness-interview소크라테스식 질문으로 숨은 가정 노출 — 통과 근거를 spec ## Ontology에 한 줄. writer(/harness-spec)와 validator를 나눈 것이 핵심입니다
plan 다듬기/harness-contrarian → /harness-simplifier가정 반박 → 단계·추상화 축소. 첫 토큰에 엔진(codex·claude·custom)을 주면 별도 컨텍스트의 read-only 검증자가 D6 루브릭으로 채점합니다 0.20.0
구현"plan §1부터 진행해줘"boundary check(선언 시) + 체크박스 갱신
테스트/harness-unittest · UI면 /harness-comptest · 프로세스 경계면 /harness-inttest스택 감지 → GWT 강제 → 위험 기반 커버리지 → 뮤테이션 자가점검
리뷰/harness-review (설계·가정을 때리려면 /harness-adversarial-review) 0.17.0엔진 중립 — codex·claude·custom을 인수로 고르고, 인수가 없으면 codex → claude 순으로 탐지합니다. artifact ## Reviews에 기록 + 기계 판독용 마커 한 줄

규칙 4개

① plan의 § 번호로 지시한다

"§2 해줘"면 충분합니다. 요구사항을 프롬프트에 다시 쓰지 않는 것이 핵심 — SSOT가 spec/plan에 있으므로 프롬프트는 포인터가 됩니다. 재개 세션도 같습니다: SessionStart 훅이 Context Card를 주입하므로 "이어서 해줘"로 충분합니다.

② 리뷰는 커맨드로 부른다

0.14부터 외부 리뷰 절차는 하네스가 소유하고, 0.17.0부터 이름이 엔진 중립입니다: /harness-review·/harness-adversarial-review. 옛 이름 /harness-codex-review·/harness-codex-adversarial-review는 deprecated alias였고 이제 제거됐으므로, 문서·브리프에 박아 뒀다면 바꾸세요.

openai-codex 플러그인의 /codex:review류는 disable-model-invocation이라 모델이 호출할 수 없습니다 — 터미널에서 사람이 직접 칠 때만 동작합니다.

③ Workflow·loop는 명시적 단어가 필요하다

다중 에이전트 fan-out은 옵트인이라 에이전트가 임의로 돌리지 않습니다. 원하면 이렇게: "이 변경을 워크플로우로 리뷰해줘 — 정확성·엣지케이스·보안 3차원으로 fan-out하고 검증 통과분만 artifact ## Reviews에 기록". 반복 감시는 /loop 30m /harness-doctor, PR 후 "/loop 10m CI 확인하고 실패하면 고쳐줘".

④ 병렬은 읽기에만 (D4)

"병렬로 조사해줘 / 리뷰해줘"는 됩니다. "병렬로 고쳐줘"는 안 됩니다. 쓰기는 항상 메인 세션 단일 스레드입니다 — 근거는 §6.

3. spec.md — 재작업의 원인은 코딩 실력이 아니라 입력 모호성이다

scaffold가 섹션을 미리 만들어 줍니다(taskSpecTemplate). 채우는 방법만 정하면 됩니다.

## 목적 / 요구사항     ← 직접 작성. 외부 문서를 가리키는 껍데기 금지
## 설계 / 접근
## Ontology            ← "X가 정확히 뭔가" 한 줄 정의 + 게이트 통과 근거
## Ambiguity 자가진단   ← Goal 40% / Constraint 30% / Success 30% / Context(brownfield) / 가중합 ≥ 0.8
## Done evidence       ← 주석으로 자리만 있다. 벗기면 done 가드가 읽는다 (0.18.1)
## 참고

# 필요할 때 추가
## 결정                 ← D1, D2… 근거 + "재고 지점"(재검토를 트리거하는 조건)
## Boundary contracts   ← 생산자/소비자 JSON Schema — plan 체크 직전 자동 대조

## Done evidence — 종결의 증거 기준을 task마다 선언한다 0.18.1

템플릿에는 주석 처리된 자리만 있습니다. 주석을 벗기면 done 가드가 이 선언을 읽습니다.

## Done evidence
```json
{ "version": 1, "tests": "required", "review": "optional", "verify": "optional" }
```

```json 코드펜스는 생략할 수 없습니다 — 펜스 없이 JSON만 두면 선언이 인식되지 않아 조용히 기본값으로 남고, 펜스를 열고 닫지 않으면 invalid로 차단됩니다.

  • tests — required(기본): task 기간에 소스가 바뀌었는데 테스트 파일이 안 바뀌면 차단합니다. 문서·설정만 바뀐 task에는 발동하지 않습니다. 정말 테스트가 불필요하면 "skip"을 선언하세요 — 무시가 아니라 선언입니다.
  • review — optional(기본) / required: required면 artifact에 이 task 기간의 리뷰 마커가 있어야 닫힙니다. 마커는 /harness-review가 기록 단계에서 남기는 <!-- harness:review kind=… at=… --> 한 줄이며, kind는 대조하지 않습니다.
  • verify 0.20.0 — optional(기본) / required: required면 검증 프레이밍 마커만 증거로 셉니다. kind가 -adversarial · -testcritic · -shipcheck · -contrarian · -simplifier로 끝나는 마커, 즉 별도 컨텍스트의 검증자가 반박을 시도한 기록입니다(D6). 검증 마커는 review 증거를 겸하지만 역은 성립하지 않습니다 — 일반 리뷰를 아무리 돌려도 verify: required는 닫히지 않습니다.
  • 선언이 깨져 있으면 그 자체로 차단됩니다 — JSON 오류·미종결 코드펜스·미지 키. 조용히 기본값으로 폴백하지 않는 것이 의도입니다(boundary check의 not-configured와 같은 원칙).
  • 가드는 마커의 존재·kind·시각만 읽습니다. finding 내용이 타당한지는 결정론 게이트 밖이며, 검증자의 반박을 재현·판별하는 것은 작성 세션의 몫입니다(D6 — 자동 수정 루프 금지). 판정 기준은 루브릭 평가 가이드가 정본입니다.
🚪
Ambiguity 게이트 — 3개 이상 미체크면 코드 금지

이건 문서 장식이 아니라 진입 조건입니다. 미달이면 /harness-interview로 돌아가 모호성을 제거하고, 통과한 근거를 ## Ontology에 한 줄 남깁니다. 작은 버그 수정에는 생략해도 됩니다.

doctor는 활성 task의 spec에 ## Ambiguity 자가진단 섹션이 있는지를 검사합니다(checkActiveSpecGate). 섹션이 없으면 "게이트 우회 — 포인터 껍데기 spec 의심" 경고와 함께 harness-team task <name>로 제대로 만들라고 안내합니다. 즉 spec을 손으로 만들어 게이트를 건너뛰는 경로가 감지됩니다.

## 결정은 D-포맷으로

기각·채택에 근거와 재고 조건을 함께 적어 두면, 나중에 "그 결정이 아직 유효한가"를 조건 대조만으로 판정할 수 있습니다. docs/decisions.md의 D2·D4가 이 포맷의 실제 예입니다.

## 결정
D1 (2026-08-10): 토큰 갱신을 인터셉터에 두지 않고 전용 큐로 처리한다.
  근거: 동시 401이 N개면 인터셉터 방식은 refresh를 N번 호출한다.
  재고 지점: 서버가 refresh 멱등성을 보장하기 시작하면 재검토.

## Boundary contracts — 한쪽 명세만 봐서는 못 잡는 불일치

응답 래핑, camelCase/snake_case, 필드명처럼 생산자와 소비자를 함께 봐야 하는 불일치는 spec에 선언합니다. 선언이 있으면 Claude가 plan 체크박스를 완료로 바꾸기 직전에 훅이 harness-team boundary check를 실행합니다. LLM 판단이 아니라 로컬 JSON Schema를 읽는 결정론적 CLI입니다.

{
  "version": 1,
  "boundaries": [
    {
      "id": "user-response",
      "producer": { "path": "contracts/server-user.json", "pointer": "/data" },
      "consumer": { "path": "contracts/web-user.json" }
    }
  ]
}

V1은 object schema의 properties·required·기본 type만 비교합니다. consumer가 필수로 읽는 필드가 producer에 없거나 producer가 required로 보장하지 않으면 실패합니다. 선언이 없으면 이렇게 통과합니다:

$ harness-team boundary check
boundary: not-configured

4. plan.md — 체크박스에 "깨뜨렸을 때 실패하는가"를 쓴다

plan은 할 일 목록이 아니라 검증 계약입니다. 각 항목은 통과 조건이 아니라 실패 조건으로 적을 때 쓸모가 생깁니다.

## 목표
(한 문장)

## 단계
### §1 추출 (동작 불변)
- [ ] hookCliInstall 모듈 스코프 추출 — 검증: 전후 출력 바이트 동일(diff)

### §2 회귀 테스트
- [ ] 금지 문자열 어써션 — 검증: README에 금지 형태를 넣으면 fail 1이 나는가

### §3 종결                ← 항상 마지막 §로 고정
- [ ] npm test 전체 통과
- [ ] 리뷰 실행 + artifact ## Reviews 기록
- [ ] artifact ## 결과 작성 → 커밋 → done

## Ontology 변경 로그       ← 개념이 새로 정의/변경되면 한 줄. spec Ontology 갱신 트리거
- (none)

좋은 검증 기준

  • "금지 형태를 넣으면 fail 1이 나는가" — 뮤테이션으로 확인 가능
  • "전후 출력 바이트 동일(diff)" — 기계가 판정
  • "401 동시 3개에서 refresh 호출이 1회인가" — 관측 가능

쓸모 없는 검증 기준

  • "정상 동작 확인" — 무엇을 보면 실패인지 없음
  • "테스트 추가" — 통과만 확인하는 테스트는 같은 결함을 다시 놓친다
  • "리팩토링 완료" — 완료의 정의가 없음

모든 박스가 - [x]가 되고 미완이 없어지면, commit 시 post-commit 훅이 PLAN_COMPLETE를 내보냅니다 — 종결 대화를 시작하라는 신호입니다.

5. Task Context Card — 재개 비용을 낮추는 작은 작업판

<name>-context.md는 SSOT가 아닙니다. spec·plan·handoff·artifact에서 파생된 현재 working set만 담는 캐시이자 workpad입니다.

예산이 정해져 있다

UTF-8 6 KiB 이하, 비공백 100행 이하, 미해결 failure capsule 최대 3개. 넘으면 context check가 잡습니다.

섹션 구성

## Now(목표·현재 atomic step·중단 조건) · ## Constraints and settled decisions · ## JIT retrieval map · ## Failure capsules · ## Resume checklist.

넣지 말 것

raw stderr, 토큰·비밀값, 전체 HTTP payload. 안전한 요약과 원문 위치만 남깁니다.

언제 갱신하나

  • task 생성 직후 / 세션을 넘기기 전
  • plan의 atomic step이 바뀔 때
  • 재현 가능한 실패가 생기거나 해소될 때

반복되는 상세 이력은 지우고, 가치 있는 학습은 artifact로 옮깁니다. 하네스는 검사만 합니다 — 자동 요약·삭제·LLM 편집을 하지 않으므로 갱신은 에이전트(당신 세션)의 일입니다.

$ harness-team context check
context: valid
path: docs/chad/auth-refresh/auth-refresh-context.md
bytes: 489/6144
nonblank-lines: 22/100
unresolved-failure-capsules: 0/3

세션 재개 — 훅이 카드를 먼저 밀어 넣는다

SessionStart 훅이 harness-team session-context를 호출합니다. 활성 task가 있으면 breadcrumb 다음에 유효한 카드를 그대로 주입하고, 카드가 없으면 context init, 읽을 수 없거나 유효하지 않으면 원문 대신 context check 안내만 냅니다.

$ harness-team session-context
[harness] 활성 task: chad/auth-refresh — 세션 시작 프로토콜대로 auth-refresh-plan.md 확인.
# auth-refresh — Context Card
## Now
- Goal: …

활성 task가 없으면 첫 작업 프롬프트에서 재개 / 새 task / task 없이 진행을 묻습니다. block이 아니라 nudge이므로 "task 없이 진행"도 선택지입니다 — 다만 그 선택을 의식적으로 하게 만드는 것이 목적입니다. 0.23.0에서 바뀐 것은 이 3택이 아니라 재개 후보 목록의 길이입니다 — 미완 task는 최근 활동순(plan.md mtime)으로 최대 8개만 나열되고 나머지는 … 외 N개 한 줄로 접힙니다. 접힌 것까지 전부 보려면 harness-team list를 쓰세요.

6. LLM으로 개발하기 — 하네스가 전제하는 협업 규율

여기까지가 "무엇을 쓰나"였고, 여기부터가 "LLM과 어떻게 굴리나"입니다. 아래 6개는 하네스의 문서 구조가 존재하는 이유이기도 합니다.

6-1. 쓰기는 단일 스레드, 읽기는 병렬 (D4)

서브에이전트의 값은 "일을 나눠서 빨리"가 아니라 메인 컨텍스트 윈도우를 더럽히지 않고 조사하는 데 있습니다. 서브에이전트당 조사 태스크는 하나로 좁히고, 결론만 받으세요.

6-2. JIT retrieval — 디렉터리를 덤프하지 않는다

  1. Context Card의 Current atomic step과 JIT retrieval map을 먼저 읽는다.
  2. 단서가 있으면 식별자를 Grep → 해당 모듈만 좁은 Glob → 매치한 파일만 Read.
  3. 단서가 없을 때만 현재 step에 맞춘 최소 검색으로 map을 채운다.
  4. 디렉터리 전체 덤프·무차별 파일 열기·원문 로그 복사는 금지.
  5. map에는 재개 비용을 낮추는 단서만 남기고 오래된 경로는 제거한다.

컨텍스트는 무한 자원이 아닙니다. "다 읽어서 안전하게"는 실제로는 덜 정확하게입니다 — 관련 없는 파일이 판단을 흐립니다.

6-3. 게이트 3개로 폭주를 막는다

게이트언제걸렸을 때
Ambiguity (입력)task 생성 직후, 구현 직전 1회자가진단 3개 이상 미체크 → 코드 금지, /harness-interview 복귀
복잡도 (범위)아키텍처 결정 · 보안 · 동시성 · 영향 파일 5개 이상멈추고 알린다 → 플랜 모드 · 서브에이전트 분할 · 페르소나 호출, 필요하면 상위 모델/effort 권유
완료 전 검증 (출력)완료 보고 직전동작을 증명하지 않으면 완료가 아니다 — 테스트 실행·로그·main과의 동작 차이 대조

막혔을 때 페르소나 호출 순서는 입력 → 가정 → 규모입니다: /harness-interview(스펙이 모호한가) → /harness-contrarian(가정이 옳은가) → /harness-simplifier(더 적게 만들 수 있는가). 작은 버그·문서 수정에는 호출하지 않습니다.

0.20.0부터 뒤 둘은 외부 검증자 모드를 갖습니다 — 첫 토큰이 엔진 이름이면(/harness-contrarian codex) 반론·제거 후보를 별도 컨텍스트의 read-only 검증자가 D6 finding 스키마로 채점합니다. 문서를 쓴 세션이 스스로 반박하면 sunk-cost 편향이 비평을 무디게 하기 때문입니다. 절차·엔진 표는 아래 6-4의 /harness-review와 같고, 대상만 diff가 아니라 task 문서입니다(scope=task-docs). /harness-interview는 외부 엔진을 쓰지 않습니다 — 문답은 여전히 당신과의 대화이고, 대신 질문 전에 spec 텍스트 증거만으로 선행 채점합니다(증거 없는 통과는 pass가 아니라 na).

6-4. 리뷰어는 작성자와 분리한다

같은 세션이 자기 코드를 리뷰하면 자기 가정을 재확인할 뿐입니다. 그래서 리뷰는 별도 프로세스·별도 컨텍스트로 나갑니다. /harness-review는 dirty면 working tree, clean이면 base 대비 브랜치 diff를 대상으로 삼고, base를 안 주면 origin/main → main으로 물러납니다. 설계 자체를 때리려면 /harness-adversarial-review를 씁니다.

엔진실행분리 수준
codexcodex exec --sandbox read-only벤더 분리 + 컨텍스트 분리
claudeclaude -p --permission-mode plan컨텍스트 분리만 — 같은 모델의 맹점은 공유합니다. codex를 쓸 수 없는 머신의 경로라 탐지 체인에서 마지막입니다
custom.harness/reviewers.json의 커맨드 템플릿설정하기 나름. 명시 호출 전용이라 자동 탐지 체인에 들어가지 않습니다

엔진 인수를 주지 않으면 command -v로 codex → claude 순서로 탐지합니다. claude는 Claude Code 환경에 항상 있으므로 어느 머신에서든 리뷰어가 하나는 보장됩니다.

📝

기록 없는 리뷰는 안 한 리뷰입니다. 요약·발견·조치를 활성 task의 artifact ## Reviews에 날짜·실행 엔진과 함께 남기세요. 폴백으로 엔진이 내려갔다면 건너뛴 엔진과 사유도 적습니다.

0.18.1부터 기록 끝에 기계 판독용 마커를 한 줄 붙입니다 — <!-- harness:review kind=<engine> scope=<worktree|diff> tip=<sha> at=<ISO8601> -->. spec이 review: required인 task는 done이 이 마커를 찾습니다. 즉 "기록 없는 리뷰는 안 한 리뷰"가 규범에서 가드가 됐습니다.

0.20.0부터 kind에 프레이밍 접미사를 붙입니다 — kind=codex-adversarial처럼 <engine>-<프레이밍> 형태이고, 프레이밍은 -adversarial · -testcritic · -shipcheck · -contrarian · -simplifier 다섯입니다. spec이 verify: required면 done이 이 접미사로 끝나는 마커만 증거로 셉니다(§8 일곱 번째 가드). 열거의 정본은 commands/harness-review.md이며 src 상수와 pin 테스트로 묶여 있습니다.

리뷰 지적을 그대로 받아들이지도 마세요. 지적 하나하나를 코드에 대조해 진짜 결함과 오탐을 가른 뒤 조치를 적습니다 — 0.14 릴리스가 실제로 그렇게 네 건을 갈랐습니다.

6-5. 통과가 아니라 실패로 검증한다

테스트의 기준을 "통과하는가"가 아니라 "의도적으로 깨뜨렸을 때 실패하는가"로 잡습니다. 0.13이 고친 설치 안내 결함이 통과했던 이유가 바로 이것이었습니다 — 검증이 문서를 읽어서 확인하고 실행하지 않았습니다. 테스트를 쓴 뒤 대상 코드를 한 줄 망가뜨려 보고, 정말 빨간불이 켜지는지 확인하세요.

6-6. 교정받은 것은 반드시 문서로 되돌린다

같은 실수를 반복하지 않는 유일한 방법은 교정을 텍스트로 고정하는 것입니다. 사용자에게 교정받으면 /harness-retro로 artifact ## Learnings에 패턴을 남기고, 반복될 성질이면 규칙(AGENTS.md·.claude/rules/*.md)으로 올립니다. 세션 기억은 다음 세션에 존재하지 않습니다.

$ harness-team retro "spec 포인터 껍데기 금지 — 자가진단이 없으면 doctor가 경고"
✓ retro: docs/chad/auth-refresh/auth-refresh-artifact.md 에 ## Learnings (2026-08-10) 추가

Codex는 예외입니다 — SessionStart 훅이 생겼습니다 (0.15.0)

init이 .codex/hooks.json을 함께 설치합니다. Claude 쪽과 동일하게 harness-team session-context를 불러 Codex 세션도 활성 task의 Context Card를 주입받습니다. 그래서 "훅은 Claude Code 전용"은 더 이상 정확하지 않습니다 — 정확한 표현은 "훅 표면의 넓이가 다르다"입니다(Claude는 위 표의 전 시점, Codex는 SessionStart 하나).

Codex는 훅 파일을 신뢰 등록해야 실행합니다(~/.codex/config.toml의 [hooks.state]에 해시로 기록). init 이후 첫 Codex 세션에서 승인하세요. 훅 파일을 고치면 해시가 바뀌어 다시 승인이 필요합니다. doctor는 .codex/hooks.json이 있는데 harness SessionStart 훅이 없는 상태를 잡아 줍니다.

8. 종결 — 가드 7종 + 선언 유효성을 통과해야 닫힌다

done은 먼저 검사입니다 — 통과하지 못하면 아무것도 바꾸지 않고 멈춥니다. 통과한 뒤에야 상태를 옮깁니다(handoff append · meta.json status/closedAt · 활성 포인터 비우기).

$ harness-team done
✗ done: 종결 가드에 걸림 (5개)
cause: plan.md에 미완 체크박스(`- [ ]`)가 남아 있음
cause: artifact.md가 템플릿 그대로임 (내용 없음)
cause: 커밋되지 않은 변경이 있음
cause: task 활성화 이후 커밋이 0개임
cause: 소스는 바뀌었는데 테스트 파일 변경이 없음 (테스트 미작성 — 불필요하면 spec에 `"tests": "skip"` 선언)
retry: 위 항목을 해소한 뒤 다시 `harness-team done` 실행
alternatives: `harness-team done --force` 로 가드를 무시하고 종결한다 — 무시한 사유를 artifact.md 에 남길 것
default: task는 활성으로 남고 handoff·artifact 어느 파일도 바뀌지 않는다
stop: 가드가 지적한 증거가 실제로 없으면 종결하지 말 것

0.18.1에서 증거 기반 가드 2종(테스트·리뷰 마커)이, 0.20.0에서 검증 마커 1종이 붙어 총 7종이 됐습니다. 위 출력에는 다섯 번째(테스트)가 보이고, 여섯·일곱 번째는 spec이 각각 review: required · verify: required를 선언한 task에서만 나옵니다. 여기에 선언 유효성이 따로 붙습니다 — ## Done evidence가 깨져 있으면 그 자체로 차단되므로, 가드 7종과 나란히 세는 항목이 아니라 7종을 읽기 전에 걸리는 관문입니다.

증거를 찾는 판정 창의 시작점은 <name>-meta.json의 firstActivatedAt입니다 0.19.0. 이 값은 생성 시 한 번만 기록되고 재활성화가 건드리지 않습니다 — 예전에는 active.json의 switchedAt을 썼는데, 끝난 task를 닫으려면 재활성화해야 하고 그 재활성화가 창을 초기화해 이미 만족된 리뷰 마커·커밋을 창 밖으로 밀어냈습니다. 손으로 고치지 마세요. 이 값을 밀면 가드가 오탐을 냅니다.

cause해소 방법
미완 체크박스실제로 끝냈으면 - [x]로. 안 할 항목이면 지우고 이유를 artifact에 — 체크로 위장하지 않는다.
artifact가 템플릿 그대로## 결과를 쓰고, 리뷰했다면 ## Reviews, 배운 게 있으면 /harness-retro.
커밋되지 않은 변경커밋하거나 되돌린다. 훅이 만드는 handoff 2개는 가드에서 제외되므로 그것만 dirty면 통과한다.
활성화 이후 커밋 0개작업이 정말 없었다면 task 자체가 필요했는지 되묻는다.
소스 변경 O + 테스트 변경 X 0.18.1테스트를 쓴다. 정말 불필요한 task(문서·설정 전용은 애초에 발동하지 않는다)면 spec ## Done evidence에 "tests": "skip"을 선언한다 — 선언하지 않고 --force로 넘기지 않는다.
리뷰 마커 없음 0.18.1spec이 review: required일 때만 나온다. /harness-review를 돌리고 결과와 마커를 ## Reviews에 남긴다 — 리뷰를 하고도 기록하지 않으면 여기서 막힌다.
검증 마커 없음 0.20.0spec이 verify: required일 때만 나온다. 일반 리뷰로는 풀리지 않는다 — 검증 프레이밍(/harness-adversarial-review · 엔진 인수를 준 /harness-contrarian·/harness-simplifier · 테스트 3형제의 testcritic 인계 · ship의 정합 검증)을 돌리고 그 마커를 남긴다.
## Done evidence 선언이 올바르지 않음 0.18.1JSON 오류·미종결 코드펜스·미지 키. 고치거나, 선언 자체를 지워 기본값(tests: required / review·verify: optional)으로 돌아간다.
🩹

--force는 가드를 경고로 낮춥니다. 쓸 수는 있지만, 왜 우회했는지 artifact에 남기지 않으면 그 task는 다음 사람에게 "닫혔지만 알 수 없는" 상태가 됩니다.

닫히면 <name>-handoff.md에 완료 줄이 append되고, <name>-meta.json이 status: "done"·closedAt으로 바뀌고, 활성 포인터가 비워집니다. 다음 task는 다시 /harness-task <name> 한 줄로 시작합니다.

🧾

0.16.0부터 done은 원장을 갱신하지 않습니다. 예전에는 여기서 <user>-task.md의 ## Completed와 docs/task_summary.md를 직접 고쳤지만, 그것이 모든 병렬 브랜치가 같은 줄에서 충돌하던 원인이었습니다. 지금 원장은 meta.json을 스캔해 렌더하는 생성물입니다 — 병합 후 기본 브랜치에서 harness-team summary --write를 한 번 돌리면 됩니다.

9. 자주 밟는 함정

대부분 "규칙을 몰라서"가 아니라 "규칙이 자동일 거라고 믿어서" 생깁니다.

증상원인조치
/harness-* 커맨드가 안 보인다플러그인 설치 채널이 미완 (프로젝트 init은 커맨드를 복사하지 않는다)내 Claude Code에 /plugin install
훅이 조용히 아무 일도 안 한다전역 harness-team CLI가 PATH에 없다harness-team doctor → 안내대로 재링크
docs/<user>/new/가 생겼다/harness-task new feature X 형태로 호출디렉터리 삭제 후 /harness-task <name>로 재생성
spec이 외부 문서만 가리킨다포인터 껍데기 spec — 자가진단·Ontology가 없다요구사항·자가진단·Ontology는 spec에 직접. 외부 문서는 보조 참조로만 (doctor가 경고)
재개할 때마다 처음부터 다시 읽는다Context Card를 갱신하지 않았다세션 넘기기 전 ## Now·JIT retrieval map 갱신 → context check
Context Card가 계속 커진다이력·로그를 append만 했다상세 이력 제거, 가치 있는 학습은 artifact로 이동 (6 KiB·100행·capsule 3)
리뷰했는데 흔적이 없다결과를 artifact에 남기지 않았다## Reviews에 날짜·요약·발견·조치 + 마커 한 줄 — 없으면 안 한 것이고, spec이 review: required면 done도 막힌다
병합했는데 task_summary.md가 그대로다0.16.0부터 원장은 생성물이라 task·done이 쓰지 않는다기본 브랜치에서 harness-team summary --write 실행 후 커밋
피처 브랜치에서 summary --write가 거부됐다가드가 기본 브랜치만 허용한다 — 의도된 동작거부가 맞다. --force로 뚫지 말고 기본 브랜치에서 돌린다
done이 "테스트 파일 변경이 없음"으로 막힌다0.18.1 테스트 증거 가드테스트를 쓰거나, 정말 불필요하면 spec ## Done evidence에 "tests": "skip" 선언
/harness-codex-review가 아무 반응이 없다0.17.0에서 /harness-review로 재편, 옛 이름 alias는 제거됐다문서·브리프의 커맨드 이름을 /harness-review로 바꾼다
