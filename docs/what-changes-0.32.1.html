손으로 복사한 리터럴 하나가
완료를 open으로 만들 수 있었습니다

0.32.1은 AI-Native SDLC 플레이북 비교에서 나온 마지막 권고 — "handoff 타입화(TCC와 중복 검토 선행)" — 의 구현입니다. 그 선행 조건이 이 릴리스의 절반을 결정했습니다: 중복 검토 결과 권고가 가리키던 것 대부분을 만들지 않기로 했습니다. TCC가 재개용 working set을 이미 소유하고 있었고, renderUserHandoff는 이미 바이트 테스트가 있었습니다. 남은 것은 소비자가 실재하는 계약 하나 — task handoff의 완료 마커뿐이었고, 거기서 실측 결함이 나왔습니다. 동작은 한 줄도 바뀌지 않습니다.

609개 테스트가 통과하는 동안 완료가 사라졌습니다

runDone이 쓰고 inferLegacyMeta가 읽는 완료 마커는 서로 다른 모듈에 손으로 복사한 리터럴 하나로만 묶여 있었습니다. 그 계약을 지키는 테스트는 없었습니다.

실측결과
생산자(task.mjs)의 em-dash를 하이픈으로 변경meta.json도 원장 행도 없는 레거시 task가 done → open으로 오분류
그 상태에서 전체 스위트609 tests / 608 pass / 0 fail — 아무도 잡지 못함
파서를 ISO 형태로 좁힘역시 아무 테스트도 실패하지 않음

도달 조건은 가정이 아닙니다. task/done은 원장을 건드리지 않고 기본 브랜치의 summary --write만 갱신하므로(AGENTS.md D5), 브랜치에서 종결됐고 원장이 아직 재생성되지 않은 레거시 task가 정확히 그 조합입니다. 재현 probe로 확인했습니다.

Changed

완료 마커가 단일 선언에서 나옵니다

변경
신규 src/handoff-marker.mjs가 renderDoneMarker(isoTs)·hasDoneMarker(content)·DONE_MARKER_RE를 소유합니다. runDone과 inferLegacyMeta가 그것을 씁니다.
왜
손으로 복사한 리터럴이 2개였고 둘을 잇는 테스트가 0개였습니다. 선언을 모으지 않으면 드리프트가 조용합니다 — 위 실측이 그 조용함의 크기입니다.
그래서
src 안의 손복사 리터럴이 2개 → 0개. append 바이트도 정규식도 그대로라 동작·파일 형식 변경은 없습니다.

권고가 가리킨 것 대부분을 만들지 않았습니다

원 권고는 한 줄이었고 네 갈래로 읽혔습니다. 선행 조건이던 TCC 중복 검토가 둘을 죽였고, 소비자 전수 조사가 셋째를 죽였습니다.

갈래판정근거
handoff 템플릿에 재개 구조를 준다기각 — 중복taskContextTemplate + validateContextCard가 재개용 working set을 6 KiB·100행·capsule 3개 한도의 결정론적 검사와 함께 이미 소유
post-commit 커밋 항목에 스키마를 준다기각 — 소비자 0## <ISO> — <sha> + diffstat을 파싱하는 코드가 전수 조사에서 하나도 없음
renderUserHandoff 계약 고정이미 충족바이트 모양·종결형/활성형 공유 포인터 테스트가 이미 존재
완료 마커를 타입화채택소비자가 실재하고, 실측 결함이 재현됨
"타입화"는 이 저장소에서 정적 타입을 뜻하지 않습니다. JS 저장소라 그 말이 모호해서, spec의 Ontology에 조작적 정의를 박았습니다 — 형식을 한 곳에 선언하고 생성·판독이 그 선언에서 나오게 하는 것이며, 판정 기준은 셋입니다: 손복사 리터럴이 0개인가, 생산자 단독 변경이 테스트를 깨는가, 호출부가 그 선언을 우회해도 테스트가 깨는가.

드리프트를 막는 것은 모듈이 아니라 테스트입니다

모듈로 모으기만 하면 렌더러와 정규식을 같이 바꿔 과거 파일을 못 읽게 만들 수 있고, 호출부가 helper를 우회하면 모듈 테스트는 전부 통과합니다. 네 방향을 각각 막습니다.

테스트막는 드리프트해당 뮤테이션에서

생산자 통합(runDone을 실제 실행해 append 바이트 대조)호출부가 helper를 우회1 fail

착수 전에는 위 네 뮤테이션 전부에서 0 fail이었습니다. 이 표가 이 릴리스의 실질입니다 — 모듈은 그 표를 쓸 수 있게 만든 수단입니다.

리뷰 범위의 한계를 밝힙니다. artifact에 남긴 리뷰 마커의 tip은 P2 반영 커밋 이전을 가리킵니다. 그 델타는 테스트 전용이며 양방향 뮤테이션으로 자체 검증했을 뿐, 리뷰어가 다시 보지는 않았습니다. tip을 새 sha로 고쳐 쓰면 하지 않은 리뷰를 주장하는 것이라 그대로 두었습니다.

배운 것 — 모듈 계약과 호출부 계약은 별개다

선언을 한 곳으로 모으면 계약이 지켜진다고 여기기 쉽습니다. 실제로는 모으는 것과 호출부가 그것을 쓰는 것이 서로 다른 계약이고, 각각 테스트가 필요합니다. Codex P2 2건이 정확히 그 자리였습니다 — 단위 테스트 8개가 전부 통과하는 동안 runDone과 inferLegacyMeta는 모듈을 버려도 됐습니다.

결함을 재현한 probe는 버리지 말고 테스트로 굳히세요. 소비자 통합 테스트는 착수 전 probe를 거의 그대로 옮긴 것입니다. probe를 임시 폴더에 두고 끝냈다면 P2를 막을 테스트를 새로 설계해야 했습니다. 덧붙여 — 뮤테이션 전에 baseline이 green인지 먼저 확인하세요. 소스 파일을 추가하면 docs/harness-overview.html이 소스와 어긋나 docs:check가 깨지는데, 그 무관한 실패를 뮤테이션의 결과로 오독할 뻔했습니다.
