리뷰를 돌리지 않고도
리뷰 증거를 쓸 수 있었습니다

0.37.0은 done 가드가 읽는 리뷰·검증 증거를 에이전트가 손으로 쓰는 마커에서 harness가 쓰는 기계 상태로 옮깁니다. 지금까지 harness-review.md 5단계는 에이전트에게 "마커 한 줄을 append 하라"고 지시했고, 가드는 그 줄만 읽었습니다 — 리뷰를 건너뛰고 마커만 쓰는 것이 정상 절차 안의 한 단계를 생략하는 지름길이었습니다. 새 명령 harness-team review가 엔진을 직접 돌리고, 성공(exit 0)한 실행만 <name>-meta.json의 reviews[]에 기록합니다. verify: required는 이제 그 배열을 읽습니다.

harness-team review — runner 표를 코드로, 증거를 meta로

엔진 runner 표(harness-review.md)는 정본 그대로이고 CLI가 그것을 구현합니다. 공용 리뷰 프롬프트는 문서의 text 블록이 정본이며 src 상수는 pin 테스트가 동기화합니다.

Added

review [codex|claude|custom] [--framing] [--prompt-file] [--scope] [--base]

실행
probe 폴백 체인(codex → claude), custom은 .harness/reviewers.json. codex는 stdin을 닫고(< /dev/null 계약), custom은 {prompt}를 POSIX 단일 인용 리터럴로 치환해 sh -c.
기록
exit 0일 때만 — meta reviews[] append + artifact ## Reviews 블록(출력 16 KiB 상한, 절단 표기) + 종전 형식 마커 한 줄(사람용·하위 호환). 실패는 아무것도 쓰지 않습니다.
Added

검증 프레이밍은 --framing으로

kind 조립
--framing adversarial → kind=<engine>-adversarial. 접미사가 VERIFY_KIND_SUFFIXES 열거 밖이면 실행 전에 거부 — verify 가드가 세지 않는 항목을 조용히 만들지 않습니다.
프레이밍 커맨드 7종
adversarial · unittest/inttest/comptest testcritic · ship shipcheck · contrarian · simplifier가 자기 프롬프트를 파일에 두고 --prompt-file로 넘깁니다. contrarian·simplifier는 --scope task-docs.
Changed

verify: required가 meta.reviews를 읽습니다

규칙
meta에 reviews 키가 있으면 verify는 그 배열만 셉니다 — 손으로 쓴 artifact 마커는 검증 증거가 아닙니다. review: required는 meta 항목·마커 어느 쪽이든 종전대로 인정합니다.
구 task
reviews 키가 없는 meta(이 릴리스 이전 task)는 종전 판정 그대로이고, CLI도 그 task에는 키를 만들지 않습니다 — artifact 마커만 남깁니다. 소급하지 않습니다.

바꾸지 않은 것

대상이 릴리스왜
가드의 위협 모델불변 — 망각·실수meta를 손으로 고치는 위조는 여전히 막지 않습니다. 바뀐 것은 증거를 만드는 코드 경로뿐입니다
리뷰 품질 판정불변 — 기계가 하지 않음기계화된 것은 "exit 0으로 실행됐고 출력이 있었다"까지입니다. 발견의 진위는 종전대로 4단계(세션·사람) 판별
엔진 runner 표·프롬프트불변문서가 정본, 코드는 그것을 구현. 프롬프트는 pin 테스트로 동기화
구 task의 종결 판정불변키 생성을 부수효과로 두면 첫 review 호출 순간 기존 손 마커가 무효화됩니다 — 적대적 리뷰 P1로 잡혀 수정
templates/불변소비자 설치 파일은 바뀌지 않습니다

적대적 리뷰 — 새 CLI로 자기 자신을 검증했습니다

이 릴리스의 task는 review·verify·tests를 전부 required로 선언했고, 새 명령으로 review claude --framing adversarial을 돌려 meta.reviews[0]에 기록된 항목으로 --force 없이 종결됐습니다. 검증 증거를 기계화하는 기능이 기계화된 증거로 닫힌 첫 사례입니다.

발견판별조치
P1 {prompt}가 템플릿 작성자의 따옴표 안(echo '{prompt}')이면 단일 인용 계약이 깨져 프롬프트가 셸 명령이 됨진짜 — PoC를 테스트로 재현{prompt}가 공백으로 둘러싸인 독립 토큰이 아니면 실행 전 거부
P1 구 task에 평범한 review 한 번이 reviews 키를 만들어 기존 손 마커 증거를 소급 무효화진짜 — spec의 "소급 금지"를 구현이 side-effect로 위반CLI는 키가 이미 있을 때만 meta에 씀. 구 task는 마커만
P2 실제 git 저장소에서 scope 판정 테스트 부재진짜dirty→worktree · clean→diff(base 폴백) · 빈 diff→미기록 · 없는 base→error 고정
P3 읽는 쪽이 exitCode를 안 봄진짜(방어)exitCode ≠ 0 항목은 증거가 아님
P2 동시 review 두 번의 meta read-modify-write 경합사실이나 범위 밖done·task 등 기존 meta 쓰기와 같은 D4(단일 스레드) 전제 — 문서에 명시

두 P1은 같은 모양이었습니다. spec이 이미 금지한 것을 구현이 부수효과로 어긴 경우 — spec의 제약을 "코드가 지키는가"가 아니라 "어떤 경로로 새는가"로 다시 읽어야 잡힙니다.
리뷰어가 못 한 것: 이 컨테이너에 codex가 없어 claude 엔진(컨텍스트 분리만, vendor 분리 없음)으로 돌렸습니다. codex 엔진 행은 문서 runner 표를 그대로 옮겼지만 실행은 미검증입니다.
