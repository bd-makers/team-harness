템플릿을 고쳐도
기존 설치에는 닿지 않았습니다

0.33.0은 배포 경로의 구멍을 메웁니다. copyStaticAssets가 정적 표면을 skipExisting으로 복사하는 탓에, templates/ 아래 파일을 고쳐도 이미 설치된 프로젝트에는 영영 도달하지 않았습니다. 판정이 파일 단위라 새로 추가된 파일은 도달하는데 수정된 파일만 막히는 비대칭이었고, 그래서 0.32.3까지 나간 new-feature Phase 3 규율이 기존 팀에 배달되지 않은 채였습니다. 적용 범위를 정적 템플릿 6개에서 13개로 넓히고, doctor가 낡은 설치본을 알려 주도록 했습니다.

소스를 읽어 짐작하지 않고, 샌드박스에서 재현했습니다

소비자 프로젝트를 만들어 init → 템플릿 수정 → init 재실행으로 실제 동작을 관찰했습니다. 결론은 소스 독해가 아니라 실행 결과입니다.

이 비대칭 자체를 테스트로 고정했습니다. 전제가 바뀌면 테스트가 먼저 깨집니다 — refresh 경로가 존재하는 이유가 이 비대칭이기 때문입니다.

정책은 이미 있었습니다 — 없던 것은 적용 범위입니다

migrate의 refreshClaudeHooks가 이미 provenance 기반 refresh를 구현하고 있었고, 주석이 스스로를 "the explicit opt-in delivery path"라고 부릅니다. 새 정책을 발명하는 대신 그 규칙을 넓혔습니다.

판정 규칙: 설치본의 바이트가 하네스가 실제로 배포한 적 있는 버전 (sha256 테이블)과 일치할 때만 갱신합니다. 그 외는 커스터마이즈로 보아 절대 덮지 않고 경고만 남깁니다. 갱신 경로는 harness-team migrate입니다 — init은 갱신 동사가 아닙니다.
