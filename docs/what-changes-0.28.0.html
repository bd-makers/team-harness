거부가 이제 다음 행동을 알려 줍니다
— escalation packet 5필드

0.28.0은 계약 하나를 넓힙니다. CLI가 무언가를 거부할 때 주던 정보는 root_cause·safe_retry·stop_condition 셋뿐이었습니다 — 왜 막혔고, 무엇을 고쳐 다시 하고, 언제 멈춰야 하는지. 그런데 소비자(에이전트든 사람이든)가 실제로 알아야 할 두 가지가 빠져 있었습니다: 지금 대신 취할 수 있는 다른 행동이 있는지, 그리고 아무것도 하지 않으면 무엇이 남는지. 2026-09-05 외부 6층 플레이북 비교 분석의 권고 ③입니다. 이제 --json 엔벨로프의 error는 5필드이고, 사람에게 넘길 때 쓰는 CLAUDE.md §5-A도 같은 목적의 패킷을 규정합니다.

무엇이 추가됐나 — 거부에 대안과 무행동의 결과를 싣는다

① 에이전트 행동 표면의 계약 확장이라 minor입니다(MAINTAINING.md 릴리스 크기 판단). 스키마는 harness/observation/v1 그대로입니다 — additive라 기존 3키를 읽던 소비자는 아무것도 고칠 필요가 없습니다.

Added

error.alternatives · error.safe_default

변경
--json 엔벨로프의 error가 { root_cause, safe_retry, alternatives, safe_default, stop_condition } 5필드가 됩니다. alternatives는 지금 대신 취할 수 있는 행동과 그 트레이드오프의 목록(없으면 빈 배열), safe_default는 아무 응답도 오지 않았을 때 남는 상태입니다(항상 비어 있지 않음). 값을 만드는 지점은 새 헬퍼 buildErrorPacket 하나이며, 필수 필드를 빠뜨리면 TypeError로 즉시 터집니다.
왜
PDF §V.A "Escalation Is Not Failure"의 패킷은 5항목입니다 — 결정 요청 · 권장안 · 시도한 대안 · 기다림의 비용 · 무응답 시 안전 기본값. 하네스는 셋만 갖고 있어서, 거부를 받은 에이전트가 다른 경로가 있는지도 포기하면 무엇이 남는지도 알 수 없었습니다. 그 둘이 없으면 escalation은 인계가 아니라 그냥 실패 통보입니다.
그래서
예를 들어 harness-team done이 가드에 걸리면 이제 alternatives가 "--force로 무시하되 사유를 artifact에 남겨라"를, safe_default가 "task는 활성으로 남고 어떤 파일도 바뀌지 않는다"를 함께 줍니다. 거부가 막다른 길이 아니라 선택지가 붙은 갈림길이 됩니다.
Changed

생산자 9곳이 공용 헬퍼를 경유한다

변경
에러 엔벨로프를 손으로 만들던 아홉 곳(summary · observe · rules promote · rules invalid-action · release의 ERROR_ADVICE 5종 · task bad-name · task retro no-active · doctor · done 가드)이 전부 buildErrorPacket/renderErrorPacket을 씁니다.
왜
필드를 하나 더하면 아홉 곳이 각자 빠뜨릴 수 있습니다. 강제 지점을 하나로 모으면 빠뜨린 생산자는 개발 시점에 터집니다 — 런타임에 조용히 undefined를 내보내는 대신.
그래서
회귀 방지 둘이 붙었습니다: src/commands/*.mjs에 리터럴 root_cause:가 있으면 실패하는 grep pin, 그리고 JSON을 내보내는 생산자 8곳에 typeof root_cause === 'string' 가드(배열 형태는 done 가드의 issue별 출력 전용입니다). 두 가드 모두 일부러 깨서 실패를 확인한 뒤 원복했습니다.

사람용 — CLAUDE.md §5-A가 1줄 권유를 그만둡니다

복잡도 게이트에 걸렸을 때 Claude가 사용자에게 넘기는 형식입니다. 스캐폴드 템플릿과 이 저장소의 사본이 함께 바뀝니다.

Changed

§5-A 복잡도 게이트 — 5항목 패킷

변경
"사용자에게 1줄 권유"가 결정 요청 · 권장안 · 시도한 대안 · 기다림의 비용 · 안전 기본값으로 바뀝니다. 모델·effort 전환 권유는 사라지지 않고 권장안 항목 안으로 들어갑니다.
왜
1줄 권유만 받은 사용자는 다른 선택지가 있었는지도 답하지 않으면 어떻게 되는지도 모른 채 정해야 했습니다. 결정을 넘기려면 결정에 필요한 것을 함께 넘겨야 합니다.
그래서
harness-team init을 다시 실행하면 프로젝트의 CLAUDE.md workflow 구획이 갱신됩니다. 마커 밖 사용자 텍스트는 건드리지 않습니다.
두 패킷은 항목이 하나씩 다릅니다. 기계용은 PDF의 "기다림의 비용" 자리에 stop_condition을 둡니다 — CLI가 거부하는 시점에 기다림의 비용은 언제나 "없음(파일 무변경)"이라 실을 값이 없기 때문입니다. alternatives도 기계용은 "지금 취할 수 있는 다른 행동"을 뜻합니다 — 거부 시점에는 시도 이력이라는 것이 존재하지 않습니다(검증이 실패했을 뿐 다른 경로를 실행해 본 적이 없습니다). 사람용 §5-A는 세션 안에서 실제로 검토·기각한 경로가 있으므로 PDF 원문대로 "시도한 대안"입니다.

코드 결함 4건은 전부 앞 세 회차에 나왔고 이후 세 회차는 문서·계획 정합만 냈습니다. 대표적인 지적 둘:

  • 보장하지 못하는 상태를 단정했다 — rules의 safe_default가 "규칙을 되돌렸고 artifact도 무변경"이라 했는데, 되돌리기 실패는 삼켜지고(unlink().catch(()=>{})) 파일 쓰기는 원자적이지 않습니다. 확인 가능한 범위로 고쳤습니다.
  • 범용 CLI가 프로젝트 관행을 처방했다 — summary의 브랜치 가드가 --force와 함께 main 직접 push를 권했습니다. 이 저장소의 원장 갱신 관행이 스캐폴드된 남의 프로젝트로 샐 뻔했습니다. escape hatch까지만 안내하고 반영 경로 처방은 지웠습니다.
#6의 READY에는 단서가 있습니다. 그 프롬프트에 판정 기준("문서가 저장소와 모순되는 것만 결함으로 본다")을 명시한 뒤 받은 판정이라, 무조건적 READY보다 약한 증거입니다. 다만 리뷰어가 프롬프트와 무관하게 대표 CLI 오류 경로 4개를 직접 실행해 5필드 출력을 확인했고, CI가 전체 테스트를 완주했습니다 — 리뷰어의 read-only 샌드박스는 6회 내내 mkdtemp EPERM으로 I/O 테스트를 돌리지 못했습니다.

배운 것 — 확인하지 않은 것을 확인한 것처럼 쓰지 않는다

검증 7회차 중 5회가 같은 뿌리의 실수를 잡았습니다. 네 가지 얼굴로 나타났습니다:

  1. 코드가 보장하지 못하는 상태를 단정 (unlink 실패가 삼켜지는데 "되돌렸다")
  2. 그걸 고치면서 같은 문장 안에서 자기모순 ("표기는 기록되지 않았다" + "일부만 쓰였을 수 있다")
  3. 세어 본 수를 전수로 서술 (타입 가드 "JSON 생산자 6곳" — 실제는 8곳)
  4. 존재를 확인하지 않은 파일·헬퍼 이름을 계획에 적고 그대로 "실행했다"고 기록

적용법은 간단합니다 — "전부"·"무변경"·"N곳"·"되돌렸다"를 쓰기 직전에, 그 문장을 거짓으로 만들 수 있는 경로를 한 번 찾습니다. 못 찾으면 쓰고, 찾으면 범위를 좁혀 씁니다. 파일·심볼 이름은 쓰기 전에 존재를 확인합니다.

부수적으로 얻은 것 하나: 정확 문자열 grep의 0건은 "없음"의 증거가 아닙니다. 낡은 출력 예시를 찾으려고 stop: 의도적으로로 훑어 "남은 표면 없음"이라 결론지었는데, 실제 파일은 stop: 뒤 공백이 2개라 0건이 나온 것이었습니다. 표면 전수 조사는 공백·구두점에 의존하지 않는 앵커로 훑고, 결과를 파일 존재·분류와 대조해야 합니다.
