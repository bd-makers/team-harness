1 · 개념 — 두 개의 검증 레이어
L4는 CLI 배관을, L5는 설치된 하네스를 측정한다. 둘은 겹치지 않는다.

L4 — CLI 배관 (빠름)

  • 무엇: tests/e2e/* + doctor --json
  • 휘발성 tmpdir에서 실제 bin/harness-team.mjs를 spawn해 기계적으로 검증
  • 플러그인 CLI 로직만 본다 (arg 파싱 · scaffold · 병합)
  • auth·에이전트 불필요, 초 단위로 끝남

L5 — agent-in-the-loop (이 가이드)

  • 무엇: tests/sim/agentloop.mjs
  • 실제 claude -p 세션을 띄워 그 사이드이펙트를 채점
  • 설치된 하네스(2번)를 측정하는 유일한 경로
  • auth · 권한 allowlist · 시간(~30–50분) 필요

왜 L5만 "설치된 하네스(2번)"를 측정할 수 있나

harness-init/apply/task가 소비자 프로젝트에 심는 것들 — 설치된 hook(SessionStart · post-commit), slash → CLI 체인, 트리거 — 은 cwd가 그 프로젝트인 세션에서만 발화한다. 한 세션 안에서 도는 스킬은 이 설치물의 발화를 구조적으로 관찰할 수 없다. 그래서 L5는 cwd=테스트프로젝트로 실제 에이전트 세션을 별도 프로세스로 띄워야만 "설치된 것이 진짜 켜지는가"를 볼 수 있다. 이것이 CLI sim(L4)이 도달 못 하는 "2번" 레이어다.

핵심 성과: CLI sim이 "⚠️ 수동확인"으로 미뤄두던 SessionStart nudge 주입을, L5는 transcript 증거로 ✅ PASS 자동 판정으로 전환했다. (실제 2번 측정 성공 — sim-agentloop-redesign-artifact.md)
2 · 아키텍처 — spawn → 사이드이펙트 → 채점
throwaway 샌드박스에서 실 에이전트를 띄우고, 산문이 아닌 관찰 가능한 상태 변화만 신호로 삼는다.
그림 1 · agentloop.mjs 채점 파이프라인 — spawn 한 세션당 사이드이펙트를 신호로 이진 판정

구성 요소

단계함수하는 일
샌드박스makeSandbox()../harness-playground/.sim-tmp/<TS>/<name>에 throwaway dir 생성. .bin/harness-team PATH shim(설치된 post-commit hook이 harness-team을 찾도록), git init + user.name=simbot, stack별 package.json.
세션 spawnrunHeadless()claude -p <prompt> --output-format json --allowedTools ...를 cwd=샌드박스로 실행. 토큰은 child env에만 주입(CLAUDE_CODE_OAUTH_TOKEN), CLAUDE_CODE_CHILD_SESSION·CLAUDECODE는 제거(중첩 세션 혼동 방지).
transcript 조회findTranscript()~/.claude/projects/<proj>/<session_id>.jsonl을 session_id로 글롭. SessionStart nudge 주입 여부를 여기서 확인.
채점sig() / manual()신호 = { label, status, note }. PASS/FAIL은 파일·git·transcript 상태로 이진 판정. 관찰 불가는 MANUAL. 에이전트 산문은 sanitizeNote()로 소독되며 신호가 되지 않는다.
스냅샷snapshot()rsync로 scaffold 산출물을 sim-snapshots/<version>/<scenario>/에 복사(.git·node_modules·.bin 제외). 버전 간 git diff용.
3 · 시나리오 — SC1 ~ SC5
SC1/SC2는 stack 매트릭스(node·next·react-native)로, SC3/4/5는 canonical(node) applied 프로젝트에서 1회.
✅ PASS — 증거 있음 ❌ FAIL — 신호 미검출 ⚠️ MANUAL — 헤드리스 관찰 불가

SC1 · init — 빈 dir에 하네스 scaffold

빈 dir + /harness-aijient-team:harness-init. 단, init은 기본이 대화형이라 헤드리스에서 멈춘다 → 프롬프트에 "NON-INTERACTIVELY, accept all defaults, pass --yes, 질문 금지"를 명시해 완주시킨다. 8개 신호:

  • agent run completed (auth/parse error 없음)
  • AGENTS.md + harness:section= 마커
  • CLAUDE.md의 @AGENTS.md import
  • GEMINI.md의 @AGENTS.md import
  • .claude/settings.json에 hooks 존재
  • .claude/rules 디렉토리 존재
  • AGENTS.md stack label = 기대값 (stack-discriminating)
  • doctor green (doctor --json status success, fail 0)

SC2 · apply — 기존 프로젝트에 비파괴 주입

기존 파일(README.md, src/index.js)이 있는 dir + harness-apply. apply는 헤드리스에서 그대로 완주한다. 6개 신호:

  • agent run completed
  • README.md 보존 (sha256 해시 불변)
  • src/index.js 보존 (해시 불변)
  • AGENTS.md 코어 주입됨
  • AGENTS.md stack label = 기대값
  • doctor green

SC3 · task — 4종 SSOT 생성

applied dir + harness-task sim-<TS>. member dir은 git user.name(=simbot). 5개 신호:

  • agent run completed
  • 4종 SSOT 생성 (spec·plan·handoff·artifact)
  • .harness/active.json이 task를 가리킴
  • spec에 Ambiguity 자가진단 섹션
  • spec에 Ontology 섹션

SC4 · 설치-hook 발화 — 본질적 "2번"

순서가 중요하다. post-commit을 먼저 돌린다 — active task가 살아 있을 때만 handoff가 갱신되기 때문. 그 다음 active.json을 null로 만들고 2번째 세션을 띄워 SessionStart nudge 주입을 확인한다.

  • ✅ post-commit handoff 갱신 (더미 커밋 후 mtime 전진, active task 존재 시)
  • ✅ SessionStart nudge 주입 — 2번째 세션 transcript에 "활성 task가 없습니다" 등장
  • ⚠️ PreToolUse protect-files 차단 — 헤드리스에서 신뢰성 있게 관찰 불가 → 항상 수동확인

SC5 · slash/skill 트리거 신뢰성 (비결정)

트리거는 비결정적이라 단일 PASS가 아니라 pass-rate(N=2)로 표기. 1/2 이하는 flaky.

  • 네임스페이스 slash /harness-aijient-team:harness-doctor 해석 (pass-rate 2/2)
  • 자연어("harness doctor 점검해줘")로도 트리거 (pass-rate 2/2)

stack 매트릭스 — 정확히 무엇을 검증하나

전제 정정: 현재 코드에서 stack별로 갈리는 산출물은 AGENTS.md의 ## 기술 스택 섹션 stackLabel 하나뿐이다. rules·settings·permissions는 stack 무관. 이 매트릭스는 ① init/apply 전 과정의 stack별 완주 ② stackLabel 렌더(stack-discriminating signal) ③ 스냅샷 stack delta를 검증하며, "stack별 rules·permissions"는 검증하지 않는다.

권한 — 스코프 allowlist (블랭킷 skip 아님)

헤드리스 에이전트는 하네스 CLI가 필요로 하는 node/git을 못 돌린다. agentloop.mjs가 딱 필요한 것만 여는 allowlist로 spawn한다. 샌드박스는 throwaway + git 격리라 안전. 필요 시 SIM_ALLOWED_TOOLS로 오버라이드.

# 기본 allowlist (runHeadless)
Bash(node:*),Bash(git:*),Bash(harness-team:*),Read,Write,Edit,Glob,Grep
어시스턴트가 대신 돌리려면 사용자 허가가 필요하다. 블랭킷 permission skip은 금지 — classifier 차단 대상이자 위험. 이 sim은 유저-런 또는 명시적 허가 하에서만 자동 구동된다.

의심 FAIL 격리 검증 — 실제 사례

SC4 post-commit ❌ → sim 버그였다 (하네스는 정상). 초기 런에서 SC4가 SessionStart 테스트를 위해 active task를 먼저 null로 만든 뒤 커밋해, active가 없으면 no-op인 handoff가 갱신 안 돼 false FAIL이 났다. CLI 레벨 격리(.git/hooks/post-commit 설치 확인 + active 있을 때 mtime 갱신 직접 검증)로 "진짜 결함 아님"을 증명 → SC4 순서를 post-commit 먼저로 교체해 수정. 이처럼 FAIL은 하네스 결함으로 바로 적지 말고 시나리오 의존성부터 의심한다.
진짜 발견 (CLI sim이 못 잡는 것): harness-init은 대화형이라 헤드리스/비대화형 컨텍스트에서 멈춰 scaffold를 안 만든다. → 프롬프트에 비대화형 지시를 주면 완주(7/7 → 현재 8신호). L5만 잡아낼 수 있는 자동화-적대성이다.

하이브리드 상태 관리 — 세 상태를 분리한다

① baseline (노이즈)

시나리오 작업 흔적(.sim-scratch·더미 커밋·handoff churn). 매 런 throwaway로 clean 복원 → 시작 조건을 버전 간 동일하게 유지(비교가능성).

③ 리포트 (측정 결과)

pass-rate를 날짜+버전 박아 sim-reports/에 누적. 점수 추이를 시간축으로 추적.

"하네스 업데이트 후 재테스트" 시나리오

이 sim이 실제로 부딪힌 이슈들. 대부분 sim 아티팩트이지 하네스 결함이 아니다.
증상원인대응
