# roadmap-to-1-0 — Spec

## 목적 / 요구사항
- **문제**: 0.46.0 릴리스에서 1.0 여부를 묻지 않고 minor로 정했다. 1.0 판단 기준이 어디에도 없었다.
  `docs/harness-cycle.md` §6의 남은 단계(5–7)에는 진행 순서가 없고, 7단계는 "메인테이너 입력 필요"로 막혀 있었다.
- **기대 결과**: 메인테이너가 2026-10-06에 정한 두 가지를 정본 문서에 남긴다.
  - §6 진행 계획(A1‖A2 → B → C1 → C2 → 1.0)과 1.0 조건
  - 위키 형태 입력(kc-platform `wiki/` 구조, 문서 원천 셋)
  MAINTAINING 버전 절에는 "1.0은 기본값으로 정하지 않는다"는 규칙을 둔다.
- **제약**: 문서만. 구현·새 장치 없음. 위키 구조는 "바뀔 수 있다"는 입력 그대로 적는다 — 하네스가 분류 체계를 확정하지 않는다.

## 설계 / 접근
- `docs/harness-cycle.md` §4-4: "메인테이너 입력 필요"를 받은 입력으로 바꾼다.
  설계 함의는 **추론**으로 표시해 C spec에서 확정하게 한다 — 분류 체계는 프로젝트 데이터, `90_system/` 규칙 준수, `99_inbox/` 폴백, `10_ssot/`와 R1의 접점.
- `docs/harness-cycle.md` §6: 7단계 문구를 갱신하고 "진행 계획" 절을 덧붙인다(묶음·task 이름·의존·1.0 조건).
- `MAINTAINING.md` 2단계 표 아래: 1.0 확인 규칙 한 문단.

### 2차 장치 규칙
새 장치가 아니다. 문서 규칙 한 문단이며, 기계 가드(예: release 명령이 1.0을 묻게 하기)는 두지 않는다 — 1.0은 한 번뿐인 결정이라 장치 비용이 이득보다 크다.

## Ontology
- **1.0 조건**: §6 7단계 완료 + 그 계약(시나리오 표·`gates.json`·pr-check·위키 컴파일)이 소비자 저장소에서 한 릴리스 이상 돈 상태.
- 게이트 근거: 바꿀 위치 3곳과 문구가 메인테이너 결정으로 고정돼 있다.
