# sim-section-scoping — Spec

## 목적 / 요구사항
*문제(오늘 무엇이 안 되는가) → 영향받는 사용자·시스템 → 기대 결과 → 제약 순으로 쓴다.
답 없는 질문은 요구가 아니다 — `## 참고` 절에 `- (open) …`으로 남긴다.*

**문제.** L5 sim 스코어러가 spec의 절 본문을 잘못 잘라 **위양성 FAIL**을 낸다.
`tests/sim/rules.mjs`의 `sectionBody`는 매치한 제목부터 **다음 `#{2,3}` 제목**까지를 절 본문으로
자른다. 그래서 `## 목적 / 요구사항` 안에 `### 요구사항` 같은 하위 제목을 둔 spec에서는 본문이
제목 직후 안내 문구까지로 잘리고, 그 아래 목록 항목이 하나도 안 들어온다.

**영향.** 하네스 개발자(= sim 리포트를 읽고 릴리스 판단을 하는 사람). 리포트가 "하네스가 계약을
어겼다"고 말하지만 실제로 어긴 것은 스코어러다. FAIL 하나마다 격리 재현에 사람 시간이 들고,
잘못 믿으면 멀쩡한 하네스를 고치게 된다.

- **R1 절 범위 (실측)** — `## 목적 / 요구사항` 아래 `### 문제`·`### 기대 결과`·`### 요구사항`을
  둔 spec에서 절 본문이 118 B(안내 문구)로 잘려 목록 항목 0개 → 출처 태그 FAIL.
  실측 출처: agentloop 런 `2026-09-07T0401` SC7 `spec-writer-2`.
- **R2 하네스는 무결했다 (실측)** — 같은 spec의 문서 전체 목록 항목은 41개이고 `### 요구사항`
  안에 `- **R1** … (confluence)`·`- **R4** … (interview, S2에서 유도)`처럼 항목별 출처 태그가
  정상이었다. 같은 런의 `spec-writer-1`은 평면 구조라 PASS했다 — 차이는 제목 구조뿐이다.
- **R3 제목 구조는 규정되지 않았다** — `commands/harness-spec.md:53`의 계약은
  "요구사항은 항목별로 출처를 표기한다"뿐이고, 평면 vs 하위 제목을 요구하는 문장은
  `commands/harness-spec.md`·`skills/harness-spec/SKILL.md` 어디에도 없다(전수 검색).
  따라서 하위 제목은 writer의 자유 선택이며 **이 FAIL에는 에이전트 행동 신호가 0**이다.
- **R4 기대 결과** — 절 본문을 **같거나 더 높은 레벨의 다음 제목**까지로 잡는다. 하위 제목은
  절에 포함하고, 같은 레벨의 다음 절로는 넘어가지 않는다.
- **C1 제약 — 동작 불변** — 기존 신호 판정을 바꾸지 않는다. 평면 구조 spec의 판정과
  `ambiguityCounts` 카운트가 그대로여야 한다.
- **C2 제약 — 범위** — 스코어러(`tests/sim/rules.mjs`)만 고친다. 하네스 쪽 코드·문서·템플릿은
  건드리지 않는다(R2·R3이 하네스 무결을 확인했다).

## 설계 / 접근

`sectionBody`가 매치한 제목의 `#` 개수를 읽어 절단 정규식을 `\n#{1,level} `로 만든다.
고정 `#{2,3}`을 레벨 파생값으로 바꾸는 한 줄 변경이며, 다른 구조는 그대로 둔다.

- 호출부는 둘뿐이다 — 요구사항 절(출처 태그 신호)과 `ambiguityCounts`(자가진단 카운트).
  둘 다 `^#{2,3}` 앵커 정규식을 넘기므로 매치는 항상 `#`로 시작한다.
- 자매 하네스 `tests/sim/codex-agentloop.mjs`·`tests/sim/skilltest.mjs`에는 같은 절단 로직이
  없다(전수 검색) — 결함은 `rules.mjs`에 국한되고 이번 변경도 거기서 끝난다.
- 회귀 방향이 한쪽뿐이라(절 범위가 넓어지기만 한다) **새는 것**을 막는 경계 테스트가 필요하다:
  같은 레벨의 다음 절에 있는 태그를 주워오면 안 된다.

## Ontology
*이 task가 다루는 핵심 개념의 정의. "X가 정확히 뭔가?"에 답한다.*

- **절 본문 (section body)**: 어떤 제목이 지배하는 텍스트 범위. 이 task 이전에는 "다음 `##`
  또는 `###` 제목 직전까지", 이후에는 **"같거나 더 높은 레벨의 다음 제목 직전까지"**로 바뀐다.
  하위 제목(`###` under `##`)은 상위 절에 **포함된다**.
- **위양성 FAIL (sim 아티팩트)**: 하네스는 계약을 지켰는데 스코어러의 결함으로 찍힌 FAIL.
  `AGENTS.md` 리뷰 기준의 "진짜 결함"과 구분해 리포트에 명시해야 하는 범주다.
- **출처 태그 계약**: 요구사항 **목록 항목**에 `(confluence)`·`(figma)`·`(interview)` 같은 괄호
  출처가 붙는 것. 문서 아무 데나 있으면 되는 게 아니라 요구사항 절의 항목이어야 한다 —
  이 "절 안에 있다"는 좁힘이 곧 `sectionBody`에 의존하는 지점이다.

## Ambiguity 자가진단
*각 항목이 명확하면 체크. 3개 이상 미체크면 구현 진입 금지 — 인터뷰/브레인스토밍으로 복귀해
모호성을 제거한다. 게이트를 통과하면 그 근거를 위 Ontology 섹션에 한 줄로 남긴다.*

- [x] **Goal 명확도** (40%) — 절 본문을 같거나 더 높은 레벨의 다음 제목까지로 잡아 위양성 FAIL을
      없앤다 (R4).
- [x] **Constraint 명확도** (30%) — 동작 불변(C1) · 스코어러만 수정(C2).
- [x] **Success 기준** (30%) — 실제 실패한 spec 원문(`spec-writer-2`)이 PASS로 뒤집히고,
      통과했던 원문(`spec-writer-1`)과 양쪽 자가진단 카운트(3/5)가 불변.
- [x] **Context 명확도** (brownfield 한정) — `tests/sim/rules.mjs` `sectionBody` + 호출부 2곳,
      테스트는 `tests/agentloop-spec-signals.test.mjs`. 전부 존재를 확인했다.
- [x] **Ambiguity ≤ 0.2** — 가중합 1.0. 실측 재현 근거가 있어 해석 여지가 없다.
