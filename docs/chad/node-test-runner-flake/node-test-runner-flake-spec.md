# node-test-runner-flake — Spec

## 목적 / 요구사항

CI가 간헐적으로 빨개진다. 지금까지 이것은 `boundary perf flake` 한 가지 원인으로 취급됐지만,
perf 쪽을 고치는 과정(PR #44)에서 workflow에 annotation 계측을 넣자마자 **두 번째, 서로 다른 원인**이
드러났다:

```
not ok 38 - tests/task-templates.test.mjs
  error: 'Unable to deserialize cloned data due to invalid or unsupported version.'
```

이 task는 그 두 번째 원인을 다룬다. **perf flake와는 무관하며, PR #44는 이 건을 고치지 않는다.**

요구사항:
1. 원인을 확정한다 (아래 조사 결과로 이미 상당 부분 확정됨).
2. CI가 이 오류로 빨개지지 않게 한다.
3. **커버리지를 임의로 줄여서 green을 사지 않는다** — 특히 "실패하는 job을 지운다"는
   해법은 그 자체로 정당화되어야 하며, 정당화 근거는 아래 "지원 종료" 항목이다.

## 설계 / 접근

### 조사 결과 — 원인은 확정됐다 (업스트림 버그)

우리 코드 문제가 아니다.

- 실패한 `tests/task-templates.test.mjs`는 **템플릿 문자열 assertion과 fs 조작만** 한다.
  자식 프로세스를 스폰하지 않고, 직렬화를 직접 쓰지 않는다.
- **동일 커밋 코드**로 앞선 CI 실행(`af6ae4c7`)은 두 job 모두 통과했다.
- 실패 job만 재실행하니 통과했다 → 전이성(transient).
- 오류는 `node:internal/test_runner/runner`의 `#processRawBuffer`에서 난다 —
  러너가 자식 프로세스로부터 결과 payload를 역직렬화하는 지점이다.

**업스트림 근본 원인** (nodejs/node#64061 → PR #64706): `processRawBuffer`가 payload 길이를
**부호 있는 정수**로 읽는다. payload가 커져 최상위 비트가 서면 길이가 음수/무효가 되어
역직렬화가 깨진다. 수정은 `child_process`에 이미 쓰이던 패턴대로 `>>> 0`(부호 없는 변환)을
붙이는 한 줄이다. **2026-07-26 머지, Node 26.7.0 (2026-08-05) 릴리스에 포함.**

이 때문에 여러 프로젝트에서 같은 증상이 보고됐고(Appium은 Node 24.10.0에서 관측),
"로컬에서는 간헐적, CI에서는 재현이 잘 된다"는 특성도 보고 내용과 일치한다 —
동시 실행되는 여러 worker가 결과를 스트리밍할 때 payload가 커지면 잘 터진다.

### 결정적 제약 — 우리 matrix가 전부 지원 종료(EOL) 런타임이었다

> **진단 시점(구현 전)의 상태다.** 이 제약이 곧 결정의 근거가 됐고,
> 현재는 `matrix: [24]` · `engines: ">=24"`로 해소됐다 (PR #45).

당시 `.github/workflows/test.yml`의 matrix는 `node: [18, 20]`, `package.json`은
`engines.node: ">=18"`이었다. nodejs/Release 공식 스케줄 기준(2026-08-25):

| 버전 | EOL | 상태 |
|---|---|---|
| **18** | 2025-04-30 | **지원 종료 (1년 4개월 경과)** |
| **20** | 2026-04-30 | **지원 종료 (4개월 경과)** |
| 22 | 2027-04-30 | 활성 LTS |
| 24 | 2028-04-30 | 활성 LTS |

즉 **우리는 지원 종료된 런타임 두 개만 테스트하고 있다.**

### 백포트 실측 — "활성 LTS로 이동"과 "flake 해소"는 별개다

초기 판단은 "활성 LTS로 옮기면 EOL 문제와 flake가 함께 해소된다"였다. **틀렸다.**
릴리스 라인별로 소스를 직접 대조해 확정했다 (추정 아님):

```
$ gh api "repos/nodejs/node/contents/lib/internal/test_runner/runner.js?ref=<branch>"     --jq .content | base64 -d | grep -c '>>> 0) + kSerializedSizeHeader'
```

| 릴리스 라인 | 취약 코드 | 수정(`>>> 0`) | 최신 릴리스 | flake 상태 |
|---|---|---|---|---|
| v18.x | 있음 | **없음** | — | **영구 잔존** (EOL 2025-04-30) |
| v20.x | 있음 | **없음** | — | **영구 잔존** (EOL 2026-04-30) |
| v22.x | 있음 | **없음** (`v22.x-staging`에도 없음) | 22.23.2 (2026-07-29) | **잔존** — 백포트 안 됨 |
| v24.x | 있음 | **staging에 있음** (`9ed7146851`) | 24.19.0 (2026-08-03, 취약) | **24.20.0부터 해소** |
| v26.x | 있음 | **있음** | 26.7.0 (2026-08-05) | **해소됨** |

근거:
- **v24 백포트 확정** — cherry-pick `9ed7146851`이 `v24.x-staging`에 있고,
  열려 있는 릴리스 PR **nodejs/node#65461 "2026-08-26, Version 24.20.0 'Krypton' (LTS)"** 의
  CHANGELOG 항목에 `test_runner: convert to uint during deserialization ... #64706`으로 명시돼 있다.
  → **Node 24.20.0 (2026-08-26 예정)부터 해소.** 현재 최신 24.19.0에는 없다.
- **v22 백포트 없음** — `v22.x-staging`의 해당 줄은 여전히 `const fullMessageSize = (` 로
  괄호 보정이 없다. 백포트 PR도 없다.
- v18/v20은 EOL이라 **영구히** 도달하지 않는다.

**따라서 "활성 LTS(22/24)로 이동"이 곧 flake 해소는 아니다.**
- 22로 가면 **flake는 그대로 남는다.**
- 24로 가면 **24.20.0 이후에만** 해소된다.
  > **정정 (2026-08-28):** 원래 여기에 "`node-version: 24`는 최신 24.x로 해석되므로 릴리스되면
  > 자동으로 24.20.0을 집는다"고 적었다. **틀렸다.** `setup-node`는 `check-latest`가 꺼져 있으면
  > dist 매니페스트보다 **러너 toolcache를 먼저** 본다(`base-distribution.ts`
  > `findVersionInHostedToolCacheDirectory()` → `tc.find('node','24')`). 이미지가 캐시한
  > 24.19.0이 spec `24`를 만족하므로 그대로 쓰인다. 자동 승계는 **러너 이미지가 갱신된 뒤**
  > 일어난다. 측정 근거는 artifact `### 검증 시도 1회차 (2026-08-28)`.
- 26은 이미 해소됐지만 **Current이고 LTS 승격은 2026-10월**이다.

### 후보

두 목표는 **분리해서** 평가해야 한다.

| 후보 | 내용 | EOL 탈출 | flake 해소 |
|---|---|---|---|
| (A1) `[22, 24]` | 활성 LTS 둘 | ✅ | ❌ **22 job에 그대로 남는다** |
| **(A2) `[24]`** | 활성 LTS 하나 | ✅ | ✅ **단 24.20.0(2026-08-26) 이후** |
| (A3) `[24, 26]` | LTS + Current | ✅ | ✅ (26은 이미 해소) |
| (B) `[18, 20, 22, 24]` | 기존에 추가만 | ❌ 18·20 잔존 | ❌ |
| (C) payload 축소 | 출력을 줄여 임계 회피 | ❌ | 🔸 증상 완화만 · 임계 미상 · 출력 늘면 재발 |
| (D) `--test-concurrency=1` | 동시 스트리밍 제거 | ❌ | 🔸 확률만 낮춤 · 스위트 느려짐 |
| (E) 실패 시 자동 재시도 | 재실행으로 green | ❌ | ❌ **채택 금지** — 진짜 회귀까지 숨긴다 |

**두 목표를 동시에 만족하는 것은 (A2)/(A3)뿐이며, 그것도 2026-08-26 이후다.**

### 채택: (A2) — `engines: ">=24"` + matrix `[24]` (2026-08-25 확정)

어떤 Node 버전을 지원할지는 제품 정책이라 이 task 단독으로 결정할 수 없었고,
**사람의 결정을 받아 (A2)로 확정했다.** 하위 호환 파기를 수용하고 EOL 탈출과 flake 해소를
동시에 얻는 선택이다. **핵심은 22를 넣지 않은 것** — "활성 LTS니까 22"는 flake를 남긴다.

- **재확인(2026-08-25):** v22는 백포트가 없다. `v22.x`·`v22.x-staging` 모두 미반영이고
  백포트 PR도 없다(최신 22.23.2, 2026-07-29). v22는 2025-10-21부터 maintenance라
  테스트 러너 버그가 백포트될 가능성은 낮다 — 22를 넣으면 flake는 **사실상 영구 잔존**한다.
- 대안으로 검토된 **floor 22(`[22, 24]`)** 는 이 근거로 채택하지 않았다.
  절충안 `engines ">=22"` + matrix `[24]` 도 **최소 지원 버전을 검증하지 않는** 공백이 생겨 제외했다.
- (C)·(D)는 증상 완화라 불필요해졌고, (E) 자동 재시도는 **채택 금지**로 못박았다.

**남은 것은 flake 해소 검증 하나뿐이다** — 패치된 런타임에서 반복 통과를 확인한다.
Node 24.20.0 자체는 **2026-08-27에 게시됐다**. 그럼에도 2026-08-28 현재 CI annotation은
여전히 `runtime v24.19.0`(미패치)을 기록한다 — 위 정정 참조. 대기 조건은
"24.20.0 릴리스"에서 **"러너 이미지 toolcache가 24.20.0을 실을 때"**로 바뀌었다.
정책 결정과 Ambiguity 게이트는 **이미 닫혔다 — 다시 열지 말 것.**

## Ontology

- **`#processRawBuffer`**: `node:test` 러너가 자식 프로세스의 결과 스트림을 역직렬화하는 내부 함수.
  이번 오류의 발생 지점이며, 우리 코드가 호출하지 않는다.
- **payload 임계**: 길이 필드의 부호 비트가 서는 크기. 정확한 값은 특정하지 않았고,
  특정할 필요도 없다 — 후보 (C)를 채택하지 않는 이상 무의미하다.
- **EOL(지원 종료)**: 업스트림이 보안 수정조차 더는 배포하지 않는 상태.
  이 버그가 node 18·20에서 영구히 고쳐지지 않는 이유다.
- **백포트 도달 여부**: EOL과 **독립된 축**이다. 활성 LTS라고 수정이 와 있는 것이 아니다 —
  v22는 활성 LTS인데도 백포트가 없다. 런타임 선택 시 두 축을 따로 확인해야 한다.
- **전이성(transient) 실패**: 같은 코드·같은 커밋에서 실행마다 결과가 달라지는 실패.
  재실행으로 통과한다는 사실이 코드 결함 가설을 반증한다.
- **러너 toolcache 도달 여부**: 백포트 도달과 **또 다른 축**이다. 업스트림이 릴리스하고
  `actions/node-versions`에 게시돼도, `setup-node`는 `check-latest` 없이는 러너 이미지가
  미리 캐시해 둔 버전을 먼저 쓴다. **"릴리스됐다"와 "CI에서 그 버전으로 돈다"는 다른 사건**이며,
  둘 사이에는 이미지 롤아웃 지연(24.19.0 기준 약 1주)이 있다.

## Ambiguity 자가진단

- [x] **Goal 명확도** (40%) — "이 오류로 CI가 빨개지지 않게 한다"는 명확.
- [x] **Constraint 명확도** (30%) — **해소(2026-08-25 사용자 결정).**
      `engines: ">=24"`, matrix `[24]`. 하위 호환 파기를 수용하고, flake 해소까지 가는
      선택지 중 (A2)를 택했다. 22를 넣지 않는 것이 이 결정의 핵심이다 — 넣으면 flake가 남는다.
- [x] **Success 기준** (30%) — 활성 LTS matrix에서 스위트가 반복 통과하고,
      이 오류가 annotation에 더 이상 나타나지 않는다.
- [x] **Context 명확도** — 원인 파일은 우리 저장소에 없다(업스트림). 영향 파일은 최종 7개:
      `.github/workflows/test.yml` · `release.yml` · `package.json` · `README.md` ·
      `docs/prerequisites.md` · `MAINTAINING.md` · `CHANGELOG.md`.
      (진단 시점에는 앞의 3개만 식별했고, 사용자 대면 문서 4개는 구현 중 grep 전수로 추가됐다.)
- [x] **Ambiguity ≤ 0.2** — 가중합 1.0 → **게이트 통과 (2026-08-25)**.

게이트는 정책 결정을 기다리며 의도적으로 열려 있었고, 결정이 내려와 닫혔다.
**채택: (A2) `engines: ">=24"` + matrix `[24]`.**
