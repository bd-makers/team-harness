# node-test-runner-flake — Spec

## 목적 / 요구사항

CI가 간헐적으로 빨개진다. 지금까지 이것은 `boundary perf flake` 한 가지 원인으로 취급됐지만,
perf 쪽을 고치는 과정(PR #44)에서 workflow에 annotation 계측을 넣자마자 **두 번째, 서로 다른 원인**이
드러났다:

```
not ok 38 - tests/task-templates.test.mjs
  error: 'Unable to deserialize cloned data due to invalid or unsupported version.'
```

이 task는 그 두 번째 원인을 다룬다. **perf flake와는 무관하며, PR #44는 이 건을 고치지 않는다.**

요구사항:
1. 원인을 확정한다 (아래 조사 결과로 이미 상당 부분 확정됨).
2. CI가 이 오류로 빨개지지 않게 한다.
3. **커버리지를 임의로 줄여서 green을 사지 않는다** — 특히 "실패하는 job을 지운다"는
   해법은 그 자체로 정당화되어야 하며, 정당화 근거는 아래 "지원 종료" 항목이다.

## 설계 / 접근

### 조사 결과 — 원인은 확정됐다 (업스트림 버그)

우리 코드 문제가 아니다.

- 실패한 `tests/task-templates.test.mjs`는 **템플릿 문자열 assertion과 fs 조작만** 한다.
  자식 프로세스를 스폰하지 않고, 직렬화를 직접 쓰지 않는다.
- **동일 커밋 코드**로 앞선 CI 실행(`af6ae4c7`)은 두 job 모두 통과했다.
- 실패 job만 재실행하니 통과했다 → 전이성(transient).
- 오류는 `node:internal/test_runner/runner`의 `#processRawBuffer`에서 난다 —
  러너가 자식 프로세스로부터 결과 payload를 역직렬화하는 지점이다.

**업스트림 근본 원인** (nodejs/node#64061 → PR #64706): `processRawBuffer`가 payload 길이를
**부호 있는 정수**로 읽는다. payload가 커져 최상위 비트가 서면 길이가 음수/무효가 되어
역직렬화가 깨진다. 수정은 `child_process`에 이미 쓰이던 패턴대로 `>>> 0`(부호 없는 변환)을
붙이는 한 줄이다. **2026-07-26 머지, Node 26.7.0 (2026-08-05) 릴리스에 포함.**

이 때문에 여러 프로젝트에서 같은 증상이 보고됐고(Appium은 Node 24.10.0에서 관측),
"로컬에서는 간헐적, CI에서는 재현이 잘 된다"는 특성도 보고 내용과 일치한다 —
동시 실행되는 여러 worker가 결과를 스트리밍할 때 payload가 커지면 잘 터진다.

### 결정적 제약 — 우리 matrix는 전부 지원 종료(EOL) 런타임이다

`.github/workflows/test.yml`의 matrix는 `node: [18, 20]`이고, `package.json`은 `engines.node: ">=18"`이다.
nodejs/Release 공식 스케줄 기준(2026-08-25 현재):

| 버전 | EOL | 상태 |
|---|---|---|
| **18** | 2025-04-30 | **지원 종료 (1년 4개월 경과)** |
| **20** | 2026-04-30 | **지원 종료 (4개월 경과)** |
| 22 | 2027-04-30 | 활성 LTS |
| 24 | 2028-04-30 | 활성 LTS |

즉 **우리는 지원 종료된 런타임 두 개만 테스트하고 있다.** 그리고 위 수정은
Node 18에는 **절대 백포트되지 않는다** — 이미 EOL이기 때문이다.
따라서 "node 18에서 이 flake를 고친다"는 목표는 업스트림 경로로는 달성 불가능하다.

### 후보

| 후보 | 내용 | 평가 |
|---|---|---|
| **(A) matrix·engines를 활성 LTS로 이동** | `[18, 20]` → `[22, 24]`, `engines: ">=22"` | **권장.** 근본 해결이자 EOL 문제를 동시에 해소. 단 **지원 범위 축소라는 정책 결정**이라 사용자 판단 필요 |
| (B) matrix에 22·24 추가만 | `[18, 20, 22, 24]` | flake는 그대로. job 수만 2배 |
| (C) payload 축소 | 진단 출력·assertion 메시지를 줄여 임계 아래로 | 증상 완화일 뿐 · 임계가 어디인지 모름 · 출력이 늘면 재발 |
| (D) `--test-concurrency=1` 전체 적용 | 동시 스트리밍을 없애 확률 감소 | 확률만 낮춤 · 스위트 느려짐 · 근본 아님 |
| (E) 실패 시 자동 재시도 | 재실행으로 green | **커버리지를 사는 방식** — 진짜 회귀도 함께 숨긴다. 채택 금지 |

**(A)가 권장이지만 이 task 단독으로 결정할 수 없다** — 어떤 Node 버전을 지원할지는
제품 정책이다. plan의 1단계가 그 결정을 받는 것이다.

## Ontology

- **`#processRawBuffer`**: `node:test` 러너가 자식 프로세스의 결과 스트림을 역직렬화하는 내부 함수.
  이번 오류의 발생 지점이며, 우리 코드가 호출하지 않는다.
- **payload 임계**: 길이 필드의 부호 비트가 서는 크기. 정확한 값은 특정하지 않았고,
  특정할 필요도 없다 — 후보 (C)를 채택하지 않는 이상 무의미하다.
- **EOL(지원 종료)**: 업스트림이 보안 수정조차 더는 배포하지 않는 상태.
  이 버그가 node 18에서 영구히 고쳐지지 않는 이유이자, (A)의 근거다.
- **전이성(transient) 실패**: 같은 코드·같은 커밋에서 실행마다 결과가 달라지는 실패.
  재실행으로 통과한다는 사실이 코드 결함 가설을 반증한다.

## Ambiguity 자가진단

- [x] **Goal 명확도** (40%) — "이 오류로 CI가 빨개지지 않게 한다"는 명확.
- [ ] **Constraint 명확도** (30%) — **미충족.** 지원할 Node 버전 범위가 미정이다.
      (A)는 `engines`를 `>=22`로 올려 **하위 호환을 깨는** 결정이며, 이 플러그인을
      node 18/20에서 쓰는 사용자가 있는지 확인되지 않았다.
- [x] **Success 기준** (30%) — 활성 LTS matrix에서 스위트가 반복 통과하고,
      이 오류가 annotation에 더 이상 나타나지 않는다.
- [x] **Context 명확도** — 영향 파일 2개: `.github/workflows/test.yml`, `package.json`.
      원인 파일은 우리 저장소에 없다(업스트림).
- [ ] **Ambiguity ≤ 0.2** — 위 Constraint 미충족으로 **가중합 0.7 → 게이트 미통과**.

**게이트 미통과 상태다. 구현에 진입하지 않는다.** plan 1단계에서 지원 범위 결정을 받은 뒤
이 절을 갱신하고 진입한다. 이는 결함이 아니라 의도된 상태 — 남은 모호성이 기술적 문제가
아니라 **정책 결정**이기 때문이다.
