## 검증 기록

*flake 해소 검증은 **아직 열려 있다.** 아래는 시도와 그 결과다.*

### 검증 시도 1회차 (2026-08-28) — 실패: 패치 런타임을 확보하지 못했다

**판정: 검증 불가 — 대기 조건이 해제되지 않았다. 해소 선언하지 않는다.**

대기 조건이었던 Node 24.20.0은 **나왔다.** 두 출처로 확인했다:

```
$ gh api repos/actions/node-versions/releases --paginate \
    --jq '.[]|select(.tag_name|startswith("24.20.0"))|"\(.tag_name) \(.published_at)"'
24.20.0-33034074684  2026-08-27T02:44:18Z
$ gh api repos/nodejs/node/git/ref/tags/v24.20.0 --jq .ref
refs/tags/v24.20.0
```

그런데 CI는 여전히 24.19.0으로 돈다. 관측한 네 런 전부:

| run | attempt | job | 트리거 | 시각 | runtime | 결과 |
|---|---|---|---|---|---|---|
| 33020051882 | 1 | 98347946860 | push(main) | 2026-08-26T22:33Z | `v24.19.0` | ✅ green |
| 33020249395 | 1 | 98348605653 | push(main) | 2026-08-26T22:36Z | `v24.19.0` | ✅ green |
| **33020249395** | **2** | **98759657160** | **rerun** | **2026-08-28** | **`v24.19.0`** | ✅ green |
| **33143940438** | **1** | **98760758995** | **pull_request (PR #56)** | **2026-08-28** | **`v24.19.0`** | ✅ green |

아래 두 줄이 이번 시도다. **24.20.0 게시로부터 약 19시간 뒤, 새 러너에서 돌았는데도
24.19.0이었다.** 즉 브리프가 전제한 "rerun하면 `setup-node`가 `24`를 현재 매니페스트 기준으로
재해석한다"가 **성립하지 않는다.**

마지막 줄은 rerun이 아니라 **완전히 새로 트리거된 `pull_request` 런**이다 — rerun 경로의
특수성(attempt 재사용 등)을 배제하기 위해 확인했고, 결과는 같았다. 원인은 rerun이 아니라
`setup-node`의 해석 순서다.

**패치 런타임 기준(`v24.20.0` 이상)으로 확보한 green은 0회다. 필요한 5회 연속 중 0회.**

#### 왜 집지 못하는가 — 소스로 확인

`actions/setup-node@v5`의 `src/distributions/base-distribution.ts`:

```ts
public async setupNodeJs() {
  let nodeJsVersions: INodeVersion[] | undefined;
  if (this.nodeInfo.checkLatest) {              // ← 우리는 설정하지 않았다
    const evaluatedVersion = await this.findVersionInDist(nodeJsVersions);
    this.nodeInfo.versionSpec = evaluatedVersion;
  }
  let toolPath = this.findVersionInHostedToolCacheDirectory();   // ← 먼저 여기
  if (toolPath) { core.info(`Found in cache @ ${toolPath}`); }
  else { /* dist 조회 후 다운로드 */ }
```

`findVersionInHostedToolCacheDirectory()`는 `tc.find('node', '24', arch)`다.
**`check-latest`가 꺼져 있으면 dist 매니페스트는 조회조차 하지 않는다.**

그리고 현재 러너 이미지가 캐시한 것은 24.19.0이다:

```
$ gh api repos/actions/runner-images/contents/images/ubuntu/Ubuntu2404-Readme.md \
    --jq .content | base64 -d | grep -A4 '^#### Node.js'
#### Node.js
- 22.23.2
- 24.19.0
```

최신 이미지는 `ubuntu24/20260823.283`(2026-08-24 게시)로 **24.20.0보다 3일 앞선다.**
캐시된 24.19.0이 spec `24`를 만족하므로 그대로 쓰인다. **이미지가 갱신되기 전까지는 rerun을
더 돌려도 결과가 같다** — 영구한 성질이 아니라 현재 이미지에 한정된 판정이다. 이미지가 롤아웃되면
그때의 rerun은 24.20.0을 집는다.

#### 대기 해제 조건 (다음 세션이 볼 것은 이것 하나)

```
gh api repos/actions/runner-images/contents/images/ubuntu/Ubuntu2404-Readme.md \
  --jq .content | base64 -d | grep -A4 '^#### Node.js'
```

목록에 **24.20.0 이상**이 뜨면 해제다. (`ubuntu-latest`가 Ubuntu 24.04 x64로 해석되는 것은
`actions/runner-images` README의 이미지 표에서 확인했다 — 그래서 이 Readme가 맞는 파일이다.) 이전 사이클의 실측 지연:
24.19.0은 node-versions 게시(2026-08-04) → 이미지 `ubuntu24/20260810.271`(2026-08-11 게시)에
이미 실려 있었다 — **약 1주.** 같은 리듬이면 24.20.0은 2026-09-03 전후로 예상된다.

#### 선택지 — 오케스트레이터 결정 사항 (워커가 임의로 고르지 않았다)

| | 내용 | 비용 | 성질 |
|---|---|---|---|
| **(a)** 이미지 롤아웃을 기다린다 | 변경 없음 | CI 0회, 대기 ~1주 | `24`로 두는 결정의 원래 의도와 일치 |
| **(b)** `check-latest: true` 추가 | `test.yml` setup-node 스텝 | 캐시 미스 시 job당 node 다운로드 (**미측정**) | **워크플로 변경** — 매니페스트 버전을 보장한다 |

(b)는 브리프 4절의 확정 제약 네 가지(22 추가·정확 패치 pin·자동 재시도·`workflow_dispatch` 추가)
중 어느 것에도 해당하지 않지만, "코드·워크플로 변경 없음"이라는 이번 작업의 범위를 벗어난다.
브리프 6절에 따라 **판단하지 않고 올린다.**

### 어떻게 발견됐나

perf flake(PR #44)를 고치면서 workflow에 annotation 계측을 넣었다 —
이 저장소를 유지보수하는 머신은 raw CI 로그를 받을 수 없기 때문이다
(`*.blob.core.windows.net` 403). 계측을 넣은 **첫 실행**에서 곧바로 잡혔다:

```
not ok 38 - tests/task-templates.test.mjs
  error: 'Unable to deserialize cloned data due to invalid or unsupported version.'
```

계측이 없었다면 이 실패는 "test (18) failed, exit code 1"로만 보였을 것이고,
perf flake와 구분되지 않은 채 같은 원인으로 오인됐을 것이다.
**"CI가 무작위로 빨개진다"에는 최소 두 개의 서로 다른 원인이 섞여 있었다.**

### 업스트림 근본 원인

- **nodejs/node#64061** — 증상 보고. `#processRawBuffer`에서 발생. "로컬 간헐적, CI 재현 잘 됨".
  Appium은 Node 24.10.0에서 관측 — **18 전용 버그가 아니다.**
- **nodejs/node#64706** — 수정. payload 길이를 **부호 있는 정수**로 읽던 것을
  `>>> 0`으로 부호 없는 변환. `child_process`에 이미 쓰이던 패턴.
  payload가 커져 최상위 비트가 서면 길이가 무효가 되어 역직렬화가 깨진다.
  동시 실행 worker가 결과를 스트리밍할 때 payload가 커지므로 CI에서 잘 터진다.
- 머지 2026-07-26 → **Node 26.7.0 (2026-08-05)** 릴리스에 포함.

### 결정적 제약 — matrix가 전부 지원 종료 런타임이다

nodejs/Release 공식 스케줄 기준 (2026-08-25 현재):

| 버전 | EOL | 상태 | 우리 사용처 |
|---|---|---|---|
| **18** | 2025-04-30 | **종료 (1년 4개월 경과)** | `test.yml` matrix · `engines: ">=18"` |
| **20** | 2026-04-30 | **종료 (4개월 경과)** | `test.yml` matrix · `release.yml` 발행 |
| 22 | 2027-04-30 | 활성 LTS | — |
| 24 | 2028-04-30 | 활성 LTS | — |

**node 18에는 이 수정이 절대 도달하지 않는다** — 이미 EOL이다.
따라서 "node 18에서 이 flake를 고친다"는 업스트림 경로로 달성 불가능하며,
이것이 후보 (A)(활성 LTS로 이동)를 권장하는 근거다.

부수 발견: **릴리스 발행(`release.yml`)도 EOL 런타임(node 20)에서 돈다.**
이 task의 원래 범위 밖이지만 같은 결정에 묶인다.

초기 보고는 "활성 LTS(22/24)로 이동하면 EOL 문제와 flake가 함께 해소된다"였다.

확정 근거:
- **v24 백포트** — cherry-pick `9ed7146851`이 `v24.x-staging`에 존재. 열려 있는 릴리스 PR

  `test_runner: convert to uint during deserialization (Aviv Keller) [#64706]` 로 명시.
- **v22 미백포트** — `v22.x-staging`의 해당 줄은 여전히 `const fullMessageSize = (` 이고
  괄호 보정(`>>> 0`)이 없다. 백포트 PR도 없다.

**교훈: EOL과 백포트 도달 여부는 독립된 축이다.** "활성 LTS면 최신 수정이 와 있다"는
가정이 틀렸다 — v22가 반례다. 런타임을 고를 때 두 축을 따로 확인해야 한다.
이 오류는 "수정이 X 버전에 들어갔다"에서 "그 이하 활성 버전에도 있겠지"로 건너뛴 데서 나왔다.

실무적 함의:
- `[22, 24]`를 고르면 **22 job에 flake가 그대로 남는다** — 가장 자연스러워 보이는 선택이 함정이다.
- `[24]`는 `actions/setup-node`가 최신 24.x를 집으므로 **2026-08-26 이후 자동으로** 해소된다.
  그 전에 검증하면 24.19.0(취약)이라 잘못된 결론이 나온다.
  > **정정 (2026-08-28):** "자동으로"의 시점이 틀렸다. `setup-node`는 러너 toolcache를 먼저 보므로
  > 승계는 **러너 이미지가 갱신된 뒤**에 일어난다. → `## 검증 기록`

### 2회차 관측 — PR #44 머지 직후 main이 이 flake로 빨개졌다

2026-08-25, PR #44가 main에 머지된 직후 `test (18)`이 실패했다. annotation이 즉시 원인을 알려줬다:

```
not ok 38 - tests/task-templates.test.mjs
  error: 'Unable to deserialize cloned data due to invalid or unsupported version.'
```

같은 run의 `test (20)`은 통과했고 perf 수치도 정상이었다
(`cold 1.70x / checkpoint 1.76x`, 예산 3x/5x). 즉 **#44의 회귀가 아니라 이 task가 다루는
바로 그 node 18 flake**이며, 이번에는 **main을 빨갛게 만들었다.**

두 가지가 확인된다:
1. 계측이 제 값을 했다 — 이전이라면 "exit code 1"만 보였을 실패가 **한 번에** 특정됐다.
2. 이 flake는 산발적 불편이 아니라 **기본 브랜치를 막는다.** 관측 2회차이고
   `[24]` 이동(이 PR)이 그대로 해소책이다 — node 18 job이 사라지기 때문이다.

### 결정 및 구현 (2026-08-25)

**결정: `engines: ">=24"` + CI matrix `[24]`** — spec 후보표의 (A2). 하위 호환 파기를 수용하고
EOL 탈출과 flake 해소를 동시에 얻는 선택이다. **22를 넣지 않는 것이 핵심**이다 —
"활성 LTS 두 개"로 보이는 `[22, 24]`는 22 job에 flake를 남긴다.

변경 지점 (grep 전수 확인):

| 파일 | 전 | 후 |
|---|---|---|
| `package.json:20` | `"node": ">=18"` | `">=24"` |
| `.github/workflows/test.yml` | `node: [18, 20]` | `node: [24]` (+ 사유 주석) |
| `.github/workflows/release.yml` | `node-version: 20` | `24` (+ 사유 주석) |
| `README.md` | "Node.js ≥ 18" ×2 | ≥ 24 |

### 주의 2 — perf 가드의 민감도가 node 24에서 낮아진다

perf 테스트(PR #44)의 비율 예산은 node 18/20 실측으로 산정됐다. node 24는 **프로세스 시작

| | node 20 | node 24 |
|---|---|---|
| bare spawn | ~17ms | ~37ms |
| baseline | ~23ms | ~42ms |
| cold | ~33ms | ~56ms |
| cold/baseline | 1.43 | **1.34** |
| 3x 예산까지 허용되는 추가 비용 | +46ms | **+69ms** |

CI(Linux)의 node 24 시작 비용은 macOS와 전혀 달랐다. 같은 hosted 러너에서 받은 값:

| CI job | spawn floor | baseline | cold | checkpoint |
|---|---|---|---|---|
| test (18) | 23.2ms | 38.6ms | **1.68x** | 1.79x |
| test (20) | 22.1ms | 35.8ms | **1.75x** | 1.89x |
| **test (24)** | 28.4ms | 38.3ms | **1.78x** | 1.83x |

교훈: 로컬(macOS) 실측만으로 CI 리스크를 단정하지 말 것 — 이 건은 로컬 수치가

## Learnings

- **EOL과 "수정이 도달했는가"는 독립된 축이다.** 활성 LTS라고 최신 수정이 와 있지 않다 —
  v22가 반례였다. "수정이 26.7.0에 들어갔다 → 그 이하 활성 버전에도 있겠지"로 건너뛴 것이
  이 task 최대의 오판이었고, 릴리스 라인별 소스를 직접 대조해서야 잡혔다.
  런타임을 고를 때 **두 축을 따로 확인**한다.
- **런타임을 바꾸면 도구의 기본 출력 형식도 바뀔 수 있다.** node ≤20은 TAP, ≥22는 spec이라
  접두사에 앵커한 CI 계측이 **실패 없이 조용히** 죽었다. "green인데 아무것도 안 나온다"는
  형태라 놓치기 쉽다. 출력 형식에 의존하는 계측은 런타임 이동 시 반드시 재검증한다.
- **로컬 실측만으로 CI 리스크를 단정하지 말 것.** macOS의 node 24 시작 비용(37~40ms)을 근거로
  perf 예산 민감도 저하를 리스크로 올렸으나, CI(Linux)는 28.4ms로 18·20과 비슷해 실현되지
  않았다. 로컬 수치가 실제보다 **나쁜 쪽으로** 오도한 사례다.
- **"관측 불가"는 고칠 수 있는 조건이다.** CI 로그가 403이라 진단이 막혀 있었는데,
  annotation API로 우회하자 이 flake가 **첫 실행에서** 특정됐고 이후 main 실패도 즉시 분류됐다.
  진단 인프라를 먼저 세우는 것이 개별 flake를 쫓는 것보다 빨랐다.
- **아직 안 나온 버전으로 pin하면 CI가 깨진다.** 리뷰가 제안한 `node-version: 24.20.0`은
  태그가 404여서 채택 불가였다 — 제안을 받을 때도 **존재 여부를 먼저 측정**한다.
- **"업스트림이 릴리스했다"와 "CI가 그 버전으로 돈다"는 다른 사건이다.** 그 사이에
  러너 이미지 toolcache라는 세 번째 축이 있고, `setup-node`는 `check-latest` 없이는
  캐시를 dist 매니페스트보다 **먼저** 본다. 24.20.0 게시 19시간 뒤 rerun이 여전히 24.19.0을
  집은 것이 그 증거다. 이 task는 이미 "EOL"과 "백포트 도달"을 분리했는데, **같은 유형의
  축 누락을 한 번 더 했다** — 릴리스 채널의 각 홉을 따로 확인해야 한다.
- **대기 조건은 검증 가능한 명령으로 적어 둔다.** "24.20.0이 나오면"처럼 적으면 조건이
  충족돼도 목표가 달성되지 않는다. 이번 재개 트리거는 러너 이미지 Readme grep 한 줄로
  바꿔 뒀다 — 다음 세션이 판단이 아니라 **관측**으로 해제 여부를 알 수 있다.
