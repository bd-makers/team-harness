0.16.0은 병렬 브랜치가 반드시 머지 충돌하던 구조를 걷어냅니다. 두 MR이 서로 다른 파일만 고쳤는데도 충돌했습니다. 원인은 내용이 아니라 위치였습니다 — task가 요약표 끝에 행을 붙이고 사용자 인덱스의 같은 헤더 아래에 항목을 끼워 넣었기 때문에, 두 브랜치의 새 줄이 항상 같은 자리를 다퉜습니다.

충돌은 내용이 아니라 위치에서 난다

Root cause

새 줄은 언제나 같은 자리에 들어갔다

변경
task와 done이 공유 원장(docs/task_summary.md, docs/<user>/<user>-task.md)을 더 이상 쓰지 않습니다.
왜
addToTaskSummary는 content.trimEnd() + row로 파일 끝에 붙였고, addToUserTaskIndex는 ## Open 헤더 바로 아래에 끼워 넣었습니다. 브랜치 A가 만든 task와 브랜치 B가 만든 task는 서로 아무 관련이 없는데도 diff 상 같은 hunk를 차지합니다. git이 고를 수 있는 답이 없으므로 충돌은 선택이 아니라 필연이었습니다.
그래서
각 브랜치는 자기 task 디렉터리의 <name>-meta.json만 만듭니다. 공유 파일 수정이 0이므로 충돌이 구조적으로 불가능합니다.
Rejected

union merge로 덮지 않는다

변경
.gitattributes의 merge=union은 채택하지 않았습니다.
왜
완화책이지 해결이 아닙니다. 서버 측 머지가 gitattributes의 merge driver를 존중하는지는 호스트 구현에 달렸고, 한쪽이 행을 추가하는 동안 다른 쪽이 같은 행의 상태를 바꾸면 중복 행이 남습니다. 충돌을 덜 나게 만들 뿐 날 수 없게 만들지 못합니다.
그래서
공유 파일을 쓰지 않는 쪽을 택했습니다. 남는 비용은 표시 지연뿐이고, 그것은 명령 한 번으로 해소됩니다.

원장을 생성물로

New

harness-team summary

변경
task 디렉터리를 스캔해 원장을 렌더링합니다. 인자 없이 실행하면 stdout으로 출력하고, --write는 파일을 갱신하며, --check는 낡았을 때 exit 1을 냅니다(mutation 없음, CI용).
왜
원장에 담긴 정보는 전부 task 디렉터리에서 계산할 수 있습니다. 두 벌로 유지할 이유가 없고, 두 벌이기 때문에 충돌했습니다.
그래서
표는 그대로 저장소에 남아 UI에서 보이고, 형식도 이전과 호환됩니다. 소비 프로젝트의 문서 대시보드가 docs/**/*.md를 파싱하므로 표·리스트 구조를 바꾸지 않았습니다.
Guard

--write는 기본 브랜치에서만

변경
feature 브랜치에서 --write를 실행하면 거부합니다(--force로 우회 가능). detached HEAD도 거부합니다.
왜
이 가드가 없으면 누군가 브랜치에서 한 번 실행하는 순간 방금 없앤 충돌이 그대로 되살아납니다. 명령을 만든 이유를 명령 자신이 지켜야 합니다.
그래서
원장 갱신 지점이 기본 브랜치 하나로 고정됩니다. git 저장소가 아닌 디렉터리에서는 브랜치 개념이 없으므로 그대로 씁니다.
Detail

기계 상태는 사람이 고치는 파일에 두지 않는다

변경
task별 <name>-meta.json이 created·status·closedAt을 갖습니다. SSOT 4파일에는 포함되지 않으며 손으로 고치지 않습니다.
왜
spec.md는 에이전트가 통째로 덮어쓰고 handoff.md는 post-commit hook이 다시 씁니다. 둘 중 어디에 frontmatter로 넣었어도 다음 세션에 유실됩니다.
그래서
harness가 읽어야 하는 값은 harness만 쓰는 파일에 있습니다. .json이라 docs/**/*.md를 읽는 도구의 파싱 대상에도 들어가지 않습니다.

과거 task를 잃지 않기

Migration

"파생 가능하다"는 검증 없이 믿을 수 없었다

변경
migrate가 원장을 읽어 meta.json으로 백필합니다.
왜
상태는 handoff.md의 — 완료 마커로 파생될 것처럼 보였습니다. 실측하니 한 저장소에서 원장의 ✅ done은 6개인데 마커는 4개뿐이었습니다. created는 더 나빠서, done이 인덱스의 - <name> (created …)를 - ✅ <name>으로 덮어쓰기 때문에 완료된 task는 원장이 유일한 출처였습니다.
그래서
백필 없이 전환했다면 과거 task가 전부 open으로, 날짜 없이 표시됐을 것입니다. 마이그레이션 입력을 코드 변경 전에 추출한 것이 이를 막았습니다.
Fixed

release가 자기 자신에게 복사하려다 멈추던 문제

변경
개발 저장소와 marketplace clone이 같은 디렉터리이면 marketplace 동기화를 건너뜁니다.
왜
메인테이너는 보통 clone 안에서 개발하므로 root === marketplaceDir이 됩니다. cp가 EINVAL (src and dest cannot be the same)로 던지면서, 매니페스트 4개와 cache는 이미 올라간 반쯤 적용된 트리가 남았습니다. 이번 0.16.0 릴리스에서 실제로 발생했습니다.
그래서
clone이 곧 source일 때는 옮길 것이 없으므로 조용히 넘어가고, 자기 자신을 stale이라고 경고하지도 않습니다.
Fixed

master 저장소를 feature 브랜치로 오인하던 문제

변경
origin/HEAD가 없으면 main과 master를 둘 다 기본 브랜치로 인정합니다.
왜
init.defaultBranch는 답이 될 수 없습니다. 대개 전역 설정이라 "새 repo를 만들 때의 선호"를 말할 뿐 이 저장소의 기본 브랜치가 아니고, main 선호를 가진 사용자가 master 저장소에서 작업하면 같은 오거부가 납니다.
그래서
로컬 전용 master 저장소에서도 --write가 동작하며, feature 브랜치 거부는 그대로입니다.

이번 릴리스가 택한 방향

공유 집계 파일은 병렬 작업의 구조적 충돌원이다

내용이 겹치지 않아도 삽입 위치가 같으면 충돌합니다. 집계는 파생으로 두고 각 작업이 자기 소유 파일만 만들게 하는 것이 유일한 구조적 해법입니다. 충돌 빈도를 낮추는 완화책과, 충돌이 날 수 없게 만드는 구조 변경은 다른 종류의 답입니다.

파생 가능하다는 가정은 실측으로 확인한다

이번에도 상태가 파생 가능해 보였지만 실제 저장소에서는 6 대 4로 어긋났습니다. 마이그레이션이 필요한지 아닌지를 결정하는 것은 설계의 우아함이 아니라 데이터입니다.
