1. 크루메이트 부트스트랩 — 워크트리에 들어가면 이 순서로

이 문서에서 발견한 실패는 전부 이 시퀀스에서 한 줄이 빠진 것이었습니다. 브리프에 그대로 붙여 넣어도 됩니다.

# 1. 워크트리 격리 확인 — 주 체크아웃에서 돌리면 즉시 멈춘다 (ship 브리프의 assertion)
git rev-parse --show-toplevel; test -f .git && echo "linked worktree OK"

# 2. 하네스 task 활성화 — .harness/active.json은 gitignore라 따라오지 않는다
#    docs/<user>/<name>/ 이 이미 있으면 '활성화', 없으면 md 5개 + <name>-meta.json 생성
harness-team task <name> --member <user>

# 3. 카드와 경계 확인
harness-team context check
harness-team boundary check        # 선언 없으면 not-configured로 통과

# 4. 작업 → 커밋 (plan 체크박스 갱신 포함)

# 5. handoff — 훅이 있으면 커밋 때 이미 돌았고, 없거나 확신이 없으면 직접
harness-team handoff

# 6. PR/MR 직전 문서 정합 (0.17.0) — spec·plan·artifact를 코드 현실과 맞춘다
#    /harness-ship 은 PR/MR을 만들지 않는다. "준비 완료" 보고에서 멈춘다.

# 7. 종결은 캡틴/배송 경로 승인 이후 (증거 가드 6종 + 선언 유효성을 통과해야 닫힌다 — §7)
harness-team done
🚫
워크트리에서 절대 돌리지 않는 것

harness-team apply · init · sync · migrate · upgrade · backup — 관리 구역(AGENTS.md 마커 섹션, .claude/, rules)을 재생성해 브랜치를 오염시킵니다. 하네스 적용은 별도 task의 일이고, 크루메이트의 기본 자세는 "이미 적용된 하네스를 쓴다"입니다.

0.16.0 이후 하나 더: harness-team summary --write. 원장은 기본 브랜치에서만 렌더합니다 — 피처 브랜치에서 쓰면 0.16.0이 없앤 병렬 충돌이 그대로 돌아옵니다. CLI가 기본 브랜치가 아닐 때 거부하지만(0.16.1에서 fail-open도 닫혔습니다 소스), --force로 뚫지 마세요. 확인만 필요하면 --check, 눈으로만 보려면 인자 없이 실행합니다.

2. 왜 이 순서인가 — 확인한 사실 4개

아래는 이 저장소의 소스와 실제 실행으로 확인한 것입니다. 표의 배지가 근거의 종류를 나타냅니다.

실측 실제로 실행해 확인 소스 하네스 소스 코드 문서 firstmate·Orca 문서
사실근거그래서 무엇을 해야 하나
.harness/active.json·config.json은 추적되지 않는다 .gitignore에 두 줄 모두 있고 git ls-files .harness는 빈 결과 실측 새 워크트리에는 활성 task가 없다 → 첫 명령이 harness-team task <name>
워크트리에서는 훅을 설치할 수 없다 연결 워크트리의 .git은 파일이고, installPostCommitHook은 .git/hooks 접근 실패 시 조용히 return 소스 실측 훅 설치는 주 체크아웃에서 1회. 워크트리에서 설치를 시도하지 않는다
그러나 훅은 주 체크아웃에서 공유 실행된다 워크트리에서 커밋 → 훅 발화, 그때 cwd는 워크트리(프로브 출력: HOOK FIRED in …/wt1), git rev-parse --git-path hooks는 주 체크아웃 경로 실측 에이전트 종류와 무관하게 커밋하는 누구에게나 발동한다(Claude 전용이 아니다). 다만 cwd가 워크트리이므로 handoff는 워크트리의 활성 포인터를 읽는다 — 없으면 주 체크아웃 handoff를 대신 고치지 않고 그냥 no-op이다
handoff는 포인터가 없으면 아무 일도 안 한다 runHandoffAuto가 readActive → null이면 즉시 return 소스 2단계를 건너뛰면 자동이든 수동이든 handoff는 갱신되지 않는다
🔁
운영 메모 한 줄 교정 — "왜"가 다르면 필요한 단계가 하나 늘어난다

firstmate data/learnings.md에는 "handoff 자동 갱신은 Claude Code 훅이라 다른 하네스 작업자에겐 발동하지 않으니 harness-team handoff를 직접 부를 것"으로 적혀 있습니다. 지시(직접 부르기)는 옳지만 이유가 다릅니다: handoff를 부르는 것은 git post-commit 훅이고, 위 실측대로 워크트리에서 커밋하는 어떤 에이전트에게도 발동합니다. Claude 전용인 것은 SessionStart(카드 주입)와 PreToolUse/PostToolUse 계열입니다.

차이가 중요한 이유: 진짜 원인은 활성 포인터의 부재이므로, 직접 부르기만으로는 부족하고 활성화가 선행되어야 합니다. 지금 브리프에는 그 단계가 없습니다 — §1의 2번 줄을 추가하면 닫힙니다.

부수 효과: docs/<user>/ 경로가 갈릴 수 있다

member 결정 순서는 --member → git config user.name → $USER → unknown이고, 이를 고정해 두는 .harness/config.json은 추적되지 않습니다. 같은 task가 다른 home·다른 호스트(secondmate)에서 활성화되면 docs/other-name/<task>/라는 두 번째 트리가 생기고, 두 트리는 서로를 모릅니다. 그래서 브리프는 --member를 못박습니다.

# 브리프에 넣을 형태 — 값은 프로젝트의 docs/<user>/ 와 정확히 일치해야 한다
harness-team task th-token-refresh --member chad

이 플래그가 항상 이기는 이유: user 결정은 config.json의 user를 먼저 보고 없으면 --member를 포함한 감지 순서로 내려가는데, 워크트리에는 그 config.json이 아예 없습니다 소스. 즉 워크트리에서는 --member가 유일한 확정 수단입니다.

3. 소유 경계 — 세 시스템이 각각 무엇을 소유하나

겹치는 것처럼 보이는 세 개가 실제로는 서로 다른 층을 소유합니다. 충돌은 대개 층을 착각할 때 생깁니다.

워크트리·터미널·조율 상태Orca워크트리 생성/해제 · 터미널 핸들 · Run/Task/Dispatch · worker_done·ask/reply·gate 문서

first mate는 프로젝트에 대해 읽기 전용입니다(hard rule 1) 문서. 그래서 하네스 문서의 수정도 크루메이트가 브랜치에서 합니다. 캡틴이 주 체크아웃에서 spec.md를 직접 고치면, 브랜치를 소유한 크루메이트와 같은 파일을 두 곳에서 쓰는 상태가 됩니다 — D4 위반이고 병합 충돌의 흔한 원인입니다.

4. firstmate 운용 — 브리프가 하네스를 가리키게 쓴다

브리프는 SSOT가 아니라 SSOT로 가는 포인터입니다. 요구사항을 브리프에 복사하면 spec과 브리프 두 개의 진실이 생기고, 크루메이트는 대개 브리프를 믿습니다.

브리프에 넣는 하네스 절

## 하네스 계약 (이 절이 요구사항의 정본을 가리킨다)

- 정본: `docs/chad/th-token-refresh/th-token-refresh-spec.md` (요구사항·Ontology·경계 계약)
- 단계: 같은 디렉터리의 `-plan.md`. 체크박스는 완료할 때마다 `- [x]`로 갱신한다.
- 첫 명령: `harness-team task th-token-refresh --member chad`
  # 활성 포인터는 gitignore라 이 워크트리에 없다. 이걸 건너뛰면 handoff·done이 조용히 무력화된다.
- 커밋 후: `harness-team handoff`
- 금지: `apply` / `init` / `sync` / `migrate` / `upgrade` / `backup` / `summary --write`
- PR/MR 직전: `/harness-ship` — spec·plan·artifact를 코드 현실과 맞춘다 (PR은 만들지 않는다)
- 완료 보고 전: `harness-team done`이 통과해야 한다
  # 6종: 미완 박스 · artifact 템플릿 · 미커밋 · 커밋 0개 · 테스트 미작성 · 리뷰 마커(spec opt-in)
  # + spec의 `## Done evidence` 선언이 깨져 있으면 그 자체로 차단된다 (조용한 폴백 없음)
  # 테스트가 불필요한 task면 {"tests":"skip"}을 선언한다 — 무시하지 말고 선언한다.

그 위에 이 저장소에서 이미 검증된 브리프 3절 패턴을 얹습니다 — 이미 확인된 사실(다시 조사하지 말 것) · 하지 말 것 · 검증(증거 없이 완료 처리 금지). 첫 절이 재조사를 막고, 둘째 절이 관리 구역 훼손을 막고, 셋째 절이 "보고서는 상세한데 산출물이 없는" 실패를 막습니다.

status 신호 ↔ 하네스 기록

firstmate의 status는 감독자가 움직여야 하는 사건만 적는 희소 채널이고, 하네스 문서는 다음 세션이 읽을 상태입니다. 둘은 같은 내용을 두 번 쓰는 게 아니라 역할이 다릅니다.

firstmate 신호언제하네스 쪽에 남기는 것
paused:스스로 풀릴 것으로 선언된 외부 대기TCC ## Now의 중단 조건 한 줄. capsule로 승격하지 않는다
blocked:firstmate가 움직여야 풀림TCC failure capsule(### F-00x) — Signal·Tried·현재 가설·다음 판별자·안전한 source 경로
needs-decision:ask-user 권한이 필요한 판단spec ## 결정에 D-초안(근거 + 재고 지점). 구현 작업자가 자기 발견을 스스로 결정하지 않는다 문서
done: PR <url> checks greenno-mistakes CI greenartifact ## 결과 + ## Reviews(파이프라인 판정·risk·조치)
done: ready in branchlocal-onlyartifact ## 결과. 병합 승인은 캡틴

paused:는 양방향으로 새는 신호입니다 — 끝나지 않을 대기를 "곧 풀릴 외부 대기"로 오분류한 사례가 있습니다 문서. 판정 기준을 한 줄로 적어 두면("무엇이 일어나면 풀리는가") 그 오분류가 눈에 보입니다.

배송 모드와 리뷰 소유권 — 리뷰를 겹치지 않는다

하네스 리뷰 프로토콜은 "중요한 변경엔 작성자와 분리된 리뷰"를 요구하고, firstmate는 "선택된 배송 경로가 자기 rigor를 소유하며 수동 리뷰를 겹쳐 쌓지 말 것"을 요구합니다 문서. 충돌이 아니라 모드별로 리뷰의 주인이 정해지는 것으로 읽습니다.

모드리뷰 주인## Reviews에 적는 것하지 않는 것
no-mistakes파이프라인파이프라인 판정 · risk 등급 · ask-user 결정과 조치 · PR URL/harness-review를 위에 덧붙이지 않는다 금지
direct-PR하네스 외부 리뷰가 유일한 리뷰/harness-review 요약·발견·조치(날짜) + 마커 한 줄파이프라인을 흉내내는 수동 게이트를 새로 만들지 않는다
local-only동일동일 + 병합 승인자와 시각가드 없는 저수준 merge 명령을 직접 부르지 않는다

어느 모드든 기록 없는 리뷰는 안 한 리뷰라는 하네스 규칙은 그대로입니다. Gemini 병렬 리뷰가 불가능한 머신에서는 "미실행" 사실을 남깁니다.

🔀
리뷰 커맨드가 엔진 중립으로 재편됐다 (0.17.0) — 그리고 기록이 기계 판독 대상이 됐다 (0.18.1)

이름은 /harness-review·/harness-adversarial-review이고, 엔진(codex·claude·gemini·custom)은 인수로 고릅니다. 옛 이름 /harness-codex-review·/harness-codex-adversarial-review는 deprecated alias로 살아 있지만 0.19.0에서 제거됩니다 — 브리프에 옛 이름을 박아 두면 그때 조용히 깨집니다.

0.18.1부터 /harness-review는 artifact ## Reviews에 <!-- harness:review kind=<engine> at=<ISO8601> --> 마커 한 줄을 append합니다. spec이 review: required를 선언한 task는 done이 이 마커를 찾습니다. 즉 리뷰를 돌리고도 기록하지 않으면 이제 종결이 막힙니다 — "기록 없는 리뷰는 안 한 리뷰"가 규범에서 가드가 됐습니다.

scout에는 하네스 task를 만들지 않는다

scout의 산출물은 data/<id>/report.md이고 워크트리는 scratch로 폐기됩니다 문서. 거기서 하네스 task를 만들면 폐기될 워크트리에 SSOT를 쓰는 셈입니다. 규칙:

  • scout 단계에서는 하네스 task를 만들지 않는다.
  • 구현이 별도로 승인되면 promote한 ship task에서 harness-team task <name>을 만들고, spec ## 참고에 리포트 경로를 인용한다.
  • 재현된 버그는 그 ship task의 회귀 테스트로 바뀐다 — 리포트에만 남기지 않는다.

5. Orca 운용 — 인계인가 감독인가를 먼저 가른다

이 갈래를 틀리면 잘못된 명령을 씁니다. 기준은 사용자가 감독을 요청했는지입니다 문서.

불변식: 1 Orca 워크트리 = 1 하네스 task = 1 writer

이것이 병렬 크루에서 D4(쓰기는 단일 스레드)가 살아남는 방식입니다. 병렬성은 워크트리 사이에 있고, 하나의 SSOT 범위 안에는 없습니다. 같은 task 문서를 두 워커가 만지게 하는 배치는 D4 위반이며, Orca는 충돌을 추론해 주지 않습니다 — 배치와 동시성은 호출자의 책임입니다 문서.

하네스 쪽Orca 쪽 대응주의
task 이름 <name>worktree --name, Task spec의 제목이름을 일치시키면 worktree list만 보고 어느 task인지 알 수 있다
spec = 요구사항 정본task-create --spec에는 경로 포인터만spec 본문을 복사하면 두 개의 진실이 생긴다
plan 체크박스워커의 status/heartbeatheartbeat는 살아있음의 증거이고 완료의 증거가 아니다
artifact ## 결과worker_done --outcome … --files-modified … bodybody에 artifact 경로를 적어 코디네이터가 증거를 열 수 있게 한다
done 가드 통과코디네이터의 수락 판단가드를 통과하지 못한 worker_done은 "완료"가 아니다
📎

플래그와 하위 명령은 이 문서가 아니라 바이너리가 소유합니다. 릴리스마다 바뀌므로 실행 전에 정본을 읽으세요: orca skills get orca-cli · orca skills get orchestration. 실행 전 orca status --json으로 reachable=true·state="ready"를 확인합니다.

6. 병렬 충돌 지도 — 어느 하네스 파일이 실제로 깨지나

0.16.0 이후 실제로 깨지는 파일은 하나입니다. 원장 2개가 생성물이 되면서 병렬 충돌의 주 원인이 사라졌습니다.

파일병렬에서 어떻게 깨지나해결
docs/<user>/<name>/*task별 디렉터리라 서로 닿지 않는다1 워크트리 = 1 task 규칙만 지키면 충돌 없음
docs/<user>/<name>/<name>-meta.jsontask별 파일이라 서로 닿지 않는다. 손으로 고치지 않는다 소스task·done과 migrate(과거 task 백필)만 쓴다 소스. 병합 충돌이 나면 실제 상태(status·closedAt)를 기준으로 고른다
docs/<user>/<user>-handoff.md매 커밋마다 전체가 덮어써진다(writeFile) → 브랜치마다 다른 내용 → 병합 시 거의 항상 충돌 소스. 0.18.1 기준 이것이 유일하게 남은 충돌원어느 쪽이든 취해 충돌을 닫고 harness-team handoff로 재생성한다. 손으로 병합하지 않는다
docs/task_summary.md더 이상 충돌하지 않는다 (0.16.0) — task·done이 이 파일을 건드리지 않는다 소스기본 브랜치에서 harness-team summary --write로만 렌더한다. 워크트리에서는 쓰지 않는다
docs/<user>/<user>-task.md동일 — 생성물이다동일
.harness/active.json추적되지 않아 충돌 자체가 불가능—
🧭

충돌을 줄이는 배치 규칙: 서로 다른 task는 서로 다른 워크트리에서, 같은 task의 후속 단계는 같은 워크트리에서. 파일이 겹치는 것 자체는 직렬화 이유가 못 됩니다 — 진짜 이유는 의미적 의존, 공유 가변 외부 상태, 양립 불가한 마이그레이션입니다 문서.

0.16.0이 무엇을 바꿨나: 예전에는 task가 원장에 행을 append하고 done이 그 행을 고쳤습니다. 모든 브랜치가 같은 줄을 건드리니 병렬 PR마다 충돌이 났고, 그 충돌을 손으로 푸는 과정에서 상태가 유실됐습니다. 지금은 상태가 task별 <name>-meta.json에 있고 원장은 그것을 스캔해 렌더합니다 — 충돌할 공유 상태 자체가 없어졌습니다. 이 문서가 예전에 "집계 파일 3개"라고 부르던 것은 이제 handoff 1개입니다.

7. 안전 — "확인 목적"으로 실행하면 안 되는 것

감독자가 상태를 확인하려고 프로젝트 명령을 돌리는 순간이 가장 위험합니다. --help가 없는 명령은 인자를 그대로 실행으로 받습니다.

🩹
harness-team release --help는 0.15.1에서 고쳐졌다 — 이제 usage만 출력한다

0.14.0까지 CLI는 help/--help/-h를 명령 위치에서만 처리했습니다. release 뒤의 --help는 평범한 boolean 플래그로 파싱됐고 bump는 taskArgs[0] || 'patch'로 결정돼, 실제 patch 릴리스가 수행됐습니다(매니페스트 4개 범프 + 캐시·마켓플레이스 동기화). 실제 사고 기록이 있습니다(2026-08-07) 문서.

0.15.1부터는 argv 어디에 있든 help로 해석돼 usage만 출력하고 명령을 실행하지 않습니다. 덤으로 오탈자 플래그(--dryrun 등)도 dispatch 전에 exit 2로 거부되고, 없던 harness-team --version이 생겼습니다 소스.

그래도 남는 규칙: ① 이 수정은 새 코드가 실제로 실행될 때만 유효합니다 — 아래 "두 채널" 카드대로 PATH의 harness-team이 옛 클론을 가리키면 옛 동작 그대로입니다. 확인은 harness-team --version으로 합니다(0.15.1 미만이면 이 명령 자체가 Unknown command로 떨어지는 것이 곧 신호입니다). ② 하네스 밖의 낯선 CLI에는 이 수정이 없습니다 — --help를 붙여 탐색하지 말고 소스·문서를 먼저 읽는 습관은 그대로 유지하세요. ③ 릴리스 절차는 MAINTAINING.md로 읽고 실행은 작업자에게 맡깁니다. 결과만 보려면 --dry-run입니다.

워크트리에서 금지

  • apply/init/sync — 관리 구역 재생성
  • migrate/upgrade/backup — 구조 이전은 별도 task
  • 하네스가 AGENTS.md를 소유한 저장소에서 fm-ensure-agents-md.sh 문서

두 채널을 따로 확인

릴리스는 전역 harness-team CLI를 갱신하지 않습니다 — 슬래시 커맨드 캐시만 새 버전이 되고, 훅이 부르는 전역 CLI는 마켓플레이스 클론에 묶여 옛 버전으로 남습니다 문서. 크루메이트가 신기능을 "없다"고 보고하면 먼저 harness-team doctor와 버전 채널을 확인하세요.

완료 판정은 증거로

  • 칸반·crew-state의 "done"을 병합 근거로 쓰지 않는다 문서.
  • 워커 보고서는 증거를 확인한다 — ls 한 번, 파일 한 번 열기. 상세하고 일관된 보고서가 산출물의 존재 증명은 아니다.
  • 반대로 워커가 스스로 신고한 간극은 대개 진짜다 — 확인하고 닫는다.
  • 하네스 쪽 증거는 done 가드 6종이다: 미완 박스 0 · artifact 내용 있음 · 미커밋 없음 · task 시작 이후 커밋 ≥ 1 · 소스가 바뀌었으면 테스트도 바뀜(0.18.1, 기본 ON — 문서·설정만 바뀐 task엔 발동하지 않는다) · spec이 review: required면 리뷰 마커 존재(0.18.1, spec opt-in).
  • 여기에 선언 유효성이 하나 더 붙는다 — spec의 ## Done evidence JSON이 깨졌거나 미지 키를 담고 있으면 그것만으로 차단된다 소스. 조용히 기본값으로 폴백하지 않는 것이 의도다(boundary check의 not-configured 전례).
  • 가드가 막는 것은 악의가 아니라 망각이다. --force로 뚫었다면 그 이유가 artifact에 있어야 하고, 없으면 그 done은 증거가 아니다.

8. 체크리스트

크루메이트 — 완료 보고 전

  • 워크트리 격리 assertion 통과했다
  • harness-team task <name> --member <user>로 활성화했다
  • plan 체크박스가 실제 상태와 일치한다(위장 체크 없음)
  • artifact ## 결과를 썼고, 모드에 맞는 ## Reviews를 남겼다 — /harness-review를 돌렸다면 마커 한 줄까지
  • context check green, boundary check pass 또는 not-configured
  • 소스를 고쳤다면 테스트도 고쳤다 — 불필요하면 spec ## Done evidence에 "tests": "skip"을 선언했다
  • 커밋했고 harness-team handoff가 handoff를 갱신했다
  • PR/MR을 열기 직전이라면 /harness-ship으로 spec·plan·artifact를 코드 현실과 맞췄다
  • status는 done: … 형식으로, 증거 경로를 포함해 보고했다

캡틴/코디네이터 — 병합 승인 전

  • PR이 전체 URL로 왔고 CI가 green이다(red 병합 금지)
  • diff에 task 문서 5종(+ <name>-meta.json)의 갱신이 들어 있다
  • artifact가 템플릿 그대로가 아니다 — 한 번 열어서 확인했다
  • <user>-handoff.md 충돌을 harness-team handoff 재생성으로 닫았다 (원장 2개는 0.16.0부터 충돌하지 않는다)
  • 병합 후 기본 브랜치에서 harness-team summary --write로 원장을 갱신했다
  • harness-team done이 --force 없이 통과했다(우회했다면 이유가 artifact에 있다)
  • 병합은 기록되는 경로로 했다(가드 없는 저수준 merge 금지)
