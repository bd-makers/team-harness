0.16.1은 0.16.0 직후의 외부 리뷰가 드러낸 결함들을 담은 patch 릴리스입니다. 시작은 리뷰 자체가 끝나지 않는다는 것이었고, 원인을 걷어내자 0.16.0이 놓친 결함 3건이 따라 나왔습니다. 그중 하나는 리뷰가 그 파일을 볼 수 없게 만들고 있었습니다.

리뷰가 돌지 않고 있었다

Root cause

codex exec는 stdin이 열려 있으면 기다린다

변경
commands/harness-codex-review.md와 harness-codex-adversarial-review.md의 모든 호출 예시에 < /dev/null을 넣고, 생략하지 말라는 경고를 달았습니다.
왜
프롬프트를 인자로 받았는데도 stdin이 열려 있으면 추가 입력을 기다립니다. 출력에는 Reading additional input from stdin... 한 줄만 남고 CPU는 0.01~0.04s에 멈춰 있습니다. 느린 것과 구별되지 않아서 기다리면 끝날 것처럼 보입니다. 실제로 리뷰 2건이 각각 38분과 63분을 그렇게 소모했습니다.
그래서
문서가 전파 경로였습니다 — 에이전트는 이 예시를 그대로 복사하므로 하네스를 쓰는 모든 프로젝트에서 같은 증상이 재발합니다. tests/sim/codex-agentloop.mjs는 이미 stdio: ['ignore', …]라 영향이 없었고, 그래서 아무도 눈치채지 못했습니다.

리뷰가 못 보던 파일

Fixed

NUL 한 바이트가 파일을 binary로 만들었다

변경
summary.mjs의 Map 키 구분자로 들어가 있던 리터럴 NUL 6개를 /로 교체하고 key() 헬퍼로 일원화했습니다. NUL 부재를 회귀 테스트로 고정했습니다.
왜
동작에는 문제가 없었습니다 — 구분자로서는 일관되게 작동합니다. 문제는 git이 파일 전체를 binary로 취급해 git diff가 Bin 0 -> 11223 bytes, --numstat이 - -를 내놓는다는 것이었습니다.
그래서
0.16.0의 핵심 신규 파일이 리뷰에서 통째로 보이지 않았습니다. 보이지 않는 것은 리뷰할 수 없습니다. 이 지적을 처음 확인할 때도 macOS grep -P 미지원 때문에 "NUL 없음"으로 잘못 판정했고, 바이트를 직접 세고 나서야 6개를 확인했습니다.

가드의 반대 실패

Fixed

--write 가드가 모를 때 열려 있었다

변경
"저장소가 아님"(쓴다) / "브랜치 확인 실패"(거부) / "브랜치 확인됨"(판정) 3-way로 나눴습니다. 저장소 여부는 두 번째 git 호출이 아니라 파일시스템에서 .git을 찾아 판정합니다.
왜
git 조회가 실패하면 branch === null이 되어 가드를 통째로 건너뛰고 원장을 썼습니다. git이 없거나 저장소를 읽을 수 없는 상황을 "브랜치가 없다"로 읽은 셈인데, 그때가 바로 어디에 있는지 모르는 상황입니다. 두 번째 git 호출로 저장소 여부를 물으면 깨진 git이 "저장소 아님"으로 위장합니다.
그래서
모를 때는 거부합니다. 브랜치 조회도 branch --show-current로 바꿔 커밋이 없는 새 저장소(unborn HEAD)를 정상 처리합니다 — 1차 수정은 그 반대 방향으로 틀려서 정상 케이스를 막고 있었습니다.
Fixed

심볼릭 링크를 지나면 같은 디렉터리가 아니게 된다

변경
release의 self-copy 판정을 path.resolve() 문자열 비교에서 realpath 비교로 교체했습니다.
왜
전역 CLI가 심볼릭 링크로 clone을 가리키는 구성이 흔합니다. source를 링크 경로로 열면 물리적으로 같은 디렉터리인데도 문자열이 달라 0.16.0에서 고친 EINVAL 중단이 되살아납니다.
그래서
이번 0.16.1 릴리스가 중단 없이 끝난 것이 그 경로의 실증입니다.

이번 릴리스가 택한 방향

멈춘 것과 느린 것은 구별해야 한다

CPU 0.04s로 63분을 보낸 프로세스를 "경합으로 느리다"고 읽었습니다. 경과 시간이 아니라 CPU 시간을 봤다면 1분 만에 알 수 있었습니다. 오래 걸리는 작업을 기다릴 때는 진행의 증거를 함께 확인해야 합니다.

검증 도구가 대상을 보고 있는지부터 확인한다

리뷰가 "문제 없음"을 말할 때, 그것이 대상을 보고 내린 결론인지 확인해야 합니다. binary로 취급된 파일, 실행되지 않은 테스트, 무한 대기 중인 프로세스는 모두 침묵을 통과로 위장합니다.
