재고 있던 자를

0.23.1은 0.23.0이 신설한 eager 계층 예산의 측정 범위를 고칩니다. 새 가드가 아니라 이미 있던 가드의 결함 수정입니다 — 검사는 매 세션 무조건 로드되는 계층을 잰다고 말하면서 정작 프로젝트 AGENTS.md+CLAUDE.md 두 개만 세고 있었고, 같은 계층인 프로젝트 .claude/CLAUDE.md와 사용자 전역 CLAUDE.md는 빠져 있었습니다.

결함은 “넘었다”가 아니라 “넘어도 못 본다”였습니다

0.23.0의 판단 — always-on 계층에 예산이 필요하다 — 은 그대로입니다. 틀린 것은 그 예산이 무엇을 세는지였습니다.

매 세션 로드되는 파일0.23.00.23.1
프로젝트 AGENTS.md측정측정
프로젝트 CLAUDE.md측정측정

넷은 서로 다른 계층이 아닙니다. 같은 계층의 서로 다른 파일입니다 — 넷 다 사용자가 아무것도 하지 않아도 매 세션 컨텍스트에 들어갑니다. 그런데 검사는 그중 둘만 보고 “eager 계층 크기”라는 이름을 달고 있었습니다.

성공의 척도가 아닌 것: 이 변경으로 특정 머신이 곧바로 노랗게 변하는지는 판단 근거가 아닙니다. 고친 것은 사각지대 자체이며, 검증은 CLAUDE_CONFIG_DIR로 fixture를 가리키는 결정론적 테스트가 담당합니다 — 실행 머신의 실제 홈 디렉터리가 아니라.

왜 파일별이 아니라 합계에 거는가

파일마다 임계를 따로 두면, 각 줄이 모두 green인 채로 합계만 예산을 넘어갑니다.

Fixed

측정 범위를 실제 상시 로드 집합으로

변경
EAGER_TIER_MAX_BYTES(24 KiB) 검사가 프로젝트 AGENTS.md·CLAUDE.md에 더해 프로젝트 .claude/CLAUDE.md와 사용자 전역 CLAUDE.md를 함께 셉니다. 예산은 넷의 합계에 걸립니다.
왜
넷 다 매 세션 무조건 로드되는 같은 계층인데 둘이 측정에서 빠져 있었습니다. 부분집합만 재는 검사는 “각 파일은 통과, 합계는 초과”를 green으로 통과시킵니다.
그래서
이 저장소에 고정된 몫은 15,968 B(AGENTS.md 11,079 + CLAUDE.md 4,889, .claude/CLAUDE.md는 없음)이고, 24 KiB 예산에서 8,608 B가 사용자 전역 파일 몫으로 남습니다. 이 수치로 예산을 정당화하지 마세요 — 전역 파일은 머신마다 달라 레포 실측은 상위집합의 부분집합일 뿐이며, 그 혼동이 이번에 고친 결함 그 자체입니다.
Fixed

경고 문구 — 내역·실제 경로·처방 순서

변경
경고가 파일별 내역과 전역 파일의 해결된 절대 경로를 함께 출력하고, 처방을 기여 바이트가 큰 계층부터 말합니다.
왜
CLAUDE_CONFIG_DIR이 설정된 머신에서는 전역 파일이 ~/.claude에 없으므로, 라벨만 봐서는 어느 파일을 열어야 할지 알 수 없습니다. 그리고 프로젝트가 10 B·전역이 24 KiB인 상황에서 “프로젝트 파일은…”으로 시작하는 처방은 초과를 만들지 않은 파일로 독자를 보냅니다.
그래서
경고는 이제 “무엇이 얼마나”와 “어느 파일부터”를 함께 답합니다. 크기만 보고할 뿐 자동 요약·삭제·LLM 편집은 여전히 하지 않습니다.

프로젝트 밖은 읽기만 합니다

전역 파일을 측정 대상에 넣는 것과, 그 파일에 조치를 지시하는 것은 다른 일입니다.

Changed

전역 파일에는 사실만, 프로젝트 파일에는 처방을

변경
프로젝트 파일에는 “절차를 lazy 정본(커맨드 문서·스킬)으로 옮기세요”가 붙고, 전역 파일에는 크기 사실만 보고합니다.
왜
전역 CLAUDE.md는 프로젝트 밖 사용자 소유입니다. 하네스는 프로젝트 디렉터리 밖에 쓰지 않으므로, 남의 파일을 어떻게 고치라고 지시할 자리가 아닙니다 — 조치는 사용자 판단입니다.
그래서
측정 범위는 넓히되 쓰기 경계는 그대로입니다. 넓힌 것은 보는 범위이지 건드리는 범위가 아닙니다.
Changed

없거나 못 읽으면 조용히 건너뜁니다

변경
전역 파일이 없거나 읽을 수 없으면(디렉터리인 경우 등) 그 항목만 빼고 기존 동작을 그대로 유지합니다. CLAUDE_CONFIG_DIR이 절대경로가 아니면 전역 항목을 건너뜁니다.
왜
전역 파일이 없는 것은 CI·컨테이너·새 머신에서 흔한 정상 상태이지 오류가 아닙니다. 그리고 상대경로 CLAUDE_CONFIG_DIR은 cwd 기준으로 풀려 프로젝트 CLAUDE.md를 이중 계산할 수 있습니다 — Claude Code 자신도 거부하는 값이라 같은 판단을 따랐습니다.
그래서
같은 이유로 해결된 경로가 겹치는 항목은 한 번만 셉니다 — config home 자체에서 doctor를 돌려도 같은 파일이 두 번 더해지지 않습니다.
Fixed

테스트가 실행 머신의 홈을 읽던 것

변경
서명을 checkEagerTierSize(targetDir, env = process.env)로 넓혀 테스트가 격리된 config home을 주입합니다. e2e·sim 샌드박스 env 빌더(tests/e2e/sandbox.mjs, tests/sim/agentloop.mjs, tests/sim/codex-agentloop.mjs)도 CLAUDE_CONFIG_DIR를 핀합니다.
왜
핀이 없으면 doctor status === 'success' 단언이 레포 밖 파일에 물립니다. 전역 CLAUDE.md가 없는 CI에서는 green인데, 그 파일이 큰 메인테이너 머신에서만 red가 됩니다.
그래서
기존 CLAUDE_PLUGINS_ROOT 핀과 같은 논리입니다 — 샌드박스는 레포 밖 상태에 의존하지 않아야 합니다. 이 결함은 외부 read-only 리뷰에서 발견·재현돼 반영했습니다.

이 릴리스가 남기는 것

부분집합을 재고 상위집합의 이름을 붙이지 않는다

0.23.0의 검사는 “eager 계층 크기”라는 이름을 달고 그 계층의 절반만 셌습니다. 이름과 측정 범위가 어긋나면, 검사는 없는 것보다 나쁩니다 — green이 “괜찮다”는 뜻이 아닌데 그렇게 읽히기 때문입니다. 예산을 파일별이 아니라 합계에 건 것도 같은 이유입니다. 컨텍스트 윈도우에는 “프로젝트 몫”과 “전역 몫”이 따로 없습니다.

보는 범위를 넓히는 것과 건드리는 범위를 넓히는 것은 다르다

전역 CLAUDE.md를 합계에 넣으면서도 하네스는 그 파일에 아무것도 지시하지 않습니다. 프로젝트 밖은 사용자 소유이므로 크기라는 사실만 보고합니다. 측정 범위를 넓힌다는 결정이 쓰기 권한을 넓히는 결정으로 미끄러지지 않도록, 처방을 계층별로 갈랐습니다.

샌드박스가 레포 밖을 읽으면 CI는 거짓으로 green이다

테스트가 실행 머신의 진짜 ~/.claude/CLAUDE.md를 읽고 있었습니다. 전역 파일이 없는 CI에서는 통과하고, 그 파일이 큰 메인테이너 머신에서만 실패하는 구조 — 가장 늦게 발견되는 종류의 결함입니다. 외부 read-only 리뷰가 이것을 잡았습니다. 같은 컨텍스트에서 자기 코드를 보는 눈이 놓치는 것을 별도 컨텍스트가 잡는다는 D6의 근거가 하나 늘었습니다.

검증

npm test 전체 스위트 통과 — unit·e2e에 이어 perf를 --test-concurrency=1로 격리 실행합니다. 새 doctor 테스트는 CLAUDE_CONFIG_DIR로 fixture를 가리켜 실행 머신과 무관하게 결정론적이며, config home이 target과 같을 때 같은 파일을 두 번 세지 않는다는 것까지 고정합니다.
