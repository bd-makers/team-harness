## 1. 정체성

**하나의 프로젝트에서 여러 팀원에게 같은 개발 사이클을 제공하는 하네스.**
**강제하는 것은 하나뿐이다**: PR을 올릴 때 그 task의 문서 — spec·plan·handoff·artifact — 를 담는다. 다이어그램은 권장이다 — 로직·구조 변화가 있으면 담는다(2026-10-06 정정, §4-6).
R1부터 PR 승인까지의 사이클(단계·산출물·게이트)은 기본으로 **제공**하지만, 개발 방식은 개발자마다 완전히 자유다(2026-10-05 메인테이너 설명).

- 사람은 루프 **안**에 있다(in the loop). spec과 plan 단계에 개발자가 직접 참여해 무엇을, 어떻게 만들지 먼저 인지한다.
- 티켓만 넣으면 끝까지 도는 완전 자동 루프(on the loop)는 목표가 아니다. 다만 그런 루프 하나를 **선택지로** 제공한다(주니어용 기본값).
- 원래 니즈 두 가지가 여전히 중심이다.
  1. 팀원이 무엇을, 어떻게, 어디를 바꿨는지가 산출물로 남는다(컨텍스트 스냅샷).
  2. 같은 지시 파일(`AGENTS.md`·`CLAUDE.md`)로 에이전트 결과물의 스타일이 비슷해진다.

참고한 1차 자료(같은 계열): OpenAI "Harness engineering"(2026-02, 실행 계획을 저장소에 커밋, 품질은 linter·CI로 기계 강제),
Anthropic "Effective harnesses for long-running agents"(세션 간 진행 산출물 인계).

## 4. 결정 (2026-10-05)

### 4-1. 세 검토 지점의 형태 (2026-10-05 피드백 반영)
세 지점은 묻는 것이 다르다. R1은 "원천 문서에 문제가 없나", R2는 "spec대로 만들어졌나", R3은 "코드가 좋은가"다.
- **R1 — 루브릭이 아니라 소스 검토 차단 게이트.** spec은 PRD·Figma·API 문서에서 나오고, 기획서·정책서가 더해질 수 있다.
  R1은 spec에 점수를 매기는 대신 **이 원천 문서들 사이의 충돌·누락·모순**을 근본적으로 검토한다.
  문제가 발견되면 사용자에게 고지하고, **해결된 뒤에만** Plan으로 넘어간다(해결 후 재검토).
- **R2 — 시나리오 ↔ 증거 대조 (§4-1b).** "Done evidence로 흡수"라는 이전 권장은 철회한다(피드백: R2에도 평가 방법이 있어야 한다).
- **R3 — PR 전 코드 리뷰 루브릭, 필수.** D2의 작성자·리뷰어 분리 그 자체다.
- 현재와의 차이: Ambiguity 게이트와 contrarian(A1–A4)은 **spec 문서 자체**를 본다. 원천 문서끼리의 정합성 검토는 아직 없다.
- **구현 (2026-10-06, task `r1-source-review`)**: `/harness-interview`가 채점 전에 R1을 돈다. 기록은 spec의 `## 원천 검토 (R1)` 절이다.
  충돌·모순은 `(unresolved)`, 누락은 `(open)`으로 적고 `→ 결정:`과 재대조 뒤 `검토 완료`로 닫는다. 미해결이 남으면 interview가 통과를 선언하지 않는다 —
  이 선언이 차단이고 기계 차단은 없다(D11). 원천 위치는 spec에 선언한다(kc-platform이면 `wiki/10_ssot/` 등 — 하네스는 분류를 정하지 않는다).
  contrarian 확장·외부 엔진 프레이밍·별도 커맨드는 기각·보류했다 — 사유는 그 task spec의 "기각한 대안".

### 4-1b. R2의 평가 방법 — TDD·BDD·Gherkin
셋은 대안이 아니라 층이 다르다.
- **BDD**는 합의 방식이다. S1에서 "무엇이 되면 완료인가"를 기획·개발·QA가 같은 시나리오 문장으로 합의한다.
- **Gherkin**은 BDD의 문장 형식이다. spec의 수용 기준을 Given / When / Then으로 쓴다. 이것이 R2가 대조할 단위다.
- **TDD**는 구현 습관이다. S3 자유 영역이라 사이클이 강제하지 않고, 기본 루프(§4-3)에서 권장만 한다.
- **권장**: spec의 `Done evidence`를 **시나리오 표**로 확장한다. 시나리오마다 증거(테스트 이름·명령)를 연결하고, R2는 4행으로 판정한다.
  1. [기계] 모든 시나리오에 증거가 연결돼 있다.
  2. [기계] 증거 명령이 통과한다(exit 0).
  3. [루브릭] 증거가 Then을 실제로 검증한다 — "테스트가 있다"와 "테스트가 시나리오를 증명한다"의 차이를 잡는다.
  4. [루브릭] spec 밖의 동작이 들어오지 않았다.
- 시나리오를 실행 가능한 테스트로 묶는 러너(Cucumber 등)는 스택별이므로 **프리셋 옵션**(§4-2)으로 둔다. 하네스가 강제하는 것은 형식과 대조뿐이다.
- 실행 시점은 R3와 같은 리뷰 호출 안에서 별도 절로 돌려도 된다(호출 비용 1회).
- **구현 (2026-10-06, task `r2-scenario-evidence`)**: "표"는 마크다운 표가 아니라 `## Done evidence` JSON의 `scenarios` 배열이다
  (증거 명령의 `|`가 표를 깨고, JSON 선언 파서를 공유한다). 1행은 선언 파서, 2행은 `harness-team scenario check`,
  3·4행은 `harness-team review <engine> --framing scenario`. exit 0은 필요조건일 뿐이다 — 이름 필터가 0건을 골라도 exit 0일 수 있어 3행이 막는다.
  `done`은 증거 명령을 실행하지 않는다(기각 사유는 task spec).

### 4-2. 언어별 템플릿을 하네스가 제공할 것인가
- **권장**: 제공하되 **코드가 아니라 데이터(프리셋)로** 제공한다.
  - 팀이 커밋하는 `.harness/gates.json`에 `commit: ["npm run lint", "npx tsc --noEmit", ...]`처럼 **명령 목록**을 둔다
    (구현 시 정정: 처음엔 `.harness/config.json`이었으나 그 파일은 사용자별 gitignore라 팀원마다 게이트가 꺼진다 — task `preset-gates` 리뷰).
  - init이 스택 감지 결과로 프리셋(node-ts, react-native, swift, python …)을 **제안**하고, 개발자가 확정한다.
  - 훅은 목록만 실행한다. 언어 분기가 훅 코드에 들어가지 않는다. 언어 추가는 프리셋 JSON 하나다.
  - RN rules도 같은 방식의 **rules 프리셋**으로 옮긴다(RN 감지 시 제안, 고정 배포 아님).
- 근거: #119에서 본 비용(127 비대칭, PM 5종 실측, yarn berry 예외)은 하네스가 "무엇을 돌릴지"를 **추론**했기 때문에 생겼다.
  명령을 명시적으로 선언하면 127은 "설정 오류"로 단순히 차단하면 된다.
- #119와의 관계: #119의 "package.json 스크립트 감지"는 node 프리셋 하나와 같은 동작이다. 프리셋 구조가 정해지면 그 안으로 흡수한다.

### 4-2b. 저장소 모양과 변경 감지 (2026-10-05 대화 반영)
현재 `src/detect-stack.mjs`는 루트 `package.json` 하나만 보고 스택 ID 하나를 고른다. workspace·turbo·nx 인식이 없다.

**init이 저장소 모양을 먼저 판별한다** — 판별은 휴리스틱이므로 결과를 보여 주고 확인을 받는다.

| 모양 | 판별 신호 |
|---|---|
| 단일 앱 | 루트 `package.json`만, workspace 없음 |
| 앱 + 내부 패키지 | workspace 있음, 앱은 하나 |
| 모노레포 | 앱 여러 개 + 패키지 여러 개 (`pnpm-workspace.yaml`, `workspaces`, `turbo.json`, `nx.json`, `apps/`·`packages/`) |

- 앱과 패키지 구분: 앱은 dev·start 스크립트나 next·expo 같은 프레임워크 의존성, 패키지는 `main`·`exports`.
- Node 밖(Cargo workspace, Gradle 멀티 프로젝트, Swift 멀티 패키지)은 첫 버전에서 "단일"로 두고 수동 지정을 받는다.

**package.json 등이 바뀌면 — 자동 갱신이 아니라 감지·제안**
- 프리셋은 개발자가 확정·수정한 값이라, 자동으로 덮으면 수정이 조용히 사라진다(D8 "커스터마이즈는 덮지 않는다").
- init 때 감지 결과의 **지문**(스크립트 이름 목록, workspace 목록)을 `gates.json`에 함께 저장한다.
- doctor 또는 커밋 훅이 현재 상태와 지문을 비교해 달라지면 알린다(예: "lint 스크립트가 추가됐습니다. gates를 갱신할까요?"). 갱신은 개발자가 확정한다.

**모노레포의 커밋 게이트 — 두 갈래**
1. **turbo·nx가 있으면 그 도구에 맡긴다(권장).** 영향 범위 계산은 그 도구가 이미 한다. 하네스가 다시 구현하면 #119 같은 두께가 또 생긴다.
   예: `{ "commit": ["turbo run lint typecheck test --filter=...[HEAD]"] }`
2. **도구가 없으면 경로별 목록.** 커밋 훅은 스테이징된 파일이 속한 workspace의 목록만 실행한다.
   예: `{ "commit": { "apps/mobile": ["npm run lint -w apps/mobile", "npm test -w apps/mobile"], "packages/*": [...] } }`

**따라오는 이점**
- RN rules 같은 rules 프리셋을 `.claude/rules`의 `paths:` 스코프로 해당 앱 경로(`apps/mobile/**`)에만 건다. 같은 저장소의 웹 앱에 섞이지 않는다.
- workspace 이름이 위키 area 키(`wiki/<area>.md`, §4-4)가 된다.

### 4-3. 기본 루프 — 오케스트레이터는 에이전트 자신 (2026-10-05 대화 반영)
- **원칙**: 기본 루프는 **Claude(또는 Codex)의 기본 기능만**으로 돈다. 서드파티 오케스트레이터나 개인 도구는 팀 하네스에 넣지 않는다.
  선택형이라 쓰지 않아도 사이클은 성립하고, 형태는 CLI 런타임이 아니라 **스킬(프롬프트) + 기존 CLI**(plan 체크·리뷰 엔진·커밋 게이트)다.
- **오케스트레이터의 개입 지점은 개발 단계(S3)부터다** (2026-10-05 피드백 반영). spec과 plan·다이어그램은 개발자가 직접 만든다 —
  에이전트의 도움은 받을 수 있지만 오케스트레이터 루프 밖이다. 이것이 "개발자가 무엇을, 어떻게 만들지 먼저 인지한다"는 원칙이다.
- **루프 모양**:
  1. [사람] R1 소스 검토 통과
  2. [개발자] plan과 다이어그램을 직접 만들어 확정한다. **확정 직후 묻는다: 오케스트레이터로 시작할까, 개별로 진행할까?**
     오케스트레이터 사용은 개발자마다의 판단이다. 개별로 진행하면 사이클의 어느 게이트에도 합류할 의무가 없다 —
     강제되는 것은 PR에 담기는 task 문서뿐이다(§1). 이전 초안의 "개별 진행은 QA에서 합류" 권장은 철회한다.
  3. **오케스트레이터 = 메인 세션**이 여기서부터 맡는다. 자동 구간: **Dev**(쓰기 담당 1명)가 plan 한 단계를 구현 →
     **QA**(읽기 전용, 별도 컨텍스트)가 커밋 프리셋 + R2 4행으로 판정 → 실패면 Dev로, 통과면 plan 체크 후 다음 단계
  4. 모든 단계 통과 → R3 리뷰(Codex 엔진, 없으면 Claude 엔진) → [사람] PR 승인
- **멈춤 조건**: 성공(모든 시나리오 + R3 통과, PR 생성은 사람) · spec 공백 발견(R1로 되돌려 사람에게 질문) ·
  진전 없음(같은 시나리오가 변화 없이 연속 실패, 횟수 상한은 임의로 두지 않는다) · 승인 필요(push·PR·파괴적 변경).
- **실행 수단 — 세션이 가진 것으로** (`probe → degrade → record`, 다이어그램 단계와 같은 계약):
  - **기본: 서브에이전트.** 모든 세션에 있다. Dev 1 + QA 1, 순차. D4(단일 쓰기)·D6(read-only 검증자)를 그대로 만족한다.
  - **있으면: Workflows.** 단계 사이 검증을 코드로 강제할 수 있다. 단, 사용자의 명시적 opt-in이 필요하다.
  - **있으면: Agent teams · cross-session messages.** 병렬 Dev가 필요할 때. 이때 각 Dev는 격리 worktree(D5)에서만 쓴다.
  - 세션에 없는 수단은 건너뛰고, 어떤 수단으로 돌았는지 artifact에 한 줄 남긴다.
- **Codex의 자리**: v1 권장은 **Codex = QA·R3 검증자**(엔진이 달라 자기 승인 편향이 없다). Codex가 없으면 Claude 엔진으로 대신한다
  (`harness-review`의 기존 codex → claude 폴백과 같다). Codex를 오케스트레이터로 쓰려면
  D2(drive = Claude)와 D9(Codex 강제력은 SessionStart만)를 먼저 고쳐야 한다 — 별도 결정.
- **워크트리 (2026-10-05 결정)**: 워크트리로 할지는 **task를 정의할 때** 정한다. 처음부터 워크트리 안에서 task를 만들면
  활성 task 포인터(`.harness/active.json`)와 문서가 그 워크트리에 생기므로 "워크트리로 넘어가면 task가 없다"는 문제가 생기지 않는다.
  작업 중간에 워크트리로 옮기는 세부 처리는 개발자가 Claude·Codex에게 직접 지시한다 — 하네스는 이를 위한 장치(포인터 복사 훅,
  브랜치 기반 자동 활성화)를 만들지 않는다. 하네스가 이미 하는 것은 워크트리 안에서 깨지지 않게 동작하는 것까지다(D5).
- **주니어용 장치**: 각 단계가 끝날 때 "무엇을, 왜 했는지" 한두 줄을 artifact에 남긴다. 머지 후 위키로 컴파일된다(§4-4).
- 조정할 기존 규범: README의 런타임 오케스트레이션 "의도적 비채택" 문구를 "서비스형 오케스트레이터는 비채택, 선택형 루프 스킬은 제공"으로 고친다.
- **확인(2026-10-06)**: codex-cli 0.159.2에 서브에이전트·병렬 실행이 있다 — 병렬이 기본이라 Codex 호스팅 루프는 실험적(`commands/harness-loop.md` "Codex" 절).

### 4-4. 프로젝트 지식 베이스 — task는 작업대, 위키가 기억 (2026-10-05 피드백 반영)
- 문제: task가 137개 쌓여도 전부 task 단위다. 이 형태로만 늘면 폴더가 끝없이 쌓이고,
  "이 기능(모듈)은 지금 어떻게 생겼고 왜 그런가"를 답하려면 여러 task를 다 읽어야 한다.
- **방향**: task 폴더는 **작업 중에만** 존재한다. PR 머지(또는 그에 준하는 단계) 이후 **LLM 위키 컴파일**로
  task의 결정·바뀐 모듈·학습을 **기능·모듈 단위 위키 항목**에 모으고, **task 폴더는 삭제한다.** 원문은 git 이력과 PR에 남는다.
- **위치는 최상위 `wiki/` 폴더**다(`wiki/<area>.md`). `docs/`는 사람이 쓰는 문서와 작업 중인 task가 사는 곳이라
  수명(영구 대 임시)과 독자(LLM 조회·인덱싱)가 다른 위키를 섞지 않는다. RAG 인덱싱 범위도 폴더 하나로 정해진다.
- 위키 항목은 원 task 경로가 아니라 **PR 번호·커밋**을 출처로 가리킨다(폴더가 사라지므로).
- **지우기 전에 옮겨야 할 것** (2차 장치 규칙 대상): summary 집계(`task_summary.md`)·`done` 판정·handoff가 지금 task 폴더를 읽는다.
  이들의 입력을 위키와 PR 기준으로 옮기거나, 필요 없어지면 뺀다.
- 원래 니즈 1(팀원이 무엇을 바꿨나)은 위키 항목의 작성자·PR 기록으로 이어진다.
- 컴파일 실행 위치는 기본 브랜치가 자연스럽다(지금 `summary --write`가 있는 자리, D5).
- **메인테이너 입력 (2026-10-06)** — kc-platform의 현재 형태다. **구조는 바뀔 수 있다.**
  ```
  wiki/
  ├─ index.md           시작 페이지와 주요 주제 링크
  ├─ 00_llm_wiki/       llm_wiki 관련
  ├─ 10_ssot/           원본 문서 정리 — PRD·기획서·정책서·Figma 등의 근거
  ├─ 20_domain/         도메인별 정리
  ├─ 40_data/  50_infra/  60_presentation/  70_monorepo/
  ├─ 90_system/         템플릿·작성 규칙·AI 편집 지침
  └─ 99_inbox/          미정리 메모·질문·링크
  ```
  문서 원천은 셋이다. ① **kc_vault** — 원본 SSOT(기획 미동결). 컴파일을 거쳐 성격에 맞는 위키 폴더로 옮겨진다.
  ② **`docs/*` 개발 문서** — task 문서(`docs/<area>/<user>/<task>/`, 예: `docs/kc-admin-web/chad/feature-00`) 포함, 위키로 통합된다.
  ③ **`wiki/*`** — LLM 위키 자체.
  **설계 함의(추론, C spec에서 확정)**: 폴더 분류가 바뀔 수 있으므로 하네스는 위키 분류 체계를 코드에 박지 않는다(D11 —
  프로젝트 데이터). 컴파일은 프로젝트의 `wiki/90_system/` 작성 규칙을 따르고, 분류하지 못한 것은 `99_inbox/`로 보낸다.
  `10_ssot/`는 R1 원천 문서 검토(§4-1)의 입력 자리와 겹친다.

### 4-5. migrate의 범위 (2026-10-05 결정)
- **migrate는 당겨 쓴다(pull).** 사용자가 필요할 때 해당 프로젝트에서 직접 실행한다. 하네스도 에이전트도 먼저 밀지 않는다
  (doctor는 실행했을 때 처방만 한다 — 지금 그대로).
- migrate에는 두 종류가 섞여 있다. **① 갱신 경로**(`refreshClaudeHooks`·`refreshClaudeTemplates`, init 마커 병합)는 영구 유지한다.
  **② 일회성 모양 변환** 13개(05–09월에 생김)는 상태 기준이라 실행할 때 해당 모양이 있으면 고치고 없으면 지나간다.
- **지원 창을 정책으로 두지 않는다.** pull이라 언제 누가 실행할지 모르므로, 날짜·버전 창보다 단순하게 간다:
  변환 단계가 유지비(테스트 깨짐·리팩터 방해)를 낼 때 그 단계를 지우고, 그보다 오래된 설치본은 재 init으로 안내한다(2차 장치 규칙).
- **정정**: 앞서 "버전 stamp(#118)로 sha 테이블을 대체 검토"라고 했으나 틀렸다. stamp는 설치 버전만 알려 주고 사용자가 파일을
  고쳤는지는 알려 주지 못한다. 대신 D8이 기각한 "설치 시점 sha 매니페스트"는 기각 근거(기존 설치본에 기준값 없음)가 재 init으로
  점차 사라지므로, 그때 D8 재검토 후보로 둔다.

### 4-6. 남은 확인 (2026-10-05 전부 결정)
- **강제 범위 (2026-10-05 확정)**: 순서는 기존대로 PR → 머지 → (기본 브랜치에서) `done`. `done` → PR로 바꾸는 안은 손볼 장치
  (머지 후 종결 절차·`remote-task.mjs`·done-on-main 안내)가 많아 기각. task 시작도 강제하지 않는다(지금의 SessionStart nudge 유지).
  lint·tsc·PR 전 로컬 리뷰는 '제공'이다. **PR에 spec·plan·handoff·artifact를 담는 것만 필수**이며
  (handoff는 커밋 훅이 자동 갱신하고, artifact는 머지 후 위키 컴파일(§4-4)의 재료다). 다이어그램은 권장이다(아래 다이어그램 결정).
- **PR 필수 문서 확인 (결정)**: 결정론적 CLI 검사 하나(`harness-team pr-check`)를 두고 호출처를 셋으로 한다.
  검사: spec·plan·handoff·artifact가 있고 비어 있지 않으며 템플릿 그대로가 아님. 다이어그램 파일도 생략 기록도 없으면 막지 않고 권장 안내만 낸다.
  호출처: ① ship 준비 보고 ② init이 설치하는 git pre-push 훅(post-commit 훅과 같은 방식) ③ 원하는 팀의 CI(같은 명령).
  하네스가 강제하는 유일한 것이라 확인 장치를 하나로 모은다.
- **다이어그램 (결정, 2026-10-06 정정)**: PR 다이어그램은 **권장**이다 — plan 단계에서 옵트인하지 않았어도 최종 변경이 로직·구조를 바꾸면 담는다.
  처음엔 "필수 + 생략 기록"이었으나 생략 기록 명령(`diagram record --skipped`)은 plan 옵트인이 없으면 거부해, 옵트인하지 않은 task는 통과할 길이 없었다.
  plan 단계 다이어그램은 선택(이해용) 그대로.
- **Cursor (결정)**: 쓰는 팀원이 있으므로 멤버와 cursor 미러를 **유지**한다. 앞선 기능 인터뷰의 "제외" 답은 무효.
- **auto-format (결정)**: 훅에 하드코딩된 `*.ts|*.tsx|*.js|*.jsx|*.json → npx prettier`는 4-2(언어 로직은 프리셋 데이터로)에 어긋난다.
  프리셋의 선택 항목 `format` 명령 목록으로 옮기고, 훅에서는 언어 분기를 뺀다.
- **sim·codex-sim·release (결정)**: 이 저장소 전용으로 돌린다. `.claude-plugin/plugin.json`의 commands 목록과 Codex 스킬에서 빼
  소비자 슬래시 메뉴에서 없애고, 파일은 이 저장소의 `.claude/commands/`로 옮긴다.
- **D11 배포 (결정)**: 결정 로그를 둘로 나눈다. **팀 운영 결정**(D2·D4·D5·D6)은 소비자에게 배포, **플러그인 결정**(D7–D11)은 이 저장소에만.
  고칠 곳: `templates/docs/decisions.md`, doctor `DECISION_HEADINGS`(`src/commands/doctor.mjs:472`), 동일성 테스트(`tests/agent-files.test.mjs:103`).
  확인 대상 헤딩이 줄어드는 방향이라 소비자에게 새 경고는 뜨지 않는다. 기존 설치본의 D8–D10 사본은 seed라 그대로 남는다(D8).

## 5. 범위 헌장 (요약 — 정본은 `docs/decisions.md` D11)

**D11 — 사이클에 봉사하는 것만 소유한다**

- **강제한다**: PR에 담기는 task 문서 — spec·plan·handoff·artifact. 이것만 막는다. 다이어그램은 권장(로직·구조 변화가 있으면 담는다).
- **제공한다**: 사이클 S0–S8의 산출물·게이트, 그리고 가로축(인계·팀 가시성·안전 가드·루프 건강·갱신 경로). 쓰든 말든 자유다.
- **소유하지 않는다**
  - **언어별 로직을 코드에**: 언어·도구 지식은 프리셋 데이터로만 둔다. 훅·CLI에 언어 분기를 넣지 않는다.
  - **구현 방식 강제**: 기본 루프는 선택형이다. 구현 단계는 자유다.
  - **사이클 밖의 편의 기능**: 파일 배치(백업 디렉터리 군) 같은 것.
  - **서비스형 런타임 오케스트레이터**, OS·네트워크 격리.
  - **개인 도구·서드파티 오케스트레이터에 대한 의존**: 메인테이너가 개인적으로 쓰는 도구의 규칙·가이드·설정을 팀 하네스에 두지 않는다.
    선택형 동반 플러그인은 핀·라이선스·없을 때의 동작을 명시한 경우만 허용한다(현재 `diagram-design`).
- **의도적으로 유지 (재론하지 말 것)**: 작은 수정도 full task다. 문서 대 코드 비율이 높은 것은 결함이 아니라 선택이다.
  다만 task는 작업대다. 머지 후 위키로 컴파일하고 폴더는 지운다(§4-4).
- **2차 장치 규칙**: 하네스의 다른 장치를 고치거나, 지키거나, 옮기거나, 보여 주기 위한 새 장치를 추가하기 전에,
  원래 장치를 빼거나 줄이는 안을 먼저 검토하고 기각 사유를 spec에 남긴다(D7의 일반화).
- **신규 기능 판정 질문**
  1. 사이클의 어느 단계(또는 가로축)를 위한 것인가? 답이 없으면 비범위다.
  2. 언어·도구별 지식이 필요한가? 그렇다면 코드가 아니라 프리셋으로 넣는다.
  3. 다른 하네스 장치의 결함·부작용 때문에 필요한가? 그렇다면 2차 장치 규칙을 적용한다.
