완료는 상태였지, 아무도 읽지 않는 상태였습니다
— meta.status의 정본화

0.32.0은 AI-Native SDLC 플레이북 비교에서 나온 Memory 계층 권고 — "완료 task 만료 없음" — 의 구현입니다. 한 줄짜리 권고라 두 갈래로 읽혔습니다: 시간이 지나면 만료되는 TTL이냐, 재활성화가 완료를 무효로 만드는 상태 전이냐. 코드를 먼저 읽었더니 실측 결함은 전이 쪽에서만 나왔습니다 — meta.status는 done이 쓰고 원장 렌더링만 읽는, 쓰이지만 정본이 아닌 필드였습니다. 그래서 작업 중인 활성 task가 원장에서 ✅ done으로 보였고, 열린 체크박스가 남은 채 닫힌 task가 영구히 재개 후보로 떴습니다. 이 릴리스는 TTL을 만들지 않고 그 필드를 읽게 만듭니다.

완료가 만료됩니다 — 시간이 아니라 전이로

"만료"의 정의가 이 릴리스의 절반입니다. 여기서 만료는 경과가 아니라 행위입니다 — done된 task를 다시 활성화하는 그 행위가 완료를 무효로 만듭니다.

Added

reopen 전이 — done → open

변경
harness-team task <name>이 status: "done"인 기존 task를 활성화하면 status가 open으로 돌아가고 closedAt이 풀리며 만료 시각이 새 키 reopenedAt에 남습니다. 출력은 activated:가 아니라 reopened:입니다 — 텍스트와 --json 엔벨로프의 summary 양쪽.
왜 TTL이 아닌가
지금 81개 task가 전부 done인 상태에서 시간 경과로 무엇이 실제로 나빠지는지 근거를 찾지 못했습니다. 반면 전이 쪽은 결함이 둘 있었고 재현됐습니다. 근거 없는 임계값은 곧 보정 부채가 됩니다.
그래서
작업 중인 활성 task가 원장에서 ✅ done으로 보이던 상태가 사라집니다. 열린 task 사이를 오가는 평범한 재활성화는 meta를 건드리지 않습니다 — 그쪽까지 쓰면 0.18.1이 고친 판정 창 오탐이 되살아납니다.
Added

레거시 task도 만료됩니다

변경
meta.json이 없는 구 task는 완료 상태가 원장·handoff에서 추론될 뿐입니다. 재활성화 시 그 추론값을 굳혀 만료시킵니다 — created는 원장에서 복원한 값을 보존하고, 알 수 없는 firstActivatedAt은 지어내지 않습니다.
왜 건너뛰지 않았나
처음엔 "레거시는 안 건드리는 것이 호환"이라 여겼습니다. 실측해 보니 레거시 설치에서는 이 기능이 통째로 없는 것과 같았습니다 — 재활성화해도 collectTasks가 계속 done을 냅니다. Codex 리뷰가 짚은 자리입니다.
그래서
호환성은 "안 건드림"이 아니라 같은 계약을 다른 증거로 지키는 것이 됩니다. 창 시작점을 모르는 것은 그대로 모르는 채 둡니다.

판정 창이 현재 라운드에서 시작합니다

만료 뒤의 완료는 새 라운드의 증거로 재야 합니다. 옛 firstActivatedAt을 그대로 쓰면 git log --since가 지난 라운드까지 훑어 "커밋 0개" 가드가 사실상 통과 전용이 됩니다.

meta 상태창 시작점왜
reopenedAt 유효reopenedAt현재 라운드의 시작. 만료 이전 커밋·리뷰 마커는 증거가 아닙니다
reopenedAt 없음firstActivatedAt한 번도 만료되지 않은 task — 0.18.1 이후 동작 그대로
reopenedAt 깨짐 · firstActivatedAt 유효firstActivatedAt으로 하강더 넓지만 유효한 창입니다. 창을 버리면 시각 가드가 전부 꺼집니다
둘 다 없음·깨짐없음(시각 비교 포기)구 task 경로 — 다른 시각으로 대체하지 않습니다
세 번째 행은 Codex P2의 결과입니다. 초안은 깨진 reopenedAt에서 창을 통째로 버렸습니다 — 인접 규칙(firstActivatedAt이 깨지면 degrade)과의 일관성이 근거였습니다. 그런데 그 규칙은 유효한 값이 하나도 없을 때의 규칙이지 덜 좋은 값이 남아 있을 때의 규칙이 아니었습니다. 창이 null이면 리뷰 마커 신선도·커밋 수·테스트 변경 가드가 전부 꺼집니다 — 손상된 기계 상태가 가드를 무력화하는 fail-open입니다. 테스트까지 잘못된 쪽을 고정하고 있었고, 리뷰어가 그것을 짚었습니다.

재개 후보 판정의 정본이 meta.status입니다

SessionStart의 재개: 후보는 plan.md에 열린 체크박스가 있는지 하나로 정해졌습니다. 완료 여부를 묻지 않았습니다.

Changed

status: done이면 후보에서 제외

변경
listIncompleteTasks가 task별 meta.json을 읽어 done인 것을 건너뜁니다. meta가 없거나 읽히지 않으면 제외하지 않습니다(구 task 하위 호환).
왜 문제였나
done --force로 닫았거나, 다이어그램 옵트인 규약대로 미실행 단계를 - [x] … — 미실행(도구 없음)이 아니라 열어 둔 채 닫은 task는 영구히 후보로 떴습니다. nudge의 신호가 그만큼 묽어집니다.
그래서
만료된 완료는 status가 open으로 돌아갔으므로 다시 후보가 됩니다 — 같은 필드 하나로 양방향이 일관됩니다.

비용은 task당 작은 JSON 읽기 1회입니다. done task는 plan.md의 readFile·stat을 건너뛰므로 순증가는 미미합니다 — 리뷰어의 실측으로 82개 task 스캔이 약 35 ms였습니다.

P2active.json을 meta보다 먼저 써서 부분 실패 시 "활성인데 원장은 done"이 남는다순서 확인 — 진짜만료를 먼저 굳히고 활성 포인터를 옮김. 실패 시 남는 상태가 "아직 done·미활성"이라 재실행이 이어받습니다

P3artifact의 EOF 빈 줄로 git diff --check가 exit 2재현 — 진짜제거(현재 exit 0)

반영하지 않은 것도 있습니다 — fsx.writeText의 비원자적 쓰기(P2와 함께 언급). 이 변경 이전부터 done·task 양쪽에 해당하는 기존 성질이라 범위 밖으로 두고 artifact에 남겼습니다.

배운 것 — 쓰이지만 읽히지 않는 필드

meta.status는 done이 쓰고 원장 렌더링 하나만 읽었습니다. 소비처가 하나뿐인 상태값은 그 상태가 거짓이 되는 경로를 의심할 자리입니다 — 아무도 읽지 않으면 틀려도 아무 일이 일어나지 않고, 그래서 조용히 틀린 채 남습니다. 결함 둘이 정확히 그 형태였습니다.

가드에서 "모르면 포기"는 fail-open입니다. 창 시작점이 깨졌을 때 창을 버리는 쪽을 골랐고, 근거는 인접 규칙과의 일관성이었습니다. 그 규칙은 유효한 값이 하나도 없을 때의 규칙이었는데 덜 좋은 값이 남아 있을 때에 적용한 것입니다. 판정을 포기하는 분기를 쓸 때는 포기 대신 내려갈 수 있는 값이 정말 없는지를 먼저 봅니다. 덧붙여 — 동사를 늘리면 그 동사로 분기하는 문서를 찾아야 합니다. reopened:를 추가하면서 다이어그램 옵트인 규칙이 created:/activated: 둘로만 갈리는 것을 놓칠 뻔했습니다.
