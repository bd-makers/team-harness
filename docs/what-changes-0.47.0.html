Added · #132

R1 원천 문서 검토 — /harness-interview 안 단계

원인
Ambiguity 게이트와 contrarian은 spec 문서 자체만 봤습니다. spec이 뽑아 온 원천(PRD·Figma·API 문서·기획서·정책서)끼리 어긋나도 채점은 통과했습니다.
지금
새 spec 템플릿에 ## 원천 검토 (R1) 절(### 원천·### 발견)이 생깁니다. interview가 채점 전에 원천을 맞대어 충돌·모순은 (unresolved), 누락은 (open)으로 기록하고, 사용자 결정(→ 결정:)과 재대조 뒤 - 검토 완료: <날짜>로 닫습니다. 원천이 없으면 - 없음 — <사유>.
차단
R1 기록이 없거나, R1 절에 미해결 발견이 있거나, spec 어디든 (unresolved)가 남으면 interview가 통과를 선언하지 않습니다 — /harness-spec이 이미 표기하던 소스 충돌을 읽는 게이트가 처음 생겼습니다. 기계 차단은 없습니다.
유지
기존 task의 spec은 그대로 두고, interview가 절이 없으면 만들어 채웁니다. 원천 위치는 프로젝트 데이터라 하네스가 정하지 않습니다. 외부 엔진 프레이밍(--framing sourcecheck)은 보류했습니다 — read-only 엔진은 Confluence·Figma MCP에 닿지 않습니다.
Added · #133

R2 시나리오 ↔ 증거 대조 (옵트인)

선언
spec ## Done evidence JSON에 scenarios 배열(id·given·when·then·test·cmd)을 둡니다 — 수용 기준을 Given/When/Then으로 쓰고 시나리오마다 증거를 잇습니다. 키가 빠지거나 비었거나 id가 겹치면 선언이 invalid라 done이 막힙니다(1행: 증거 연결).
기계
harness-team scenario check가 각 cmd를 /bin/sh -c로 실행해 exit 0을 봅니다(같은 명령은 1회, 2행). 출력은 boundary check와 같은 계약 — not-configured·pass (N checked)·failed + failure: 줄, 실패 시 exit 2.
루브릭
harness-team review <engine> --framing scenario(kind <engine>-scenario)가 증거가 Then을 실제로 검증하는지, spec 밖 동작이 없는지를 봅니다(3·4행). exit 0은 필요조건일 뿐입니다 — 이름 필터가 0건을 골라도 exit 0이 나므로 3행이 그 틈을 봅니다.
가드
시나리오를 선언한 task에서 verify: required는 -scenario kind만 검증 증거로 셉니다. done은 증거 명령을 실행하지 않습니다 — 그것은 scenario check 몫입니다.

선택형 기본 루프 — /harness-loop

서비스형 런타임 오케스트레이터는 여전히 채택하지 않습니다. plan을 확정한 뒤 개발자가 고를 수 있는 루프 하나를 명령 문서로 제공합니다.

Added · #134

plan 단계마다 Dev → QA → 로컬 커밋

흐름
메인 세션이 오케스트레이터가 되어 plan 단계마다 Dev(서브에이전트, 단일 쓰기, 커밋 금지) → QA → 로컬 커밋을 순차로 돌립니다. QA는 기계 검사(gate commit·boundary check·scenario check + 테스트 이름이 찍힌 출력 기록)이고, 모든 단계 뒤 read-only review --framing scenario와 R3 리뷰가 이어집니다.
멈춤
성공 · spec 공백 · 진전 없음(실패 집합 동일 + diff 무변화, 횟수 상한 없음) · 승인 필요. push·PR은 하지 않습니다.
범위
루프 전용 CLI는 없습니다 — 명령 문서가 기존 CLI를 엮습니다. Codex 래퍼 skills/harness-loop가 있고, Codex가 오케스트레이터를 맡는 경로는 실험적입니다. README의 설계 스코프 문구를 "서비스형 오케스트레이터는 비채택, 선택형 루프는 제공"으로 정정했습니다.

Added · #135 · #136

머지된 task → 최상위 wiki/ 항목

언제
머지 후 종결 절차에서 done 다음, summary --write 전에 /harness-wiki <user>/<task>를 돌리고 같은 종결 커밋에 담습니다. 선택 단계입니다.
입력
새 하위 명령 harness-team wiki sources [<user>/<task>] [--pr <N>](읽기 전용)가 기본 브랜치 first-parent 이력에서 PR 번호(GitHub·GitLab 머지 형식)·커밋·작성자를 추론하고, 출처 마커 <!-- harness:wiki task=… pr=… commit=… author=… at=… -->, 이미 컴파일된 위치, wiki/90_system/ 작성 규칙 파일, 막힘(not-done·no-pr·no-commit·shallow-history)을 냅니다. 얕은 클론은 출처를 추측하지 않고 막습니다.
분류
분류 체계는 코드에 없습니다 — 프로젝트의 wiki/90_system/ 규칙을 따르고, 규칙이 없거나 분류하지 못한 것은 wiki/99_inbox/로 갑니다. 같은 task를 다시 컴파일하면 멈춥니다(명시 요청 시 그 단락만 교체).
위험
위키 본문은 종결 커밋으로 PR 리뷰 없이 기본 브랜치에 들어갑니다(수용됨) — 단락마다 PR·커밋 출처가 남아 원문 대조가 가능합니다. 릴리스 전에 #136이 인용문·목록 안 펜스의 예시 마커를 컴파일 흔적으로 세던 문제를 고쳤습니다 — 작성 규칙 문서가 예시를 그렇게 쓰면 task가 compiled로 잡혀 영영 컴파일되지 않았습니다.
