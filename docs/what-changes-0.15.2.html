0.15.2는 하나의 조용한 실패를 드러내는 patch 릴리스입니다. installed_plugins.json은 새 버전을 가리키는데 훅과 터미널은 옛 코드로 실행되고 있었고, 아무 신호도 없었습니다. 0.15.1 직후 실제로 전역 CLI가 0.14.0이었고, 그래서 0.15.1이 고친 --help 가드가 없는 채로 harness-team release --help가 또 진짜 릴리스를 수행했습니다.

플러그인은 세 곳에 있다

릴리스 뒤 이 플러그인은 서로 다른 세 위치에 존재하고, 갱신 주체가 각각 다릅니다. 이 구조를 몰랐다는 것이 사고의 뿌리입니다.

핵심: Claude Code는 cache에서 커맨드·스킬을 읽지만, SessionStart·post-commit 훅과 터미널은 PATH의 harness-team을 실행합니다. 그 바이너리는 보통 marketplace clone을 가리키는 심볼릭 링크이고, release는 clone의 카탈로그만 갱신합니다. 그래서 셋이 조용히 어긋납니다.
Root cause

자기모순 상태가 된 clone

변경
MAINTAINING.md에 세 위치(버전별 cache = 설치본, marketplace clone = 카탈로그, PATH 바이너리)와 갱신 주체를 표로 명시하고, 릴리스 절차에 harness-team --version 확인 단계를 추가했습니다.
왜
release는 clone의 marketplace.json과 commands/만 덮어씁니다. clone의 코드는 /plugin marketplace update(= git pull)가 갱신합니다. 그 사실이 어디에도 적혀 있지 않아, clone이 옛 커밋에 멈춘 채 버전만 새 값이 되는 상태가 몇 주씩 유지될 수 있었습니다.
그래서
어디를 갱신해야 훅이 새 코드로 도는지가 문서에 남습니다. 릴리스 절차의 마지막 단계가 그것을 확인합니다.
Rejected

전역 CLI를 cache에 링크하지 않는다

변경
설치 대상은 marketplace clone 그대로 둡니다. hookCliInstallCommand의 형태도 바꾸지 않았습니다.
왜
cache 경로는 버전별(…/0.15.1/)이라 심볼릭 링크가 그 버전에 영구히 고정됩니다. 드리프트가 사라지는 게 아니라 방향만 바뀌고, 다음 릴리스마다 재설치가 필요해집니다.
그래서
clone이 안정적인 링크 대상이라는 판단은 유지하고, 결함을 링크 대상이 아니라 "clone의 코드를 아무도 갱신하지 않는다"로 규정했습니다.

두 지점의 신호

드리프트가 생기는 순간(릴리스)과 그것을 발견해야 하는 순간(진단), 양쪽에 신호를 넣었습니다.

release

낡은 clone을 알린다

변경
카탈로그 동기화 뒤 clone의 package.json 버전을 방금 자른 버전과 대조해, 다르면 ⚠️와 next: 힌트를 냅니다. JSON 모드에서는 next_actions에 실립니다.
왜
부분 갱신 자체는 의도된 동작입니다 — 남의 checkout을 대신 pull 하는 것은 이 명령의 일이 아닙니다. 문제는 부분 갱신을 하고도 조용했다는 점입니다.
그래서
release는 clone을 건드리지 않으면서, 자기가 만든 불일치를 그 자리에서 말합니다. 이 릴리스(0.15.2)를 자르는 순간 실제로 발화했습니다.
doctor

global CLI version drift 검사

변경
PATH harness-team --version과 installed_plugins.json의 설치 버전을 대조해 다르면 경고합니다. plugin-dev 저장소에서도 실행됩니다.
왜
주변의 소비자 전용 검사들은 plugin-dev에서 skip되는데, 그 근거("소비자의 훅 배선은 소스 저장소에서 증명할 수 없다")는 드리프트에 전이되지 않습니다. 전역 CLI와 소스 트리가 가장 크게 벌어지는 곳이 메인테이너 머신이고, 이번 사고도 거기서 났습니다.
그래서
"낮으면"이 아니라 "다르면"으로 판정합니다 — 설치본보다 새로운 PATH CLI도 드리프트입니다. 순서 비교는 --version이 도입된 0.15.1 한 곳에서만 해서, --version에 답하지 못하는 CLI를 결론지을 때만 씁니다.

doctor 결론 정정

새 경고를 붙이자, doctor가 오래전부터 자기 경고를 스스로 지우고 있었다는 사실이 드러났습니다.

Pre-existing

⚠️ 직후의 All checks passed

변경
텍스트 모드와 JSON 모드가 같은 경고 카운터를 공유합니다. 경고가 있으면 N warning(s).으로 끝냅니다.
왜
텍스트 모드의 집계가 checks 배열을 읽었는데, 그 배열은 JSON 모드에서만 채워집니다. 그래서 항상 0이었고, ⚠️를 출력한 직후 초록 결론이 찍혔습니다 — 같은 실행의 JSON은 status: "warning"이었으니 두 출력이 서로 어긋났습니다.
그래서
드리프트와 무관한 선행 결함이고 모든 경고 경로에 있었습니다. 새 검사가 그 모순을 눈에 띄게 만들었을 뿐입니다.
Codex review

실행 실패를 나이로 오독하던 문제

변경
readPathCliVersion에 unknown 상태를 추가했습니다. ENOENT·EACCES는 missing, 타임아웃·exit 127·비숫자 코드는 unknown, 평범한 non-zero exit만 legacy입니다. 버전 파싱도 출력에서 semver를 추출하도록 바꿔 v0.15.1 오탐과 0.15.2-rc.1 누락을 없앴습니다.
왜
초안은 ENOENT 외 모든 실행 실패를 "0.15.1 이전 CLI"로 보고했습니다. 권한 오류나 #!/usr/bin/env node 래퍼가 node를 못 찾은 경우(exit 127)는 바이너리가 답을 못 한 것이지 오래된 것이 아닙니다. Codex read-only 외부 리뷰가 지적했습니다.
그래서
실행되지 못한 바이너리를 침묵으로 나이 매기지 않습니다. 리뷰 지적 4건은 모두 반영했고 기록은 task artifact의 ## Reviews에 남겼습니다.

이번 릴리스가 택한 방향

두 교훈 모두 "통과했다"가 "옳다"의 증거가 아니라는 같은 이야기입니다.

가드를 넣는 것과 가드가 도는 것은 다르다

드리프트 검사를 주변 검사들과 같은 plugin-dev 분기에 넣었다면, 사고가 난 바로 그 머신 상태에서 skip됐을 것입니다. 기존 분기가 이 저장소에서 어떤 상태를 내는지 먼저 실행해 확인한 뒤 배치했습니다.

살아남은 mutation은 테스트가 그 코드에 닿지 않는다는 뜻

unknown 분류를 제거하는 mutation이 잡히지 않았습니다. 가드가 불필요해서가 아니라, 테스트가 잘못된 shebang으로 그 분기를 노렸는데 macOS가 그것을 ENOENT로 돌려줘 다른 분기로 빠졌기 때문입니다. exit 127로 바꾸니 잡혔습니다. 같은 이유로, 개발 머신의 실제 ~/.claude를 읽던 테스트는 로컬에서 통과하고 CI에서 실패했습니다 — 이제 비교의 양쪽을 모두 fixture로 줍니다.
