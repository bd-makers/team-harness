Q10.13에서 루프·그래프·워크플로우가 자체 기능으로 가능한가?

아니요 — 셋 다 하네스 자체 기능으로는 없다. 구조적으로 의도된 부재다.
항목자체 지원실제로 있는 것
루프 없음 스케줄러·데몬·watch 없음. hooks 4종(SessionStart·post-commit 등) + 1회성 CLI 명령뿐
그래프 없음 DAG 엔진 없음. plan.md는 순차 체크리스트, boundary check는 두 스키마의 1:1 대조, Mermaid는 문서 생성용
워크플로우 없음 templates/.claude/에 workflows/ 배포 없음. 문서의 "워크플로우"는 task→spec→plan→done이라는 규범적 절차를 뜻하는 말

이유: 0.12에서 하네스를 "설정·상태 하네스"로 재정의하며 런타임 오케스트레이터 역할을 명시적으로 버렸다(AGENTS.md D4). 실행 레이어는 호스트(Claude Code)의 /loop·cron·Workflow 도구가 맡는 구조다.

가능한 조합은 "하네스 명령을 호스트 기능에 얹는 것"이다 — 예: /loop 30m /harness-doctor. doctor가 read-only·결정론적이라 루프 대상으로 안전하기 때문.

Q2그럼 확장할 필요가 있는가?

기각 유지 (D1), 재검토 트리거 없음. 2026-08-06 결정이 여전히 유효하고, 0.13이 "발동 갭"을 닫으면서 근거가 오히려 강해졌다.

용어부터 — 범주 오류 (D1 근거 1)

"loop/그래프 엔지니어링"은 2026-07 커뮤니티 조어다. Anthropic 어휘로 옮기면 graph와 workflow는 같은 것이라 3형제(task loop/task graph/task workflow)의 셋째 자리에 들어갈 독립 개념이 없다.

커뮤니티 조어Anthropic정의
loop engineeringagentLLM이 스스로 프로세스·도구 사용을 지휘
graph engineeringworkflow미리 정의된 코드 경로로 오케스트레이션 (+5패턴)
harness engineeringharness세션을 가로지르는 상태 구조

D1 기각 근거 4

  • 범주 오류 — 위 표. 실제 층은 harness → agent/loop → workflow=graph 3층.
  • task는 이미 harness 층 산출물 — spec↔feature list, plan↔progress 파일, session-context↔세션 시작 프로토콜, done-guard↔"declares victory too early" 방어. loop/graph 형제를 만들면 층을 섞는다.
  • graph(런타임 오케스트레이션)는 7/28에 이미 기각 — 1차 소스 6종 (Anthropic×2·OpenAI·Cognition·Karpathy·12-Factor)이 병렬 작성자 토폴로지를 신뢰성 위험으로 봄. 호스트 Workflow 도구가 이미 제공하므로 재구현은 플랫폼 중복.
  • 비용 명백 — task당 4→7파일, 매 세션 읽을 문서 배가. "smallest set of high-signal tokens" 위배.

핵심 반전 (D2) — 진짜 갭은 "형태"가 아니라 "발동"이었다

probe 실측 결론: "loop는 트리거할 필요가 없고(훅이 자동), workflow는 트리거할 방법이 없다(진입점 부재)." 그래서 확장 대신 발동 갭 3건을 메웠고 — 그게 그대로 0.13이 됐다. 확장이 필요해 보이던 증상의 원인이 고쳐졌으니 확장 논거는 더 약해졌다.

재고 조건 3 — 오늘(2026-08-08) 기준 대조

D1을 다시 여는 조건현재
에이전트 간 통신·컨텍스트 공유가 성숙해 Cognition의 반대 근거(중간 결정 비가시성)가 무너질 때 미성립 병렬 작성자 회피가 여전히 프론티어 공통 권고

유일하게 D1을 건드리지 않는 확장은 "workflow 템플릿 배포" (실행이 아닌 설정 배포)지만, 이것도 구체적 수요 전에는 만들 이유가 없다.

Q3활용법 — 단계별 프롬프팅 플레이북

0.13부터 task 생성 stdout이 이 체인을 안내한다: spec 작성 → /harness-interview → 구현 → 테스트 → 리뷰 → /harness-retro → done. 프롬프팅은 이 체인에 맞춘다.

단계프롬프트 예발동되는 것
시작/harness-task new feature auth-refresh + 요구사항 2~3문장 4파일 + TCC 생성, 다음 단계 안내 출력
spec 검증/harness-interview 소크라테스식 질문으로 숨은 가정 노출
plan 다듬기/harness-contrarian → /harness-simplifier 가정 반박 → 단계 축소
구현"plan §1부터 진행해줘" boundary check(선언 시) + 체크박스 갱신
테스트/harness-unittest (UI: comptest / 프로세스 경계: inttest) GWT 강제 + 커버리지
리뷰"Codex 리뷰 돌려줘" → Bash codex exec --sandbox read-only (AGENTS.md 공식 호출 방식) 또는 워크플로우 명시 요청 (아래). 플러그인의 /codex:review·/codex:adversarial-review는 disable-model-invocation이라 터미널 대화형 세션 전용 — 앱 세션에서는 못 쓴다 Codex read-only 리뷰 → artifact ## Reviews 기록. Gemini는 gemini -p CLI 설치 시에만 병렬 실행, 미설치면 미실행 사실을 기록
종결"retro 남기고 done 처리해줘" /harness-retro append → done-guard 4중 확인

규칙 4

  • plan 단계 번호로 지시한다 — "§2 해줘"면 충분. 요구사항을 프롬프트에 다시 쓰지 않는다. SSOT는 spec/plan, 프롬프트는 포인터. 재개 세션도 SessionStart 훅이 TCC를 주입하므로 "이어서 해줘"면 된다.
  • Workflow는 명시적 단어가 필요하다 (옵트인 규칙) — "이 변경을 워크플로우로 리뷰해줘 — 정확성·엣지케이스·보안 3차원 fan-out, 검증 통과분만 artifact ## Reviews에 기록"
  • 루프도 명시적으로 — /loop 30m /harness-doctor (무결성 감시), PR 후 "/loop 10m CI 상태 확인하고 실패하면 고쳐줘"
  • 병렬은 읽기에만 (D4) — "병렬로 조사·리뷰해줘"는 되고, "병렬로 고쳐줘"는 안 된다. 쓰기는 항상 메인 세션 순차.
