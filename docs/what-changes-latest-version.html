이미 커밋한 구현까지 봅니다

--scope 없이 돌린 harness-team review는 하네스 기록 파일 밖의 미커밋 편집이 하나라도 있으면 worktree scope를 고릅니다. 그런데 프롬프트는 "working tree changes"만 가리켜, 리뷰어는 HEAD 대비 미커밋만 봤습니다. 구현을 커밋한 뒤 문서를 손보다 돌린 R2·adversarial은 커밋된 구현을 통째로 놓친 채 증거로 기록됐습니다. 0.49.2의 worktree는 base와의 merge-base 대비 작업 트리 전체입니다.

왜 patch인가 — 증거로 기록된 리뷰가 구현을 보지 않았다

명령·플래그는 그대로입니다. scope 판정 규칙(언제 worktree를 고르는가)도 0.49.1과 같습니다. 바뀐 것은 worktree가 무엇을 리뷰하는가와, 그 범위를 기록에 남기는 두 키입니다. 명시한 --scope diff·task-docs는 동작이 같습니다.

worktree의 새 의미 — merge-base 이후 전부

기준점은 diff scope가 <base>...HEAD로 쓰는 것과 같은 merge-base입니다. CLI가 sha를 계산해 프롬프트에 직접 넣으므로 리뷰어가 base를 추측하지 않습니다.

Fixed · #140

리뷰 범위 — 커밋 + 미커밋 + untracked

원인
worktree 프롬프트의 채움은 working tree changes 한 줄이었습니다. 리뷰어는 이를 git diff(HEAD 대비)로 읽어, 브랜치에 이미 커밋한 구현을 보지 않았습니다.
지금
채움이 working tree changes since <mergeBase>, the merge base with <base> — committed and uncommitted, including untracked files (git diff <mergeBase>; git status)가 됩니다. 프롬프트의 자리표시 문구 자체는 그대로라 미러는 바뀌지 않았습니다.
기본 브랜치
base 브랜치 위에서는 merge-base가 HEAD라 종전과 같은 범위(미커밋)입니다.
Fixed · #140

base를 못 정할 때 — 실패 대신 내려가기

사다리
--base → origin/HEAD → origin/main → origin/master(있는 ref만) → origin이 없을 때만 로컬 main. diff scope와 같은 순서입니다.
degrade
git 저장소가 아니거나 base·merge-base를 못 구하면 실패하지 않고 종전 의미(미커밋만)로 리뷰하고, 출력 맨 앞에 경고와 --base <ref> 재실행 안내를 냅니다.
error
명시한 --base가 틀린 경우만 exit 1이고 아무것도 기록하지 않습니다. 미커밋만 리뷰하고 싶으면 --base HEAD를 줍니다.

기록과 과거 기록 — 두 키로 구분한다

meta.reviews[] 항목은 git scope(worktree·diff)일 때 base·mergeBase를 함께 남깁니다. mergeBase..tip이 그 리뷰가 본 범위의 사후 증명입니다. task-docs는 두 키를 쓰지 않습니다.

기록 모양읽는 법증거 자격
base·mergeBase 둘 다 값merge-base 이후 전부를 리뷰함(0.49.2 의미)그대로
둘 다 nulldegrade — 미커밋만 리뷰함그대로(경고만)
두 키 모두 없음0.49.1까지의 기록 — 미커밋만 본 것으로 읽음그대로(소급 없음)
가드는 바꾸지 않았습니다. done·verify 증거 판정은 종전처럼 리뷰 kind만 봅니다. worktree 기록을 증거에서 빼는 안은 기각했습니다 — 정당한 커밋 전 리뷰까지 빼면서 정작 결함(리뷰가 커밋을 안 봄)은 고치지 못하고, 이미 있던 증거를 소급해 무효로 만들면 가드가 --force를 부추깁니다.
