0.32.2는 질문 하나에서 시작했습니다 — "task를 시작하면 spec·plan이 자동 생성되나?" 답은 아니오였고, 확인하는 과정에서 더 좁은 공백이 드러났습니다. spec에는 writer(/harness-spec)와 validator(/harness-interview)가 모두 있는데, plan에는 validator만 둘(/harness-contrarian·/harness-simplifier) 있고 저자가 없었습니다. 게이트를 통과한 뒤 "plan 작성"을 누가·어떤 형식으로 하는지 문서 어디에도 없었습니다. 이 릴리스는 그 자리를 명령을 만들지 않고 채웁니다.

스캐폴딩은 골격만 만듭니다 — 그 다음이 비어 있었습니다

harness-team task <name>은 정적 템플릿으로 파일 6개를 씁니다. 요구사항을 읽고 채우는 동작은 이 명령에 없습니다 — 그것은 설계대로입니다. 문제는 채우는 쪽의 담당자가 spec에만 적혀 있었다는 것입니다.

단계writervalidator
spec/harness-spec (Confluence·Figma·인터뷰 3소스)/harness-interview (선행 채점 + 게이트 판정)
plan없음/harness-contrarian · /harness-simplifier

실무에서는 이미 superpowers:writing-plans를 쓰고 있었습니다. 즉 저자가 없었던 것이 아니라, 저자가 계약에 적혀 있지 않았습니다. 적히지 않은 관행은 세션이 바뀌면 사라집니다.

두 가지 자연스러운 답을 모두 기각했습니다

"/harness-spec에 합친다"와 "/harness-plan을 만든다" — 둘 다 그럴듯했고, 둘 다 이 저장소의 기존 결정과 충돌했습니다.

기각

/harness-spec에 plan 초안을 합치기

왜 안 되나
"plan.md를 선작성하지 않는다"는 스타일 규칙이 아니라 Ambiguity 게이트를 지탱하는 장치입니다. 통과를 선언하는 곳은 /harness-interview 한 곳뿐이고, writer가 plan까지 쓰면 검증되지 않은 spec에 대한 실행 계획이 나옵니다.
부차적
입력이 다릅니다 — spec은 외부 3소스, plan은 코드베이스 탐색. 한 페르소나에 검색 모드 둘을 얹는 셈입니다.
보류

/harness-plan 페르소나 명령 신설

왜 지금은 아닌가
이 저장소가 형식 계약에 쓰는 관용구는 페르소나 명령이 아니라 결정론적 검사입니다 — context check·boundary check. 같은 모양의 문제를 이미 두 번 그렇게 풀었습니다.
비용
외부 스킬을 감싸는 명령은 /harness-diagram이 겪은 preflight 부담(설치 상태가 머신마다 다름 · 없다고 task를 실패시키지 않음 · 폴백 계약)을 그대로 물려받는데, 고유 내용은 형식 규칙 몇 줄입니다.
대신
이미 실무에 있던 superpowers:writing-plans를 계약에 적었습니다. 없으면 직접 씁니다.

흩어져 있던 계약 네 가지를 한 절로 모았습니다

AGENTS.md에 ### plan.md 계약이 생깁니다. plan.md가 산문이 아니라 다른 명령의 입력이기 때문에 필요한 목록입니다.

계약누가 읽나어기면
## 단계의 줄머리 체크박스harness-team done 가드 · SessionStart 재개 후보 판정미완 - [ ]가 남으면 완료가 막히고, 하지 않은 단계를 미리 - [x]로 켜면 종결이 거짓이 됩니다
다이어그램 옵트인 체크박스그 자체가 상태지우면 옵트인 사실이 사라지고, 열어 두면 done이 막힙니다 — 사유를 붙여 닫습니다
## Ontology 변경 로그spec.md의 Ontology 절 갱신 트리거개념 변화가 spec에 반영되지 않습니다
spec의 ## Boundary contracts · ## Done evidencecheckbox 완료 직전 boundary check · 종결 시 done 가드선언과 plan 단계가 어긋납니다
상세는 복제하지 않고 각 정본을 가리킵니다. 다이어그램은 harness-task 명령 문서, 나머지는 spec 템플릿과 done 가드입니다. 이 절은 plan.md 관점의 색인이지 새 정본이 아닙니다 — 정본을 둘로 만들면 다음에 갈라집니다.

문서 두 곳으로 끝나지 않았습니다

계약을 AGENTS.md에만 쓰면 두 종류의 독자가 그 계약에 도달하지 못합니다. 리뷰에서 잡혀 표면 두 곳을 더 열었습니다.

표면변경없었으면
AGENTS.md · templates/AGENTS.md.hbs### plan.md 계약 절 신설(마커 구간 동기 유지)—
commands/harness-interview.md게이트 통과 6번 인계에 writer + 폴백 명시통과 선언 직후가 계속 비어 있습니다
skills/harness-interview/SKILL.mdCodex 미러에 superpowers:writing-plans 번역 규칙Codex 세션은 그 이름을 해석할 수 없습니다 — Claude 플러그인 스킬 이름입니다
templates/.claude/skills/new-feature/SKILL.md소비자 스캐폴드 Phase 2에서 계약으로 링크소비자 프로젝트에는 "체크리스트 작성" 한 줄만 남습니다
src/commands/task.mjs안내 라인에 plan.md 작성 단계 삽입/harness-interview → 구현으로 plan이 건너뛰어 보입니다
CLI 출력에는 superpowers:writing-plans를 넣지 않았습니다. 미설치 환경에서 없는 명령을 가리키게 됩니다. --json 엔벨로프의 nextActions도 그대로 뒀습니다 — 생성 직후의 "즉시 다음 행동"은 spec 초안이 맞고, plan은 게이트 통과 이후입니다.

2·3단계는 조건을 적어 두고 만들지 않았습니다

"있으면 좋다"는 언제나 참입니다. 올라가는 조건을 관측 가능한 사건으로 적었습니다.

단계무엇올라가는 조건
1 (이번)writer 명시 + 계약 색인—
2harness-team plan check — 결정론적 형식 검사문서로 막히지 않는 형식 깨짐이 실제로 관측될 때
3/harness-plan 페르소나 명령초안 작성 자체가 실패 지점으로 드러날 때
유일한 실증 데이터는 명령을 정당화하지 않습니다. 이 영역의 실제 사고는 소급 task에서 아직 하지 않은 단계를 - [x]로 켰다가 Codex P2를 받은 한 건뿐입니다. 그런데 "체크된 항목이 실제로 수행됐는가"는 결정론적으로 판정 불가이고, 초안 생성기가 있었어도 나중에 사람이 켠 그 체크를 막지 못합니다. 규율·문서 쪽 문제라 1단계에 넣었습니다.
