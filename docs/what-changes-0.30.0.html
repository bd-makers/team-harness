가드가 브랜치 이름 대신 커밋을 봅니다
— summary --write

0.30.0은 공유 원장 가드의 판정 기준 하나를 바꿉니다. harness-team summary --write는 docs/task_summary.md와 docs/<user>/<user>-task.md를 렌더하는데, 이 파일들은 D5가 기본 브랜치에만 유보한 생성물이라 feature 브랜치에서 갱신하면 병렬 브랜치끼리 다시 충돌합니다. 그래서 가드는 브랜치 이름이 기본 브랜치가 아니면 거부해 왔습니다. 문제는 이름이 잘못된 대리 지표라는 점입니다 — git worktree 세션은 원본 체크아웃이 main을 점유해 애초에 체크아웃할 수 없고, 내용이 origin/main과 한 커밋도 다르지 않은 브랜치에 서 있어도 거부당했습니다. 남는 길은 매번 --force였고, 우회가 습관이 되면 진짜 feature 브랜치에서도 그대로 눌립니다. 이제 가드는 이름이 아니라 HEAD 커밋이 기본 브랜치와 정확히 같은가를 봅니다.

Changed

이름이 아니라 커밋으로 판정합니다

변경
브랜치 이름이 기본 브랜치가 아니어도, HEAD가 origin/HEAD가 가리키는 브랜치와 정확히 같은 커밋이면 원장을 씁니다.
왜 안전한가
그런 브랜치에는 로컬 커밋이 하나도 없습니다. 원장 커밋이 기본 브랜치 tip 바로 위에 얹히므로 기본 브랜치에서 쓴 것과 결과가 같습니다. 가드가 막으려던 "병렬 브랜치끼리의 충돌"이 성립할 수 없는 상태입니다.
그래서
worktree 세션이 원장을 갱신할 때 더 이상 --force가 필요 없습니다. --force는 남아 있지만, 이제 진짜로 갈라진 상태에서만 쓰이는 escape hatch입니다.
판단

왜 우회 습관이 문제였나

증상
worktree 세션은 기본 브랜치를 체크아웃할 수 없습니다(원본 체크아웃이 점유). 원장을 갱신하려면 매번 --force였습니다.
왜
가드는 거부해야 할 상태와 거부할 필요가 없는 상태를 이름으로 구분할 수 없었습니다. 그래서 정당한 우회가 일상이 되고, 일상이 된 우회는 정당하지 않은 자리에서도 그대로 눌립니다.
그래서
가드의 값어치는 "얼마나 많이 막느냐"가 아니라 거부가 신호로 남느냐에 있습니다. 새 경로가 열린 뒤 남는 거부는 전부 진짜로 갈라진 상태입니다.

왜 정확한 동일성만인가 — 열지 않은 것들

"기본 브랜치와 관계있음"에는 여러 눈금이 있습니다. 이 릴리스는 그중 가장 좁은 하나만 엽니다.

상태판정근거
HEAD == origin/HEAD tip허용로컬 커밋 0개 — 기본 브랜치에서 쓴 것과 결과가 같습니다
ahead (로컬 커밋 있음)거부진짜 feature 브랜치입니다. ancestor 관계는 인정하지 않습니다
behind거부낡은 base 위에 렌더한 뒤 push가 non-fast-forward로 실패해 더 헷갈립니다
origin/HEAD 없음거부기본 브랜치를 특정할 수 없으므로 새 경로를 열지 않습니다
rev-parse 실패 · unborn HEAD · git 오류거부fail-closed — 예외는 전부 false로 떨어집니다
판정 근거는 origin/HEAD 하나뿐입니다 — 이것이 리뷰가 바꾼 계약입니다. 초안은 기존 defaultBranchCandidates(main/master 폴백)를 재사용했는데, 실제 기본이 main이고 origin/HEAD는 없으며 origin/master만 남은 저장소에서 0.29.0이 거부하던 브랜치가 통과해 원장을 실제로 썼습니다. 그 브랜치의 커밋은 진짜 기본으로 fast-forward 되지 않으므로, behind를 거부한 근거와 정면으로 모순됩니다. 같은 폴백이라도 이름 판정에서는 아무것도 열지 않지만(feature 브랜치는 어차피 거부됩니다) 커밋 판정에서는 쓰기를 엽니다. 그래서 helper는 defaultBranchCandidates를 아예 호출하지 않습니다.

ref는 refs/remotes/<base>로 완전하게 씁니다 — origin/main이라는 이름의 로컬 브랜치나 태그가 판정을 대신 답하지 못하게 하기 위해서입니다.

호환성 — 무엇이 실제로 달라지나

표면변화영향
기본 브랜치에서 --write무변경이름 판정이 먼저 통과하므로 helper를 부르지 않습니다
synced 브랜치에서 --write거부 → 허용이 릴리스가 여는 유일한 경로입니다
ahead·behind 브랜치무변경계속 거부됩니다
거부 메시지 · cause/retry/alternatives무변경escalation 패킷 형식도 그대로입니다
--check무변경가드 위에서 return으로 끝나 도달하지 않습니다 — BEFORE/AFTER 실행으로 대조했습니다
origin 없는 로컬 전용 저장소무변경origin/HEAD가 없어 새 경로가 열리지 않습니다
defaultBranchCandidates무변경helper가 호출하지 않습니다

외부 검증 — 적대적 리뷰 1회 + shipcheck 1회

별도 컨텍스트의 read-only 리뷰어(codex gpt-5.6-sol)가 diff를 봤습니다. 발견은 전부 재현한 뒤 판별해 반영했습니다.

회차판정발견조치
적대적 리뷰P0·P1 없음, P2 1건BRG-01 — 폴백이 쓰기를 연다수용 · origin/HEAD 단일 기준으로 재설계
shipcheck (D6)REJECTS1·S5 BLOCKER둘 다 수용 · 문서 6곳 정합화 + 검증 기록 교체

BRG-01은 기각할 뻔했습니다. "이름 판정도 이미 느슨하다"는 반론이 있었고, 실측해 보니 그 반론 자체는 사실이었습니다(후보가 둘일 때 master가 origin/master보다 ahead여도 0.29.0이 통과시킵니다). 그러나 발견을 무효화하지는 않았습니다 — 기존 느슨함은 범위 밖의 계약이고, 새 경로가 그 위에 쓰기 표면을 더한 부분이 이 변경의 책임이기 때문입니다.

shipcheck의 두 BLOCKER는 모두 "문서가 코드보다 낡았다"였습니다. S1은 BRG-01 반영 때 spec Ontology와 CHANGELOG는 고쳤지만 설계 절·갈라진 브랜치 정의·자가진단·plan·TCC에 옛 계약이 남은 것을 짚었고, S5는 "검증 (전부 실행 결과)"라고 선언해 놓고 정작 산문으로 요약한 것을 짚었습니다. 네 블록을 실제 명령·출력 transcript로 교체했습니다. 리뷰어의 한계도 기록합니다 — read-only 샌드박스라 전체 npm test를 재실행하지 못했고 node --check만 돌렸습니다. 재실행은 작성 세션이 했습니다.

배운 것 — 통과하는 테스트는 커버리지의 증거가 아니다

이 task가 추가한 ahead·behind 테스트는 구현 전부터 통과했습니다(이름 판정이 이미 거부하므로). "그러면 회귀 방지용으로 잘 고정하고 있다"고 추론한 뒤 넘어갈 뻔했습니다. mutation을 넣어 돌려 보니 판정이 갈렸습니다:

mutation결과뜻
B: 정확 동일성 → origin ref 존재만으로 허용ahead·behind 테스트 RED두 테스트가 진짜로 정확 동일성을 고정합니다
C: origin ref 없을 때 fail-open기존 로컬 전용 테스트 2개 REDplan이 요구한 커버리지를 기존 테스트가 이미 갖고 있었습니다
A: rev-parse HEAD 실패 시 fail-open전부 통과미커버 경로 — 도달 경로를 잘못 짚었습니다

A가 뚫린 이유는 rev-parse HEAD가 origin이 없어도 성공하기 때문입니다. 실패하는 것은 커밋이 하나도 없는(unborn) HEAD이고, branchState는 거기서도 브랜치 이름을 냅니다. 그 상태 테스트를 새로 넣고 mutation A를 다시 얹어 RED을 확인한 뒤에야 fail-closed가 고정됐다고 말할 수 있게 됐습니다.

적용법: 구현 후에도 통과 상태로 남는 테스트를 plan에 세울 때는, 그 테스트가 지키는 불변식을 깨는 mutation을 한 번 넣고 RED을 봅니다. 통과만 보고 체크박스를 닫지 않습니다. "이 테스트는 X를 잡는다"는 코드를 읽고 세운 가설이지 관측이 아닙니다.

주석으로 문서화한 느슨함은 고친 것이 아닙니다. 구현 중에 폴백 문제를 알고 있었고, "이름 판정이 이미 갖던 성질"이라는 근거로 주석 한 문단으로 처리했습니다. 리뷰어는 주석을 읽고 넘어가지 않습니다 — 동작을 봅니다. 판정을 가른 것은 "기존에도 느슨했다"가 아니라 느슨함이 무엇을 여는가였습니다. 답이 "쓰기"면 주석이 아니라 코드를 고칩니다.
