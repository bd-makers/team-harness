모노레포 task를
앱·서비스 단위로 묶습니다

harness-team task web-next-login --area web-next는 task의 meta.json에 area를 기록하고, list·원장이 그 값을 보여 줍니다. 경로는 바꾸지 않습니다 — docs/<app>/<user>/<task>/ 3단 구조를 검토했지만 실측한 위험 때문에 보류했습니다. 그 준비로 흩어져 있던 task 경로 조립을 한 곳으로 모았고, 이것은 동작 변화가 없는 리팩터입니다.

더한 것과 바꾼 것

Added · CLI

--area — task를 앱 단위로 묶는 라벨

무엇
task <area>-<이름> --area <area>가 meta.area를 기록합니다. list는 줄 끝에 [area]를 붙이고 list --area로 거릅니다. 원장(summary)은 area를 가진 task가 하나라도 있을 때만 Area 열을 맨 뒤에 붙입니다 — 맨 뒤라 원장 역파싱이 그대로 맞습니다.
왜
앱마다 제품·담당·릴리스가 다른 모노레포에서 <area>-<name> 이름 접두는 사람만 읽었습니다. web과 web-next처럼 접두가 겹치면 이름만으로는 area가 모호합니다 — 정본은 이제 meta.area입니다.
규칙
접두로 먼저 만든 task에 --area를 주면 채택합니다(meta에 area만 추가, 판정 창 필드 보존). 이미 다른 area인 task·접두 없는 이름·형식 위반은 exit 1이고 아무것도 쓰지 않습니다. area는 바꾸지 않습니다 — 다른 area의 일이면 새 task입니다.
Changed · 동작 변화 없음

task 경로 조립을 한 곳으로

이전
docs/<user>/<task>/…를 13파일 약 60줄에서 따로 조립했고, task를 판정하는 2단 스캐너가 3벌 복제돼 있었습니다. 경로 규칙을 바꾸려면 전부를 같이 고쳐야 했습니다.
지금
src/task-paths.mjs가 유일한 조립 지점입니다. 새 조립 지점은 tests/task-paths-single-source.test.mjs가 막습니다.
증거
리팩터 전 코드에서 먼저 green으로 고정한 golden e2e가 파일 바이트·stdout을 대조합니다. 보강한 스냅샷도 리팩터 전 트리에서 다시 green인 것을 확인했고, --area 추가 뒤에도 그대로 통과합니다.
Decision

3단 경로는 왜 보류했나

설정 위치
레이아웃 스위치를 둘 .harness/config.json은 소비자 저장소에서 gitignore 대상입니다 — 클론마다 task 위치가 갈립니다.
오인
migrate의 레거시 탐지가 3단 구조를 옛 task로 읽어 파일을 만드는 것을 실측했습니다(user 디렉터리 아래 handoff, user 이름 fix·feature).
결론
목록·묶음·소유권은 meta.area와 glob(CODEOWNERS docs/*/web-next-*/)으로 충분합니다. 디렉터리 prefix를 요구하는 도구가 생기면 커밋되는 area 마커 방식으로 다시 봅니다 — 설계 기록은 docs/spec-monorepo-scope.md.

소비자가 할 일

Do

플러그인 갱신만

왜
templates/가 바뀌지 않았습니다. --area를 쓰지 않는 저장소는 파일·출력이 종전과 같습니다.
어떻게
/plugin marketplace update(또는 clone에서 git pull). migrate는 필요 없습니다.
Optional

접두 규약을 쓰던 모노레포

무엇
이미 <area>-<name>으로 만든 task는 harness-team task <그 이름> --area <area>로 한 번씩 채택하면 list·원장에 area가 보입니다.
주의
원장에 Area 열이 처음 생기는 시점에 summary --check가 낡았다고 보고합니다 — 기본 브랜치에서 summary --write로 갱신하면 됩니다.
