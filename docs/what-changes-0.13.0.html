정확성 수정

Install guidance

존재하지 않는 npm 패키지를 가리키던 설치 안내 수정

변경
npm i -g harness-aijient-team은 npm 공개 저장소에 없어 404로 실패했습니다. README·doctor의 경고 detail·JSON nextActions를 모두 /plugin install이 만드는 로컬 마켓플레이스 클론을 링크하는 절차(npm i -g ~/.claude/plugins/marketplaces/harness-aijient-team-marketplace)로 맞췄습니다.
왜
안내가 실제로 동작하는지는 추측이 아니라 실측으로만 확인할 수 있습니다. 이 머신의 npm ls -g가 이미 마켓플레이스 클론 경로를 링크하고 있었고, 그것이 유일하게 동작하는 형태였습니다. 선장은 이번에 npm 공개 배포를 하지 않기로 확정했습니다.
그래서
README·doctor 경고·자동화된 nextActions가 같은 절차를 가리키게 되어, clone한 팀원이 안내를 그대로 따라도 전역 CLI가 실제로 연결됩니다.

새 기능

task 활성화와 CLI 연결 상태처럼, 사람이 놓치기 쉬운 다음 단계를 도구가 직접 안내합니다.

Task activation

task 생성·재활성화 평문 출력에 다음 단계 안내 추가

변경
harness-team task <name>의 평문 출력이 spec 작성부터 done까지 이어지는 다음 단계를 안내합니다. 재활성화 시에는 plan의 현재 단계 힌트도 함께 보여줍니다. --json 스키마는 그대로입니다.
왜
task를 만들거나 재개한 뒤 다음에 뭘 해야 하는지가 도구 출력에 없으면, 에이전트가 spec 작성이나 interview 단계를 건너뛰기 쉬웠습니다.
그래서
task 생성 직후 화면에서 바로 다음 행동이 보이고, 재개 시에는 어디까지 했는지 다시 plan 전체를 읽지 않아도 됩니다.
Doctor check

훅이 호출하는 CLI의 실행 가능성을 doctor가 직접 검사

변경
harness-team doctor가 PATH의 harness-team이 실제로 실행되고 session-context/handoff를 지원하는지 확인합니다. 실패하면 전역 CLI를 다시 링크하라는 복구 안내를 냅니다. 플러그인 소스 저장소 자신은 이 검사를 n/a로 skip합니다.
왜
SessionStart/post-commit 훅은 PATH의 harness-team을 호출합니다. CLI가 끊겨 있으면 훅이 조용히 아무 일도 하지 않고, 증상은 한참 뒤에야(재개 안내가 안 뜨는 식으로) 드러났습니다.
그래서
CLI 연결이 끊긴 상태를 doctor 실행 시점에 바로 알 수 있고, 위 설치 안내 수정 덕분에 복구 명령도 실제로 동작합니다.

문서·유지보수

clone한 팀원이 실제로 밟는 순서를 README에 명시적으로 남겼습니다.

Onboarding

독립된 3채널과 clone 팀원 복구 절차 문서화

변경
apply / Claude Code 플러그인 설치 / 전역 CLI 링크가 서로 독립된 채널임을 표로 명시하고, 이미 하네스가 적용된 저장소를 clone한 팀원이 밟아야 할 순서(플러그인 설치 → 전역 CLI 링크 → doctor)를 README에 추가했습니다.
왜
세 채널 중 하나만 완료하고 나머지를 완료했다고 착각하는 사례가 있었습니다. apply가 슬래시 커맨드까지 설치한다는 오해가 대표적입니다.
그래서
clone한 팀원이 자신에게 부족한 채널이 무엇인지 표에서 바로 확인하고, 순서대로 따라가면 실제로 완결됩니다.
Enforcement table

에이전트별 강제력 비대칭을 표로 명시

변경
Claude Code(hooks 4종 + 커맨드 19개)와 그 외 에이전트(OpenCode/Gemini/Cursor/Codex, hooks 0)가 받는 강제력 차이를 README에 표로 남기고, 훅이 .claude/settings.json에 사는 Claude Code 전용 메커니즘이라는 구조적 이유를 함께 설명했습니다.
왜
다섯 에이전트가 같은 규칙을 같은 강도로 지킬 거라는 암묵적 기대가 있었지만, 실제로는 Claude Code 외 에이전트는 결정론적 강제 없이 규범(문서)에만 의존합니다.
그래서
Codex·Gemini·Cursor·OpenCode를 쓰는 팀원이 자신의 에이전트에서 무엇이 자동으로 지켜지고 무엇을 스스로 챙겨야 하는지 문서만 보고 판단할 수 있습니다.

이번 릴리스가 택한 방향

문서를 고치는 방법도 하나로 수렴합니다: 추측한 절차가 아니라, 실측해 확인한 절차만 안내에 남긴다.

추측보다 실측

안내 문구를 "그럴듯한 명령"으로 고치는 대신, 이 머신에서 실제로 동작하는 npm ls -g 링크 대상을 확인한 뒤 그 결과를 안내·경고·nextActions에 그대로 반영했습니다.

일관성은 세 자리 동시 수정으로

설치 절차 하나를 고치려면 README·doctor.mjs 경고·JSON nextActions 세 곳이 함께 맞아야 합니다. 한 곳만 고치면 사람이 보는 안내와 에이전트가 받는 복구 명령이 다시 어긋납니다.
