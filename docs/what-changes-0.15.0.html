0.14.0 이후 병합된 #22를 배포하는 0.15.0 minor 릴리스입니다. 하네스는 "Codex와 Cursor도 같은 SSOT에서 설정을 받는다"고 문서에 적어 왔지만, 실제로는 Codex 세션이 task context를 전혀 받지 못했고 Cursor 미러는 규칙의 경로 스코프를 파괴한 채 넘겨주고 있었습니다. 이번 릴리스는 그 간극을 산출물 단위로 메웁니다.

Codex 표면 완성

Claude 세션은 SessionStart 훅으로 활성 task의 Context Card를 받아 왔습니다. 같은 SSOT를 공유한다던 Codex 세션에는 그 경로가 아예 없었습니다.

Session context

Codex SessionStart 훅 템플릿

변경
templates/.codex/hooks.json을 신설해 apply/init이 대상 프로젝트에 설치합니다. Claude 쪽 .claude/settings.json과 동일하게 harness-team session-context를 호출하고, 훅이 Codex 세션의 cwd에서 실행되므로 --target "$(git rev-parse --show-toplevel || pwd)"로 저장소 루트를 직접 해석합니다.
왜
0.14.0 시점에 Codex CLI가 프로젝트 로컬 훅을 지원한다는 사실이 확인됐는데도 하네스는 그 표면을 쓰지 않았습니다. 그동안 Codex 세션은 활성 task·Context Card 없이 시작했고, 이는 "같은 SSOT"라는 약속이 Claude에만 성립했다는 뜻입니다.
그래서
Codex 세션도 활성 task의 Context Card를 주입받습니다. 하위 디렉터리에서 Codex를 띄워도 "활성 task 없음"으로 오보하지 않고, .claude/settings.json·.opencode/opencode.json과 같은 JSON deep-merge 레인을 쓰므로 이미 자기 Codex 훅을 쓰던 프로젝트도 사용자 훅을 잃지 않습니다(재적용 멱등).
Backup architecture

.codex를 백업 대상에 포함

변경
backup/clone/symlink/delete/upgrade의 item 목록(JS 5곳 + shell 템플릿 3곳)과 AI gitignore 항목에 .codex를 추가했습니다.
왜
훅 템플릿이 .codex/를 만들기 시작하면서, 백업 아키텍처가 모르는 디렉터리가 생겼습니다. 그대로 두면 backup 시 .codex만 프로젝트에 실물로 남고 delete 시 잔재가 남습니다.
그래서
Codex 설정이 다른 하네스 산출물과 같은 수명주기(백업 → 심볼릭 링크 → 제거)를 따릅니다.

Cursor 규칙 미러 정합

.claude/rules → .cursor/rules 미러는 "규칙을 그대로 전달한다"고 가정돼 있었지만, 실제로는 스코프를 넓히고, 지우지 않고, 일부는 빠뜨리고 있었습니다.

Scope

경로 스코프를 파괴하던 미러

변경
paths: frontmatter를 Cursor globs:(auto-attach, alwaysApply: false)로 번역하고 원본 frontmatter는 소비합니다. paths:가 없는 규칙만 alwaysApply: true로 남습니다.
왜
미러가 paths:를 무시하고 모든 규칙에 alwaysApply: true를 붙인 뒤 원본 frontmatter를 본문에 그대로 남겼습니다. 좁혀 둔 규칙이 Cursor에서는 항상 로드되고, 죽은 frontmatter가 리터럴 텍스트로 프롬프트에 섞였습니다.
그래서
같은 규칙이 두 에디터에서 같은 범위로 적용됩니다.
Prune

원본이 사라져도 남던 미러

변경
.harness/cursor-mirror.json에 직전 실행이 쓴 경로를 기록하고, 그 기록에 있으면서 이번에 다시 쓰이지 않은 산출물만 제거합니다. 비게 된 디렉터리를 정리하고 sync가 prune 건수를 보고합니다.
왜
미러가 쓰기만 하고 지우지 않아, 규칙 이름을 바꾸거나 폴더로 옮기면 옛 .mdc가 남고 Cursor는 그것을 계속 로드했습니다 — 규칙 하나가 옛 스코프와 새 스코프로 두 번 적용되는 셈입니다.
그래서
삭제 권한을 파일 내용이 아니라 기록에서 가져오므로, 생성물을 복사해 만든 사용자 규칙과 구버전 산출물은 건드리지 않습니다. <!-- harness:mirror --> 스탬프는 2차 게이트로 남아, 사용자가 스탬프를 지우면 인수한 것으로 보고 보존합니다.
Recursion

하위 디렉터리 규칙 누락

변경
재귀 탐색으로 구조를 보존해 미러합니다(frontend/styling.md → .cursor/rules/frontend/styling.mdc). 공유 규칙 심볼릭 링크도 따라가되 realpath 집합으로 순환을 차단합니다.
왜
미러가 최상위 readdir 하나만 돌았습니다. Claude Code는 .claude/rules/**/*.md를 재귀 탐색하므로, 규칙을 폴더로 정리한 프로젝트에는 Claude에는 있고 Cursor에는 없는 규칙이 조용히 생깁니다.
그래서
규칙을 폴더로 정리해도 두 에디터가 같은 집합을 봅니다.
YAML

파싱되지 않던 globs: 값

변경
glob이 YAML indicator로 시작할 때만 작은따옴표로 감쌉니다. 일반 케이스는 Cursor 문서의 평문 형태를 유지합니다.
왜
**/*.ts·[id].tsx가 첫 항목이면 생성된 frontmatter가 통째로 파싱 불가입니다(**는 alias, [는 flow sequence로 읽힘). 현 템플릿 4개가 전부 src/·app/ 선행이라 우연히 통과하고 있었습니다.
그래서
사용자가 자기 규칙에 흔한 glob을 쓸 때 미러가 조용히 무효가 되지 않습니다.

안내 정정

강제력 표는 0.11.0 probe 기준이라 낡았고, 규칙 표면의 비대칭은 어디에도 적혀 있지 않았습니다.

README

규칙 표면의 비대칭을 명시

변경
강제력 표에 경로 스코프 규칙 열을 추가하고 .claude/rules가 팀 전체 규칙이 아니라는 경고를 넣었습니다. Codex | hooks 0 표기도 정정해, 훅 표면과 커맨드 표면을 분리해 기술했습니다.
왜
경로 스코프 규칙을 읽는 건 Claude Code(+미러를 받는 Cursor)뿐이고 Codex·Gemini·OpenCode는 .claude/를 보지 않습니다. 리뷰 기준을 .claude/rules에 두면 리뷰어(Codex)가 모르는 기준으로 리뷰하게 됩니다.
그래서
팀 전체가 지켜야 할 기준은 AGENTS.md에, 편집 시점 힌트는 .claude/rules에 — 어디에 무엇을 둘지 판단할 근거가 문서에 남습니다.
Codex skill

커맨드 안내 공백

변경
skills/harness-team/SKILL.md의 커맨드 목록에 context init|check(0.13)와 release(0.12)를 추가했습니다. 훅·하네스가 호출하는 session-context·boundary check는 직접 호출 금지로 명시했습니다.
왜
Codex에게는 이 스킬이 유일한 진입점이라, 안내 공백이 곧 기능 공백입니다. 두 릴리스에 걸쳐 추가된 커맨드가 목록에서 빠져 있었습니다.
그래서
Codex 세션이 Context Card를 스스로 만들고 검사할 수 있고, 에이전트가 호출해선 안 되는 명령의 경계도 분명해집니다.

이번 릴리스가 택한 방향

모든 변경이 한 문장으로 수렴합니다: 설정이 전달됐다는 것은 문서가 아니라 산출물이 증명한다.

존재가 아니라 내용을 검사한다

doctor는 .codex/hooks.json의 존재·JSON 유효성만이 아니라 harness SessionStart 훅이 실제로 들어 있는지까지 확인합니다. 손으로 편집해 harness 그룹이 빠진 파일은 파싱 검사만으로는 healthy로 보이지만, 그 상태가 곧 Codex 세션이 조용히 task context를 잃는 드리프트입니다.

삭제 권한은 기록에서 온다

Cursor 미러 prune은 생성물 스탬프가 아니라 .harness/cursor-mirror.json의 직전 실행 기록에서 삭제 권한을 얻습니다. 스탬프는 공개 문자열이라 사용자가 복사해 만든 규칙도 그것을 가질 수 있기 때문입니다 — 무엇을 만들었는지 아는 쪽만 지울 자격이 있습니다.
