intent.md는 파일이 아니라 질문 두 개였습니다
— Problem 축 · (open) 규약 · observe 루프백 nudge

0.31.0은 Anthropic의 AI-Native SDLC Playbook이 Stage 1에 두는 intent.md를 하네스와 대조한 결과입니다. 플레이북은 발의자가 자기 언어로 쓴 proto-spec(Problem · Proposed outcome · Affected users and systems · Constraints · Open questions)을 별도 파일로 커밋하고, product owner의 accept가 spec.md 생성을 트리거하며, 운영 지표 이탈은 다시 intent.md를 써서 같은 루프에 넣습니다. 하네스의 spec 템플릿과 Ambiguity 게이트는 그중 대부분을 이미 담고 있었고, 빠진 것은 "오늘 무엇이 안 되는가"를 묻는 축과 답 없는 질문의 집, 그리고 관측 이탈을 task로 잇는 간선이었습니다. 이 릴리스는 6번째 파일을 만들지 않고 그 셋을 기존 표면에 넣습니다.

무엇이 달라졌나 — spec 표면에 흡수한 두 요소

파일·게이트·가중치는 늘리지 않습니다. 바뀌는 것은 /harness-spec·/harness-interview 명령 문서의 계약과 spec 템플릿의 안내문 한 줄입니다.

Changed

Problem 축 — 오늘 무엇이 안 되는가, 누가 영향받는가

변경
/harness-spec 인터뷰 차원에 Problem이 앞에 붙습니다. /harness-interview의 선행 채점은 Goal을 pass로 주려면 기대 결과 문장과 문제 문장 두 개를 spec에서 인용해야 하고, 문제 문장이 없으면 Goal은 pass가 아니라 na입니다. Goal 질문 각도에 "오늘 사용자가 무엇을 못 하는가? 누가 영향받는가?"가 들어갑니다.
왜 채점 차원을 늘리지 않았나
인터뷰어는 채점표에서 fail 또는 na인 차원에만 질문을 만듭니다. Problem을 별도 각도로 두면 트리거가 없어 발사되지 않고, 다섯 번째 가중 축으로 만들면 기존 task의 자가진단과 템플릿이 갈립니다. Goal 차원 안에 넣으면 기존 구조 안에서 발사됩니다.
그래서
결과만 있고 문제가 없는 spec — 해결책이 문제를 찾는 상태 — 가 게이트를 통과하지 못합니다. 직접 작성 경로는 spec 템플릿 목적 절의 안내문(문제 → 영향 → 기대 결과 → 제약)이 같은 순서를 요구합니다.
Changed

(open) 규약 — 답 없는 질문은 요구가 아니다

변경
답을 못 받았거나 범위 밖으로 미룬 질문은 spec ## 참고 절에 - (open) … 항목으로 남깁니다. 게이트는 항목마다 답이 spec에 반영돼 마커가 지워졌거나 - (open → <대상>) …으로 이월 대상이 적혀 있어야 통과를 선언합니다.
왜 절을 만들지 않았나
writer의 (unresolved)는 소스 충돌 전용이고 validator의 follow-up은 범위 내 질문만 다루므로 범위 밖 질문은 사라졌습니다. 그렇다고 점수 없는 산문 절을 추가하면 "고쳐진 것처럼 보이는" 표면만 늘어납니다. 목록 항목 + 마커는 grep 가능하고 게이트 조건으로 검사됩니다.
그래서
(unresolved)와 (open)이 구분됩니다 — 앞은 요구가 둘이고 선택이 남은 것, 뒤는 답 자체가 없는 것입니다. 안내문은 산문이라 sim의 출처 태그 규칙(요구사항 절의 목록 항목만 셈)에 잡히지 않으며, 그 사실을 테스트가 고정합니다.

관측 이탈이 task로 이어집니다 — nudge이지 emitter가 아닙니다

harness-team observe는 트립와이어가 발화하면 exit 1과 세션 로그 추적 안내로 끝났습니다. 발화 내용이 task로 이어지는 간선이 없었습니다.

Added

루프백 nudge — harness-team task observe-<id>-<day>

변경
발화 시 --json의 next_actions 둘째 줄과 텍스트 출력의 next: 줄에 task 생성 제안이 붙습니다 — 제안된 이름으로 task를 열고 spec 목적 절에 발화 id·수치를 "오늘 무엇이 안 되는가" 문제 진술로 옮기라는 문장입니다.
왜 자동 생성이 아닌가
임계값(20·5·2×·3회)이 실사용 보정 전입니다. 자동 생성은 오탐 task를 만들고, 그 task는 done 가드가 다시 설득해야 하는 부채가 됩니다. 사람 또는 에이전트가 따를 때만 task가 생기는 SessionStart task-gate와 같은 nudge 계층입니다.
그래서
플레이북 Stage 6의 "이탈 → intent 작성 → 같은 파이프라인" 루프가 하네스 어휘로 닫힙니다 — 단, 사람이 그 줄을 따를 때만.
트립와이어<day>의 출처왜
failure-rate-2xdetail.day (오늘)오늘의 실패율을 직전 날들과 비교하는 지표라 사건일이 곧 실행일입니다
repeat-failure-3x최다 실패 hit의 마지막 실패 시각을 UTC 인스턴트로 버킷창 전체(최대 14일)를 검사하므로 실행일로 키를 잡으면 같은 사건이 매일 다른 이름을 받습니다
hit 없음 · 시각 깨짐실행일 폴백이름 없는 제안은 내지 않습니다
이름의 키가 실행일에서 사건일로 바뀐 것은 Codex P2의 결과입니다. 초안은 window.to를 썼습니다. spec에는 "재실행하면 새 task가 아니라 activated:로 수렴한다"고 적어 두고, 정작 무엇이 같아야 같은 이름이 나오는지는 따지지 않았습니다. 다음 날 재실행 시 같은 이름이 나오는지, 오프셋 타임스탬프가 UTC 기준으로 버킷되는지, 둘 다 발화하면 첫 와이어가 이름을 정하는지를 순수 함수 테스트로 고정했습니다.

만들지 않은 것 — 왜 6번째 파일이 아닌가

플레이북의 intent 요소 6개를 하네스 현 위치에 대응시킨 뒤, 파일 분리가 여는 실패 모드를 따졌습니다.

후보판정근거
<name>-intent.md 6번째 파일기각AGENTS.md가 "spec을 포인터 껍데기로 두지 말 것"을 금지하고 doctor checkActiveSpecGate가 경고합니다. intent를 떼어내면 spec 목적 절이 intent를 가리키는 껍데기가 되는 정확히 그 실패 모드가 되살아납니다. 표면은 이미 6개(SSOT 4 + TCC + meta)입니다
product owner accept 게이트 · intent home · 비엔지니어 발의기각(스코프)역할표(D2)에 PO가 없습니다. 도입은 역할 모델 변경이라 D 결정이 먼저입니다
요청자(author) 필드보류docs/<user>/는 실행자지 요청자가 아닙니다. 요청자 ≠ 실행자가 실제로 생길 때 meta.json에 넣습니다
요구 churn 지표(첫 plan 커밋 이후 spec 커밋 수)보류git log로 뽑을 수 있지만 읽을 소비자가 없습니다
Problem을 5번째 가중 축으로보류가중치를 파싱하는 코드가 없어 승격 비용은 템플릿 + 문서 2개뿐입니다. 문제공간 누락이 반복 관측되면 올립니다
observe 발화 시 task 자동 생성기각임계값 미보정 — 위 루프백 절 참조

역방향으로 하네스가 더 갖고 있는 것도 있습니다 — Success 기준(30%), Ontology, ## Done evidence, ## Boundary contracts. 플레이북이 spec.md 내용을 규정하지 않으므로 밀도를 비교할 수는 없지만, 기계가 검사하는 구조는 하네스 쪽이 더 많습니다.

별도 컨텍스트의 리뷰어(codex gpt-5.6-sol)가 워킹트리 diff를 봤습니다. 발견은 코드에서 재현한 뒤 반영했습니다.

판정발견재현조치
REQUEST CHANGES · P2 1건nudge의 task 이름이 실행일(window.to)을 쓰는데 repeat-failure-3x는 창 전체를 검사한다repeatFailureTripWire는 창 전체 레코드를 순회하고 hit에 last_at만 남김 — 진짜 결함wireDay() 도입 · 회귀 테스트 · 문서 4곳에 <day> 의미 명시

그 외 세 명령 문서의 계약 정합, 템플릿 안내문, (open) 규약, JSON·텍스트 공통 문구, task 문서가 diff를 옳게 서술하는지에서는 유의미한 불일치를 찾지 못했다고 했습니다. 리뷰어의 한계도 기록합니다 — read-only 샌드박스라 임시 디렉터리를 쓰는 테스트 18개를 돌리지 못했고(assertion 실패가 아니라 EPERM), 전체 스위트 재실행은 작성 세션이 했습니다.

배운 것 — 계약 문장에는 테스트가 붙어야 한다

spec에 "재실행 시 activated:로 수렴"이라고 적었습니다. 수렴·멱등 같은 단어는 무엇이 같아야 같은가를 전제하는데, 그 전제(이름 키의 입력이 실행일인가 사건일인가)를 테스트로 고정하지 않았습니다. 리뷰어가 그 자리를 짚었습니다. 적용법: 계약 문장을 spec에 쓰는 순간 그 문장이 참이 되는 조건을 테스트 하나로 옮깁니다.

외부 지침을 흡수할 때는 새 파일보다 기존 표면의 트리거 구조를 먼저 읽습니다. 두 세션이 같은 결론(6번째 파일 금지)에 이르렀지만, 한쪽 안은 인터뷰 "질문 각도"에 Problem을 추가하는 것이었습니다. 인터뷰어는 채점표의 fail/na 차원에만 질문을 만들므로 그 각도는 발사되지 않았을 것입니다. 문서 한 줄이 실제로 어느 분기에서 실행되는지 확인하는 것이 적용 판단의 절반입니다. 두 검토는 서로 다른 것도 봤습니다 — 한쪽은 요청자 ≠ 실행자를, 다른 쪽은 (open) 질문의 집을. 같은 프롬프트 N회가 아니라 다른 렌즈를 쓰라는 규칙의 실증입니다.
